### 1. ~~Arena mis-measures a near-champion candidate by ~280 Elo~~ — RESOLVED: NOT an arena bug
- **Root cause (confirmed 2026-08-07 by experiment):** training on SOFT self-play (τ 1.0→0.5) makes the trainer's policy **diffuse**; the arena **samples** at τ 0.6→0.2, so a diffuse policy samples sub-best moves and loses. The puzzle probe scores **argmax top-1**, which is blind to diffuseness — hence the probe read 1708 ("fine") while the arena read −280. The arena was measuring *correctly*.
- **Proof:** with everything identical (same seed, dropout=0) but **self-play τ set to the arena schedule (0.6/0.2/0.02)**, arena #1 = **43.1% / −48 Elo** (vs −211/−317 under soft self-play). The arena `pol` (played-move prob) column confirms the mechanism: soft run 0.20→0.68 (diffuse) vs sharp run 0.48→0.83 (sharp).
- **Why it only showed now:** past self-play runs forked *weak, co-evolving* champions (both sides soft → arena ~0). Tonight was the first fork of a **sharp corpus-distilled champion** into **soft** self-play, so the trainer softened away from it.
- **Not a code bug — a config/interpretation issue.** Follow-ups worth considering: (a) either keep self-play τ near the arena τ when forking a sharp champion, or scale the arena-vs-self-play τ gap deliberately; (b) the probe (argmax) and arena (sampled) disagree by construction — consider a sampled-play probe or reporting policy entropy so this divergence is visible without an arena. ### 1b. SYSTEMIC: in-memory weight transfer is by INDEX, not by name  *(latent fragility — audit ALL call sites; not tonight's culprit)*
- `ChessNetwork.exportWeights()` returns an ordered `[[Float]]` and `loadWeights()` consumes it **positionally** (`for (i, v) in allVars.enumerated()`, ChessNetwork.swift:1756+), guarded only by a **count** check — no per-tensor name match, only element-count-per-tensor. Any order divergence between the source and destination nets (different `bnMode`, different arch-build path, a future refactor that reorders `trainables.append`) **silently loads weights into the wrong slots**: no error, because the count still matches. This is inherently fraught.
- **Widespread — ~12 `trainer.network.exportWeights()` sites cross bnMode by index**, plus inference-source ones: arena candidate sync (Arena:94-96, training→inference), arena champion sync (131-132, inf→inf), promotion copy-back into champion+trainer (284-286), the trainer clone-from-champion (Training:1358-1359, inference→training — this one is PROVEN to work since the trainer probes 1708, so orders align today), candidate/tactical/lichess probes (CandidateProbe:55, RunAllAnalyses:250, TacticalProbeWatcher:234, LichessProbeWatcher:235), manual promote (ManualPromote:117), play-vs-user (PlayController:937). The safetensors *disk* path loads by NAME and is safe.
- **Status:** not corrupting today (the inference↔training clone works → mode orderings align for this arch), but every one of the ~12 cross-mode sites silently corrupts if a future arch/mode change reorders the variable list. Latent, systemic.
- **Fix direction:** key in-memory transfers by tensor **name** (build a name→tensor map on both sides), or at minimum assert name+shape per index (debug build) / add a name-ordered checksum so an order divergence fails LOUDLY instead of silently corrupting. Until then, treat every `exportWeights → loadWeights` pair as a latent corruption site.

### 2. ~~vBaseline forward pass runs WITH dropout~~ — FIXED 2026-08-11
- **Was:** `valueBaselineExecutable` compiles targeting `valueOutputFP32`, downstream of the residual-branch dropout op in the training-mode graph. At rate>0 the baseline v(s) was computed through the dropout-masked tower → the advantage `(z − vBaseline)` became a function of that step's random draw.
- **The suggested fix did not work.** `dropout_rate` was a graph **VARIABLE**, so it cannot be fed per-executable; and zeroing it around the baseline races the training step, because `internalComputeValueBaseline` deliberately commits WITHOUT waiting so its GPU work overlaps the training-step encode (GPU_UTILIZATION_PLAN Phase 3).
- **Actual fix:** `dropout_rate` is now a **placeholder fed per execution** (`dropoutRateFeedPlaceholder`). The training step binds a live-rate buffer; every other consumer binds a preallocated zero. Because `batchInputEntry.feeds` is shared, that one change made the value baseline, BN warmup, and batched inference all dropout-free at once. The old variable + assign-op setter (`dropoutRateLoadPlaceholder` / `dropoutRateAssignOp` / load ND array / load tensor data) is gone, and `ChessTrainer.dropoutRate` is now a buffer write instead of a `graph.run`.
- **Bonus, previously unlisted:** the diagnostics `evaluate` path on a training-mode network (acknowledged at ChessTrainer.swift:4863 as polluted "at a nonzero channel-dropout rate, by live dropout") is fixed by the same change — `inferenceFeeds` binds zero.
- **Regression test:** `DropoutGraphWiringTests.testValueBaselineIsDropoutFree` — asserts v(s) is identical at rate 0 and rate 0.5. Verified failing before the fix (all 8 positions differed) and passing after, unmodified. `testDropoutScaffoldingIsTrainingGraphOnly` was updated to assert the new mechanism (same invariant: scaffolding on training graphs only, never inference) — done with the user's express permission.

### 3. ~~Corpus + UCI training ignore the dropout setting~~ — FIXED 2026-08-11
- **Was:** only self-play applied `dropout_rate`. Root cause was one level deeper than described: `ReplayParams` — the Sendable snapshot both CLI runners take — **had no `dropoutRate` field at all**, so the value never even reached them. (Also: the constructor takes 15 args, not 13.)
- **Fix:** added `dropoutRate` to `ReplayParams`, populated it from `TrainingParameters` at both construction sites, and applied `trainer.dropoutRate = Float(p.dropoutRate)` after trainer construction in `CorpusReplayRunner` and `TrainVsUciRunner` (it has no `init` argument — it is a property setter that pushes into the graph).
- **Logging:** `dropout=` added to `[REPLAY-HPARAMS]`, and a `[VS-UCI-HPARAMS]` line was added — that path previously logged **no** hyperparameters at all, so a finished run left no record of what it trained under.
- **Still open (deliberately):** `ArchSweepCLI:82` and `SweepCLI:41` construct trainers without dropout too. They are sweep harnesses with their own parameter semantics; not touched.

### 4. CLI `--parameters` leaks into UserDefaults
- `TrainingParameters.apply()` → `applyOne()` assigns each property, and every property has `didSet { Self.persist(...) }` (TrainingParameters.swift:906+). So a `--parameters foo.json` CLI run **permanently writes foo.json's values into UserDefaults**, contaminating the next GUI/app launch. CLI overrides should be transient per-run (snapshot + restore UserDefaults around the CLI apply, or apply without persisting).

### 5. `--parameters` loader only accepts NSNumber (latent string-param gap)
- `CliTrainingConfig.load` (CliTrainingConfig.swift) bridges only bool/int/double; a string-valued parameter would `throw wrongType`. No parameter is string-typed today, so it's latent — but adding one silently breaks `--parameters` for it. (Good news: unknown keys `throw unknownParameter` at apply time — typos are loud, not silent.)

### 6. ~~`--output` (results.json) is written ONLY by the self-play/GUI path~~ — FIXED 2026-08-11
- **Confirmed, but NOT as originally described.** `cliOutputURL` was parsed in `DrewsChessMachineApp.swift` and read only by `SessionController+Training.swift` — however `--replay-corpus … --output x.json` did not "silently produce nothing": the `--replay-corpus` / `--train-vs-uci` pre-flight parsers have a `default:` case that does `Darwin.exit(2)` with `unexpected argument '--output'`, so the run **failed at parse time**. Fixed together with #3, because a dropout sweep on the CLI paths is unmeasurable without it — which is precisely what `CliTrainingRecorder`'s `dropoutRate` field exists for.
- **Fix:** added `outputURL` to `CorpusReplayConfig` / `TrainVsUciConfig`, and both runners now build a `CliTrainingRecorder` when a destination is given, append a stats line on the same cadence as their `[REPLAY]` / `[VS-UCI]` log lines, and write the JSON after the final model save.
- **Gotcha:** the `--replay-corpus` / `--train-vs-uci` pre-flights are **static** handlers that never reach the app instance, so each parses `--output` from `rawArgs` itself rather than reading `self.cliOutputURL`.
- **New API:** `CliTrainingRecorder.StatsLine` has 92 fields and no explicit init, most of them self-play-shaped. Added a dedicated initializer **in an extension** (a body init would suppress the memberwise init the self-play path depends on) for runs with no self-play loop and no arena. Its zeros/empty strings are the honest value for "this run type does not have that" — a corpus run plays no self-play games, runs no ratio controller, tallies no outcomes, has no champion — and every field such a run genuinely has is a required argument, so none can be silently forgotten at a call site.
- **Known imprecision:** `TerminationReason` has no case for corpus exhaustion or epoch limit, so a clean corpus exit reports `step_limit_reached`. Adding a case would change the results.json schema for the self-play path too, so it was left alone. (The vs-UCI path DOES distinguish its two clean exits — it tracks the actual cause rather than inferring it from which limits were configured.)
- **Write failures are logged, not thrown**, matching the self-play path: the trainer model is already saved by then, so a bad `--output` path or a full volume must not turn a completed multi-hour run into a nonzero exit.

## Audit findings (context for the above)

- **CLI param honoring (self-play `--train`):** `--parameters` is a generic id→value map applied at launch (DrewsChessMachineApp.swift:1064) via `apply()` → per-id `applyOne` switch (validate→decode→assign). Coverage is complete for numeric params; unknown keys throw. Issues = #4 (leak) and #5 (string gap).
- **Settings export:** `--show-default-parameters` emits **62** keys and iterates `allKeys`/`definition` (complete, macro-driven). Round-trip (`--create-parameters-file` → edit → `--parameters`) should be faithful for numeric params modulo #4/#5. *(Not yet empirically round-tripped — TODO if desired.)*
- **results.json contents (when written):** root = totalTrainingSeconds, trainingElapsedSeconds, terminationReason, sessionID, trainingSteps, positionsTrained, arenaResults[], stats[], candidateTests[], recordingCorpusID. `Arena` entries are rich (W/D/L by side, elo±CI, promoted/kind/promotedID, candidate/champion/trainer IDs, learningRate, promoteThreshold). **Not obviously captured:** the full hyperparameter set (only lr + promoteThreshold ride along per-arena). Consider adding a top-level params/config block for reproducibility. See #6 for the path-coverage gap.

## Verified OK (checked during the audit, no bug)
- **Constructor applies all 13 args:** `ChessTrainer.init` assigns lr/entropy/drawPenalty/wd/gradClip/policyW/valueW/illegalMass/smoothing×2/momentum/complementCE/sqrtBatchLR (init:16-28), and corpus training demonstrably works — so corpus/vs-uci DO honor their non-dropout params. The self-play setters (SessionController:930-948) are the live-reconcile path. Only `dropout_rate` has no init arg → that's the sole gap (#3).
- **Dropout applied at startup:** `[PARAM] dropoutRate applied to training graph: …` fires at launch — no self-play "dropout unset until first reconcile" window.
- **BN running-stat calibration:** only runs for `.randomWeights` inits (ChessMPSNetwork:98); loaded-weight nets use their own stored stats on all paths — consistent, no inconsistency.
- **vBaseline / main-step dropout masks:** the baseline pass doesn't advance the RNG state, so baseline and the training step use the SAME mask for a given step (consistent) — but the baseline still applies dropout at all, which is #2.
- **Unknown `--parameters` keys throw** (`applyOne` default = `unknownParameter`) — typos are loud, not silent.
