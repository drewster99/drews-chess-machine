## Analysis (analyzer, full)

G8 analysis (corpus replay exact resume): 4 of 5 items are REAL as reported, and persist#2 is PARTLY real.
Summary: The most serious one is cli#1. A --resume-exact with the default epoch budget, from a checkpoint saved in epoch >=1, quietly does nothing. When the checkpoint sits partway into the epoch it also writes a save whose corpus position is behind its parent's, so a later resume trains those games a second time, and nothing in the log says so. cli#2 cannot fail with default settings, but when it does, the [RESUME] verdict still says EXACT; one cheap check on the rebuilt buffer would catch it along with other underfills. cli#6 and persist#2 break the no-silent-defaults and surface-errors rules. cli#10 is cosmetic naming.
(Disclosure: early on I ran one read-only `ls Models | grep -c replay-latest-replay` under ~/Library/Application Support/DrewsChessMachine. It returned 0. Nothing was modified, and I did not touch that folder again.)

1. cli#1 — REAL. Severity HIGH, effort S–M.
 Evidence (file is CLI/CorpusReplayRunner.swift):
 - :1608: `epochLimit = config.epochs ?? (stepLimit == nil ? 1 : nil)`.
 - The resume sets `reconstructStartEpoch = startEpoch-1` (:1296) and `epochsCompleted = reconstructStartEpoch` (:1623).
 - The refeed (:1721-1726) calls the same `nextGame()`, which on the wrap does `epochsCompleted += 1 ... if let el = epochLimit, epochsCompleted >= el { return nil }` (:1640-1644).
 - With the default el=1 and startEpoch >=1, the wrap inside the refeed returns nil. The refeed then sets `corpusExhausted = true; break` and still logs "buffer reconstructed" (:1728). The main loop hits `if corpusExhausted && epochLimit != nil { break }` (:1787) at step 0.
 - The final save (:1933-1941) takes resumePoint() = (0, 0, startEpoch), because the wrap already reset `nextGameWithinEpoch = 0`. When the parent had until>0, this save is behind the parent's (until, startEpoch). A later resume from it re-trains games [0, until) of that epoch. The new segment is written with the EXACT verdict and steps=0.
 When it happens: until < gamesBack = ceil(1.5·cap/avgPly). That is about 19k games at the default 1M capacity, and it includes the normalized end-of-epoch save (0, N) that every default single-pass run finishes on.
 Also inconsistent today: a resume in epoch >=1 that does not cross the wrap ignores the spent budget and trains to the end of the epoch.
 It was never caught because ResumeEquivalenceTests.config (:201-205) and scripts/resume_equivalence.sh (:50-52) always pass a step limit, which makes epochLimit nil.
 Stale comments:
 - :1275-1283 ("Cross-epoch reconstruction isn't supported yet … Fail loud") describes behavior that the C1 #6 code right below it replaced.
 - :1712-1717 ("refeed stays within one epoch … no wrap fires mid-reconstruction") is false.
 - :1638 and :1689 ("resume bounds this same file enforces on read") are false: the read clamps silently (`until = max(0, min(rm.nextGameIndex, total))`, `startEpoch = max(0, rm.epoch)`, :1269/:1271).
 Fix (recommended):
 (a) Define `stepLimit` / `epochLimit` once, above the resume block, and use that definition at :1608.
 (b) In the resume block, before the network build: `if let el = epochLimit, startEpoch >= el { throw CorpusReplayError.exactResumeEpochBudgetSpent(savedEpoch: startEpoch, epochLimit: el) }`. Message: "the checkpoint has completed N pass(es); --epochs is M (default 1); pass --epochs > N or --training-step-limit". Once a spent budget is refused up front, the refeed can never reach the budget, because its epochsCompleted is at most startEpoch < el.
 (c) Make the refeed fail instead of falling through: `guard let g = nextGame() else { throw exactResumeShardFailure ?? CorpusReplayError.exactResumeRefeedEndedEarly(reachedEpoch:, reachedGame:, targetEpoch:, targetGame:) }`. It must never set corpusExhausted.
 (d) Replace the two silent clamps with validation: `guard rm.epoch >= 0, (0..<totalCorpusGames).contains(rm.nextGameIndex) else throw`. That makes the :1638/:1689 comments true.
 (e) Rewrite the stale comments.
 (f) Add the buffer-fill check from item 2.
 (g) Update the `--epochs` help in DrewsChessMachineApp.swift:559 to say the budget is counted from the lineage start, so a resume needs `--epochs` greater than the saved epoch.
 Owner decision: (b) changes current behavior. A non-crossing resume in epoch >=1 with no budget flags used to finish the current epoch and would now be refused. The alternative that keeps that behavior is to exempt the refeed from the budget (a `refeeding` flag in nextGame) and still do (c). That still overshoots `--epochs` on resume, though. I recommend (b).
 Tests (new; they need a config helper that takes `epochs:`. Adding a sibling helper in ResumeEquivalenceTests is additive, but it is an edit to a test file, so flag it for the owner):
 - `testAResumeWhoseEpochBudgetIsSpentIsRefused`: first = a step-limit run that ends early in epoch 1 (as in the existing wrap test), then a resume with stepLimit nil and epochs nil. Assert it throws `.exactResumeEpochBudgetSpent` and that no out-model file exists. Before the fix it returns steps==0 and writes a file with the earlier position.
 - `testACrossEpochResumeUnderAnEpochBudgetEndsWhereTheUninterruptedRunEnds`: straight run with epochs:2 compared against first (step limit n) plus a resume with epochs:2. This is coverage for a path never tested before and passes before and after.
 Risks: existing tests use step limits, so they are unaffected. All new throws must be throws, not Darwin.exit (item 4).

2. cli#2 — REAL, but narrower than reported. Severity LOW–MED, effort S for detection, M–L for the full fix.
 Evidence:
 - :1301 `reconstructStart = max(0, until - gamesBack)` ignores where the parent run started.
 - LineageRecord.CorpusPosition (:264-284) has no feed start.
 - `rm.populatedPlies` is only logged (:1306) and never compared.
 - The verdict comes from resumeGaps, which contains nothing about this (:1317-1320). So it logs EXACT.
 It is wrong only when the parent's ring was not full at the save (fewer plies fed since --start-game-index/--start-shard than the capacity). The ring keeps the last cap plies of a sequential stream, so a refeed that starts earlier but ends at the same point gives identical logical contents once the parent's ring was full. Sampling maps logical (oldest-first) indexes, so the physical write head does not matter (ReplayBuffer.physicalSlot :737-743). With default capacity 1M and K≈batch/ratio, the ring is full after about 117 steps, so the first autosave at step 1000 is already safe. Exposure is early aborts, small step limits, or large capacities.
 Fix:
 (a) Recommended, no format change. After the refeed: `guard buffer.count == rm.populatedPlies else throw CorpusReplayError.exactResumeBufferMismatch(saved:, rebuilt:, savedCapacity:, capacity:)`. Why this is enough: the parent's stream is a suffix of the refeed's, so equal counts mean equal contents. The same check also catches an underfill when the 1.5x window falls short over locally short games (today that is silently inexact), and a changed replay_buffer_capacity. As far as I can see corpus replay never compares the parameter snapshot, only feedPerStep, so a capacity change currently passes as EXACT; that is worth a separate look. For legacy files with no populated count (item 3), log a "[RESUME] buffer fill not checked: …" line instead.
 (b) Full fix, owner call: add `feed_start_epoch` / `feed_start_game_index` to CorpusPosition. A fresh run or branch sets them to its first fed game; an exact resume inherits them. Clamp reconstructStart, in epoch-linear terms, to that position. This changes the format and needs an answer for v7 files that lack the fields (backward-compat code needs owner approval).
 Test: `testAResumeOfARunStartedMidCorpusIsNotReportedExact`. Run with startGameIndex G>0 and a small n so populated < capacity, then resume-exact. Assert it throws `.exactResumeBufferMismatch`; with (b), assert it equals the straight G-start run of n+m steps. Before the fix it runs with EXACT and no error. It needs a helper that takes `startGameIndex:`, with the same test-edit caveat as item 1.

3. persist#2 — PARTLY. Severity LOW, effort S.
 Evidence: SafetensorsModelIO.swift:485-507 uses `try? FileHandle`, `try? read`, `try? JSONSerialization` and `?? 0` for replay_next_game_index, replay_epoch, replay_populated_plies and replay_capacity, plus `?? ""` for the path. A malformed value such as "abc" also becomes 0.
 The IO-misreport part is mostly moot. replayResumePoint (:455-456) calls readParentFile first, which already reads the header through the throwing ModelFileCatalog.headerMetadata, so the try? can only fire on a race between the two reads.
 The `?? 0` part is real but needs a hand-edited or corrupt pre-v7 file; the old writer wrote all the keys (DETERMINISM plan :846). The effect would be a silent resume from game 0, epoch 0.
 Fix: replace it with `legacyResumeMetadata(fromMetadata md: [String:String], file:) throws -> ReplayResumeMetadata?`, parsing the dictionary that has already been read (add a `readParentFile(fromMetadata:source:)` overload so the header is read once).
 - No replay_corpus_id -> nil, which gives the existing `.noLegacyResumeMetadata`.

 - populated_plies and capacity become `Int?` (absent -> nil; malformed -> throw).
 - The path becomes `String?`.
 Keep these optional: the existing test LineageRecordTests.testReplayResumePointOfALegacyFileUsesItsReplayKeys (:390-403) writes only id, next and epoch, and it must keep passing unmodified.
 Tests (new, in LineageRecordTests):

5. cli#10 — REAL. Severity LOW, effort S.
 Evidence:

 - EnumeratedCheckpointNaming.fileName (:415-419) uses `contains` plus `replacingOccurrences`, which replaces every marker: segment 1 writes X-replay-seg1-step1000-replay-seg1-step1000. A mid-stem marker ("a-replay-latest-b") gives "a-replay-step7-b".
 - The parser (:428-441) and the any-stem parser (:481-485) agree with the writer, so nothing collides; the names are just malformed.

Make the any-stem parser's candidate reconstruction trailing-only as well. Mirror the change in replay.py (`om[:-len(m)]` when `om.endswith(m)`).
 I checked the existing tests by hand: TrainerOutputFileGuardTests testEnumeratedNameParsingRoundTripsAStemThatRepeatsTheMarker (round-trip only) and testAnyStemParserRecognizesEveryEnumeratedShape (including the "a-replay-latest-replay-latest" and "a-replay-latest-b" stems under both tags) still pass under suffix-only naming, as does SegmentIndexedCheckpointNamingTests :63.
 Whether to stop the compounding default out-model name is an owner call.
 Test (new): `SegmentIndexedCheckpointNamingTests.testARepeatedRollingMarkerReplacesOnlyTheTrailingOne`. Assert naming("a-replay-latest-replay-latest","replay",segment:1).fileName(step:1000) == "a-replay-latest-replay-seg1-step1000.safetensors", and that "a-replay-latest-b" gives "a-replay-latest-b-step7.safetensors".
