1. tools#2 + #3 — dashboard tick and probe_backfill
 #2 REAL. tick.py:29 `replay.track(run)` and :32 `replay.probe_backfill(run)` sit outside any try.
  - track() calls probe() at replay.py:799, which raises ProbeFailure on timeout, a non-zero exit, an error event or a bad summary (:155-168).
  - probe_backfill writes the rows it filled, then raises ProbeFailure whenever any file failed (:923-929).
  - So one checkpoint that keeps failing (or a stale BIN that can't read a newer format) makes every tick raise at step 1 or 1b. The log-backfill rows (step 2), render (step 3) and the table (step 4) never run, so the dashboard freezes.
  - Each tick also re-probes every failing file, at up to PROBE_TIMEOUT_SECONDS each, while cron_tick.sh holds /tmp/dcm_cron_tick.lock. cron_tick.sh:25-120 only raises an alarm after 1800 s.
  - qeu8_tick.py:45-46 has the same pattern (legacy; qeu8 stopped 2026-08-06).
 #3 REAL. In _backfill_one (replay.py:823-871), only ProbeFailure is caught (:836).
  - These run after a successful probe and can raise: internals_cells (:839 → ValueError for mixed ReZero, KeyError for a missing tensor, ArchitectureError), st.elapsed_and_clock, _metrics_at and lineage_cells (:843 → LineageError on a segment, step or games_base contradiction).
  - Any of these escapes probe_backfill before write_csv (:922-924), so the probes already done in that pass are lost.
  - The same file raises again next pass, so files after it in sort order are never filed.
  - Legacy `-frozen` scan (:913-920) passes no segment, so seg_for guesses (its own ⚠ doc at :451). A `-frozen` copy that freeze() (:783-786) made of a v7 rolling out-model carries a lineage record, so a wrong guess on a forked/boundary segment raises in lineage_cells. This is plausible but I did not reproduce it.
 FIX:
  (a) _backfill_one:
   - Compute the non-probe parts first (internals_cells, elapsed_and_clock, _metrics_at, lineage_cells), so a contradiction doesn't waste a GPU probe.
   - Wrap them in `except (ValueError, KeyError, OSError) as error: failures.append((name, f"cannot file: {error}")); print(...stderr); return 0`. LineageError and ArchitectureError are ValueError subclasses.
   - Nothing is swallowed: probe_backfill still raises at the end, after write_csv. Reword that final message to "could not be probed or filed" and include each reason, not only the names.
   - Optional: for the legacy scan, when checkpoint_facts(path) has a segment_id that matches a registry segment, pass that segment index instead of guessing.
  (b) tick.py:
   - Move the body into `def main(arg) -> int` with an `if __name__ == "__main__": sys.exit(main(...))` guard.
   - Run track and probe_backfill each in `try/except replay.ProbeFailure as e: failures.append(...)`.
   - Always do log-backfill, render and the table, then print the failures to stderr and return 1 if there were any. cron_tick.sh already logs the non-zero status.
   - Do NOT catch LineageError or other contradictions in tick: they are registry/data errors that need the owner, so they should still stop the tick loudly.
   - Apply the same change to qeu8_tick.py if it is still used.
 TESTS (tests/test_replay_probe.py, which already has a stub binary via DCM_BIN and DCM_DASH_ROOT):
  - test_backfill_saves_probed_rows_when_a_later_file_cannot_be_filed: two enumerated checkpoints; replay.internals_cells patched to raise ValueError on the second. Assert probe_backfill raises ProbeFailure AND the CSV holds the first row. Fails before the fix because no CSV gets written.
  - test_tick_renders_when_probing_fails: patch replay.track and replay.probe_backfill to raise ProbeFailure and replay.render to a recorder. Assert render was called and main() returns 1. Fails before the fix because the exception escapes.
 RISK: tick's exit status still flags the failure. The cost of re-probing every tick is unchanged; a per-file retry cap would be a separate decision. Severity MEDIUM, effort S.

  - Keep dcm_lineage.MAX_HEADER_BYTES as a re-export only if a test reads it; grep first.

 RISK: scan_files catches (OSError, ValueError, struct.error), and both error types are ValueError subclasses, so it is unaffected. Severity LOW, effort S.
