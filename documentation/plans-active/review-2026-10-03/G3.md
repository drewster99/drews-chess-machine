## Analysis (analyzer, full)

G3 analysis (ui#4, ui#5, ui#6): all three are REAL. #4 is broader than reported, #5 includes a silent-discard bug, #6 only happens in a race.

SUMMARY
- #4: Save treats an untouched field as "keep the live value" only for the 27 rounded Double fields. Every Int field, the live-propagated fields, the autosave-minutes field and the arena interval are re-parsed against the declared range. Two things trigger it: (a) session-resumed values outside today's range, which `restoreFromSession` deliberately holds in memory; (b) values inside the declaration but above an app-side cap: self-play delay 3000 vs declared 10000, arena concurrency 1024 vs declared 4096. Also found: an untouched non-whole-minute autosave interval is silently rewritten on any Save (90 s becomes 120 s).
- #5: the hardcoded ranges are confirmed. The worst effect is silent loss: a replay-ratio typed outside 0.1...5 (but inside the declared 0.01...100) is never applied, yet Save closes the popover. A train-step delay of 3001–10000 is silently clamped to 3000 while Save reports success.
- #6: confirmed. The menu item is disabled when busy or networkReady, so the refusal only fires if state changes while the sheet is open. Effect: a false `[BUTTON] Build Network … init_seed=` log line, a stale `buildArchitecture`, and the user's custom design is lost because the sheet closes before the refusal.

1. ui#4 — untouched out-of-range fields block popover Save. REAL (wider than reported). Severity MEDIUM-LOW. Effort S–M.

Evidence
- `TrainingSettingsPopoverModel.swift:317-328`: `roundedTextFields` lists only Double fields. `editedValue` (:338-347) returns the live value only for those.
- Int fields always run `K.parsedInDeclaredRange(text)` on the seeded text:
  - warmup :785, lrCyclePeriod :844, lrCycleCount :851, momentumCyclePeriod/Count :882/:889, decayHorizon :918, batch :1163
  - selfPlayConcurrency :1176 (plus `n <= maxSelfPlayWorkers`)
  - replayBufferCapacity :1298, minPositions :1310, maxPeriodicAutosavesKept :1411, klProbeInterval :1444
- Live-propagated fields are re-validated even when untouched: drawKeep :1241, selfPlayMaxPlies :1255, drawWatch threshold/streak :1270/:1281, maxPlies/targetLen/maxDraw :1337-1363, replayRatioTarget :1369, delays :1375 (`n <= selfPlayDelayMaxMs`) and :1382.
- The :1375 check runs even when auto-adjust is ON. In that state the delay rows are hidden (`TrainingSettingsPopover.swift:2261` shows `liveDelayRow` instead), so a stored self-play delay of 3001–10000 (legal per the declaration at `TrainingParameters.swift` SelfPlayDelayMs 0...10000) keeps Save from closing, with the red field hidden.
- Autosave interval :1394-1403. The seeded text is minutes rounded to nearest (:232-234). Save compares `abs(secs - p.periodicAutosaveIntervalSec) > 0.5`, so an untouched 90 s interval is written back as 120 s and logs a [PARAM] change on every Save.
- `ArenaSettingsPopoverModel.swift`:
  - games :189 and SPRT min/max games :361-362 are re-parsed.
  - concurrency :199 adds `c <= maxConcurrency`, where maxConcurrency = `UpperContentView.absoluteMaxArenaConcurrency = 1024` (`UpperContentView.swift:313`, :582) against the declared 1...4096. A `parameters.json` value of `arena_concurrency: 2000` blocks arena Save indefinitely.
  - interval :209-214: `formatDurationSpec` (`UpperContentView.swift:3311`) truncates fractional seconds, so an untouched 900.5 is rewritten to 900.
- Out-of-range live values are real and intended: `TrainingParameters.restoreFromSession` (`TrainingParameters.swift:2224-2244`) admits them via `admittingSessionValueOutsideDeclaredRange`. Every Int key above is restored through it (`SessionController+Training.swift:110-229`, plus delays at :509/:519).

Fix
- In both models, generalize the "untouched means keep the live value" rule to every seeded text field.
  - Rename `roundedTextFields` to `seededTextFields` and list every String field `seedFromParams` writes. Update its doc comment.
  - Add `private func isUntouched(_ field:) -> Bool { seededText[field].map { $0 == self[keyPath: field] } ?? false }`.
  - Add an Int twin of `editedValue`:
    `editedValue<K>(_:_:current: Int) -> Int? where K.Value == Int { isUntouched(field) ? current : K.parsedInDeclaredRange(self[keyPath: field]) }`.
- Commit-on-Save Int fields use it. Apply the extra caps (`<= maxSelfPlayWorkers`, `<= maxConcurrency`, `<= selfPlayDelayMaxMs`) only to an edited value.
- Validate-only live fields: `if isUntouched(\.x) { xError = false } else { existing validation }`.
- Autosave minutes and arena interval: if untouched, skip the write entirely. This also fixes the 90 s → 120 s and 900.5 → 900 rewrites.
- Keep `seededText` in sync with the two non-seed writers that reflect live values:
  - `resyncLrWarmupText` (:305)
  - the `applyLiveReplayRatioAutoAdjust` Task (:618-622) that reseeds the delay texts.
  Without this, those fields count as edited. That is harmless today, since the values are in range, but inconsistent.
- Root cause of trigger (b) is two sources of truth for the caps. That fix belongs with #5.

Risks
- Text-equality means "edit then retype the same text" counts as untouched. That is fine, because the value is identical.
- Cross-field checks still use the live values: lr/momentum min ≤ max (:840, :878), peak ≥ trough (:914), follow pairs (:958-966), and `SPRTConfig`. An inverted pair restored from a session would still block Save. I'd leave that as is: it flags a genuinely inert schedule. It is an owner call.
- Existing tests:
  - `PopoverSaveKeepsUneditedValuesTests`, `TrainingSettingsCycleValidationTests`, `ArenaSettingsSPRTValidationTests` and `TrainerHyperparametersTests:271-282` all edit text before Save, so they are unaffected.
  - Noted for reference: `PopoverSaveKeepsUneditedValuesTests.makeTrainingModel` passes `maxSelfPlayWorkers: 8` against a default concurrency of 180, so its Save never closes. Those tests assert only values, so they still pass.

Regression tests (new file `PopoverUntouchedOutOfRangeTests.swift`, same setUp/tearDown as `PopoverSaveKeepsUneditedValuesTests`; build the model with the `UpperContentView` statics)
- `testTrainingSaveAcceptsUntouchedSessionValuesOutsideTheDeclaredRange`
  - Setup:
    - `p.restoreFromSession(KLProbeInterval.self, 20_000, into: \.klProbeInterval)` (declared 0...10000)
    - `LRWarmupSteps` 200_000 (declared 0...100000)
    - `MaxPliesFromAnyOneGame` 500 (declared 1...400)
    - `DrawWatchPDrawThreshold` 0.3 (declared 0.5...1.0)
    - new model; `isPresented = true`; `save()`
  - Asserts: none of the four error flags set, `isPresented == false`, all four values unchanged.
  - Before the fix the flags are true and the popover stays open.
- `testTrainingSaveKeepsAnUntouchedNonWholeMinuteAutosaveInterval`: `p.periodicAutosaveIntervalSec = 90`, then `save()`. Asserts the value is still 90. Before the fix it is 120.
- `testArenaSaveAcceptsAnUntouchedIntervalOutsideTheDeclaredRange`: `restoreFromSession(ArenaAutoIntervalSec.self, 30, …)` (declared 60...86400). Asserts no `intervalError`, the popover closes, the value is 30.
- `testArenaSaveKeepsAnUntouchedFractionalInterval`: 900.5 stays 900.5.

2. ui#5 — hardcoded Stepper ranges disagree with the declarations. REAL, plus two silent-loss bugs. Severity MEDIUM-LOW. Effort S.

Evidence (`TrainingSettingsPopover.swift`)
- :1206 batch Stepper `32...32_768`; declared `TrainingBatchSize` 32...65536.
- :1571 concurrency Stepper `1...256`; declared 1...8192, which equals `absoluteMaxSelfPlayWorkers` (`UpperContentView.swift:470`). The status-bar `ConcurrencyStepperRow` (`SelfPlayStatsColumn.swift:53-57`) correctly uses `1...maxWorkers`.
- Replay ratio:
  - :2247 Stepper `0.1...5.0` and :2252-2255 text `.onChange` guard `v >= 0.1, v <= 5.0`; declared `ReplayRatioTarget` 0.01...100.
  - Save (:1369) only validates against the declaration and never writes this field.
  - So typing 0.05 or 8 is never pushed live, Save succeeds and closes, nothing is applied and no [PARAM] line is logged. Silent discard.
- Self-play delay:
  - :2281 Stepper `0...3000` and :2286-2289 guard `v <= 3000` are literals.
  - The real cap is `UpperContentView.selfPlayDelayMaxMs = 3000` (:494); declared `SelfPlayDelayMs` is 0...10000.
- Train-step delay:
  - :2302 Stepper uses `TrainingStepDelayMs.declaredClosedRange` (0...10000) and :2309-2313 pushes any declared-range value.
  - `applyLiveTrainingStepDelay` (model :597-604) clamps to `stepDelayMaxMs = 3000` (`UpperContentView.swift:484`).
  - Save (:1382) checks only the declaration. Typing 5000 sets the parameter to 3000, the text still reads 5000, Save closes. Silent clamp. This is inconsistent with self-play delay, which does check its cap (:1376).
- `ReplayRatioController` (:247-248, :771, :779) and `validDelayRungsMs` (`UpperContentView.swift:500`) take their caps from the same 3000 statics, so the delays have two upper bounds: 3000 enforced and 10000 declared.
- I could not verify read-only how a SwiftUI Stepper behaves when its bound value starts outside `in:`. For the live-bound steppers (ratio, delays), any press writes and live-pushes immediately, so a pre-existing out-of-range value can be changed by a single click.

Fix
- Replace the literals with the declarations, via the model so view and Save share one source:
  - batch: `in: TrainingBatchSize.declaredClosedRange`
  - concurrency: `in: SelfPlayConcurrency.declaredClosedRange.clamped(to: 1...maxSelfPlayWorkers)`
  - replay ratio: Stepper `in: ReplayRatioTarget.declaredClosedRange`; `.onChange` becomes `if let v = ReplayRatioTarget.parsedInDeclaredRange(newValue) { onLive…(v) }`
- Delays: add model-exposed ranges and use each for Stepper, `.onChange` guard and Save:
  - `selfPlayDelayRange = SelfPlayDelayMs.declaredClosedRange.clamped(to: 0...selfPlayDelayMaxMs)`
  - `trainingStepDelayRange` likewise
  - Save :1382 gains the cap check, so 5000 is flagged instead of silently clamped.
- Make Save commit the edited live fields as well (`applyLiveReplayRatioTarget(parsed)` etc. when edited and valid). The `.onChange` push then becomes a preview only, and no typed value can be dropped.
- Owner decision (single source of truth): either narrow the `SelfPlayDelayMs` / `TrainingStepDelayMs` declarations to 0...3000 and derive `stepDelayMaxMs` / `selfPlayDelayMaxMs` from `declaredClosedRange.upperBound`, or raise the caps to 10000. The same question applies to `ArenaConcurrency` (declared 4096, app cap 1024).
  - Narrowing makes stored UserDefaults or `parameters.json` values above the cap invalid. At launch that surfaces in the invalid-stored-settings sheet; on session resume the value is admitted with a `[RESUME-PARAM] WARNING`.
  - The `parameters.json` / `--show-default-parameters` output changes.
  - My recommendation is to narrow, since the 3000 / 1024 caps are the enforced behavior.

Risks
- Batch Stepper going up to 65536 lets someone step into a GPU-memory-heavy batch. It is the declared range, so it is acceptable, but owner-visible.
- `TrainerHyperparametersTests:271` builds the model with 10_000 caps, so a model-derived range keeps those tests valid.

Regression tests (new file `TrainingPopoverLiveFieldRangeTests.swift`)
- `testTypedReplayRatioInsideTheDeclarationButOutsideTheOldStepperRangeIsApplied`: set `replayRatioTargetText = "0.05"`, then `save()`. Asserts `p.replayRatioTarget == 0.05`. Before the fix it is unchanged.
- `testTrainStepDelayAboveTheEngineCapIsRejectedNotClamped`:
  - Setup: model with `stepDelayMaxMs: 3000`, auto-adjust off, `isPresented = true`; `replayTrainingStepDelayText = "5000"`; `save()`.
  - Asserts `replayTrainingStepDelayError == true` and `isPresented == true`.
  - Before the fix there is no error and the popover closes.
- `testStepperRangesMatchTheDeclarations`: asserts the model's exposed ranges equal declaration ∩ cap. This one is compile-level only before the fix.

3. ui#6 — Build sheet writes `buildArchitecture`/`buildInitSeed` and logs the seed before the refusal. REAL, race-only. Severity LOW. Effort S.

Evidence
- `UpperContentView.swift:1236-1244`: `onBuild` sets `session.buildArchitecture` and `session.buildInitSeed`, closes the sheet, then calls `session.buildNetwork()`.
- `SessionController.swift:1073-1092`:
  - resolves the seed, drawing from the system when none was entered
  - clears `buildInitSeed`
  - logs `[BUTTON] Build Network (<arch>) init_seed=N (drawn|entered)`
  - only then checks `isBusyProvider()` / `networkReady` and refuses.
- The menu item is `.disabled(commandHub.isBusy || commandHub.networkReady)` (`DrewsChessMachineApp.swift:844-845`), so a refusal needs a state change while the sheet is open. Example: the auto-resume countdown firing while its sheet is hidden (ui#2).
- On a refusal the log shows a build that never ran, with a seed that was never used, and `buildArchitecture` stays at the refused design.
- Reachability of the stale value: `ensureChampionBuilt(arch:)`'s nil default (:1151) is never used, since both callers (`SessionController+Checkpoint.swift:707`, :897) pass an arch. The `--train` auto-build (`UpperContentView.swift:2097`) cannot follow a sheet build. Practical impact is the false log line plus the lost custom design: the sheet is already dismissed when the refusal alert shows.
- `commandHub.buildNetwork` (`UpperContentView.swift:2334`, `AppCommandHub.swift:82`) is assigned but never called (dead).

Fix
- Replace the set-then-call pattern with parameters, removing the stored state:
  `func buildNetwork(architecture: NetworkArchitecture, enteredInitSeed: UInt64?)`
  - The busy and networkReady guards run first and return before any seed draw or log.
  - Then resolve the seed and log `[BUTTON] Build Network …`.
- Delete `buildArchitecture` and `buildInitSeed`. Make `ensureChampionBuilt(arch:)` non-optional; both callers already pass one.
- Callers:
  - sheet: `session.buildNetwork(architecture: request.architecture, enteredInitSeed: request.enteredInitSeed)`
  - `--train` (:2097): `session.buildNetwork(architecture: .newModelDefault, enteredInitSeed: nil)`
  - dead `commandHub.buildNetwork`: delete it, or update it the same way.
- Optional, to keep the design on a race: pass `isBusy || networkReady` (with `busyReasonMessage()`) into `BuildNewModelView` and disable its Build button with the reason. Keep the guard in `buildNetwork`. Don't move the refusal alert ahead of the sheet dismissal: on macOS an alert on the presenting view does not show while the sheet is up.
- Minimal alternative if the API change is unwanted: just move the two guards to the top of `buildNetwork()`, and set the properties inside it after the guards. Still two-step state, so I don't recommend it.

Risks
- The `--train` auto-build path has to pass `.newModelDefault` explicitly. That is identical to today's behavior, since nothing else sets `buildArchitecture` there.
- No persistence formats or tests reference these properties (grep: only `SessionController.swift` and `UpperContentView.swift`).

Regression test (new file `BuildNetworkRefusalTests.swift`, `@MainActor`; `SessionController()` is test-constructible, see `SessionSaveReplayBufferTests:29`)
- `testRefusedBuildHasNoSideEffects`:
  - Setup: `isBusyProvider = { true }`, `busyReasonProvider = { "busy" }`, capture `onRefuseMenuAction`, count `onDropTrainer` calls.
  - Call: `buildNetwork(architecture: <non-default preset>, enteredInitSeed: 7)`.
  - Asserts: one refusal, `isBuilding == false`, `network == nil`, `onDropTrainer` not called.
- Same test with `networkReady` true instead of busy.
- Honest caveat: before the fix this fails only at compile level (new signature). The false log line isn't assertable because `SessionLogger` has no capture hook. Adding one is out of scope; the test pins the "no side effects" contract instead.
