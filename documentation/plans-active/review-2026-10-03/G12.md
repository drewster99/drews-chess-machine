## 1. lichess#1 — Session ending without .finished is never handed to filing

Verdict: REAL. Severity MEDIUM, effort S–M.

Evidence:
- GameSession.run breaks on a game-stream 404 without a finish (GameSession:262-266). The manager then emits .gameSessionEnded (SessionManager:806-812).
- The controller's handler (Controller:2976-2984) enqueues nothing.
- gameFinished, and with it the post-game-chat → enqueue path, is driven only by the journal's .finished entry (Journal:192-213, Controller:2890-2903).
- The reconciler drops games that have a live owner (Reconciler:209-211, 317-320). Its doc says "that owner enqueues it again when it is done" (Reconciler:49-52), which is false for this path.
- Launch recovery (Controller:2582-2591) runs once, 30 s after go-online. A session that 404s after that leaves its journal in InProgress/ until the next go-online, which can be days away.
- The unauthorized and stopMoving exits (GameSession:258, :299, :472, :862, :874) call failRuntime, which tears down the whole runtime; that is consistent with the rest of the design. So the gap is only the in-runtime 404 exit (mostly aborted games that Lichess deleted).

Fix:
- Manager (SessionManager:782-785):
  `sessionTasks[gameID] = Task { [weak self] in await session.run(); let finished = await session.isFinished; await self?.sessionEnded(gameID: gameID, finished: finished) }`
- Change the event to `.gameSessionEnded(gameID: String, finished: Bool)`. GameSession.isFinished already exists (GameSession:173).
- Controller handler:
  `if !finished, let reconciler = runtime?.reconciler { protocolLog.record(.game, "session ended without a finish; handed to filing", gameID: gameID); Task { await reconciler.enqueue(gameID: gameID) } }`
- Correct the reconciler's "one decider" doc to say a session-without-finish owner enqueues via the controller.
- Using the session's own flag, rather than gamesAwaitingPostGameChat membership, avoids depending on the order of the .gameFinished and .gameSessionEnded events.

Risks:
- A game that comes back (gameStart replay starts a new session) is dropped by the reconciler's owner check. That is correct.
- A 404'd aborted game ends in export 404 → handleMissingExport → retry window → quarantine alarm. That is the right outcome: the operator is told instead of getting silence.
- failRuntime paths: the generation check drops the old runtime's events, so nothing is enqueued after teardown.
- Existing tests use `if case .gameSessionEnded = event` (DrewsChessMachineTests/LichessBotSessionManagerTests.swift:288, 346), so they still compile with the extra associated value.

Regression test: testASessionEndingWithoutAFinishIsHandedToFiling, in a new file DrewsChessMachineTests/LichessBotSessionEndFilingTests.swift.
- Steps: go online, start game cbob, then make the fake close the game stream and answer reopens with 404. Give cbob a terminal export.
- Assert a record exists under Games/ within 10 s.
- Why it fails before the fix: recovery only runs at 30 s, so nothing files the game in 10 s.
- Needs a fake extension (a `goneGames` set plus `endGameStream(_:)`) in DrewsChessMachineTests/LichessBotResumeFakeLichess.swift. That is a test-support edit and needs owner OK; otherwise put a new fake in the new file.

## 2. lichess#2 — Quit skips filing of games awaiting post-game chat; next launch raises a false alarm

Verdict: PARTLY. The deferral is deliberate; the alarm and chip text are wrong. Severity MEDIUM, effort M.

Evidence:
- applicationShouldTerminate (Controller:1021-1029) stops at once when !hasGamesInPlay. goOffline instead drains awaiting games (Controller:953).
- Skipping filing on quit is documented design: Controller:823-829, and finishIfDrained (Controller:3159-3162) says "when quitting, stop at once (launch recovery files anything unfinished)".
- It also happens on every quit with games in play: the drain-for-quit stops right after the last finish, before its 5 s delayed enqueue (Controller:2894-2897).
- The defect: noteLeftoverJournalsAtLaunch (Controller:850-865) raises [ALARM] "The last run left N game(s) not filed … Any still live on Lichess is running on DCM's clock". The chip then says "N unfinished from last run" (UI/LichessBotStatusChip.swift:61-63) for games that finished cleanly. Normal quits produce this regularly.

Fix (recommended):
- In noteLeftoverJournalsAtLaunch, split the leftovers with store.journalFinishedStatus(gameID:) (RecordStore:147-155). The bot is offline here, so there is no live-append contention.
- Finished games: a session-log line plus a new `finishedGamesAwaitingFilingFromLastRun` list, no alarm. The chip says "N to file" or similar.
- Unfinished games: keep the alarm.
- A journal that can't be read: alarm naming the error ("can't tell whether it finished: …"), not a silent default.
- Keep quit fast. The alternative is making quit drain-and-file like goOffline, which can take up to filingTimeLimitSeconds (120) and hit export spacing; that is the owner's call.

Regression test: testAFinishedGameLeftByQuitIsNotAlarmedAtNextLaunch.
- Steps: controller A goes online, cbob finishes (opponentResigns), postGameChatFetchDelays set long so the game stays awaiting. Then abandonAndStop() and shutdown (same on-disk state a quit leaves). Controller B on the same directory runs noteLeftoverJournalsAtLaunch.
- Assert B.alarms is empty, B.leftoverGamesFromLastRun == [], and B.finishedGamesAwaitingFilingFromLastRun == ["cbob"].
- Why it fails before the fix: an alarm is raised.
- The existing LichessBotResumeTests:218-222 (live game cbob, not finished) is unaffected.

## 3. lichess#3 — Second session for the same game resets carryover

Verdict: REAL. Severity LOW, effort M.

Evidence:
- sessionOrigin removes the resumable entry (SessionManager:794), so any later session for the same game in this runtime gets .new → .newGame carryover (SessionManager:735-737).

Triggers:
- A transient 404 followed by a gameStart replay on event-stream reconnect: the greeting is resent at ply ≤1, and the takeback allowance, command-reply budget and resign/draw streaks reset.
- A gameStart replayed just as the game ends: the new session's gameFull is finished → finish() with farewellSent=false sends a duplicate goodbye (GameSession:1030-1032) and schedules duplicate post-game chat fetches.

The doc at SessionManager:788-792 ("a later session for the same game in this runtime resumes one this runtime already listed") is misleading.

Fix:
- Add `func carryoverSnapshot() -> LichessBotGameSessionCarryover` on GameSession (greeted, farewellSent, takebacksAccepted, commandBudget replies sent, readings).
- In sessionEnded, the manager stores it in `endedSessionCarryover[gameID]`, with the first start Date.
- sessionOrigin returns a new case `.restartedInThisRuntime(carryover:, firstStartedAt:)` when an entry is present.
- Update the switches in startSessionIfNeeded, Controller gameSessionStarted logging, and listStartedGame (it normally finds the existing or retained LiveGame; otherwise create one with an anomaly note).
- The oneGameMode `case .new = origin` check then correctly ignores restarts.
- Option: re-read the journal instead; rejected because the journal may already be filed (post-chat filing) → unknownHistory plus a spurious alarm.

Regression test: testASecondSessionForTheSameGameKeepsItsCarryover (LichessBotSessionManagerTests style).
- Steps: session 1 greets and accepts a takeback; its stream ends with 404; gameStart is replayed.
- Assert no second greeting POST and that the takeback allowance is still counted. Fails before the fix.

## 6. lichess#6 — Quit while offline skips shutdown

Verdict: REAL. Severity LOW-MEDIUM, effort S.

Evidence:
- `guard let runtime else { return .terminateNow }` (Controller:1022) skips shutdown().
- shutdown waits for in-flight challenge sends and withdrawals (Controller:1130-1166) and flushes the journal and file queues. Teardown starts the withdrawals (Controller:2663-2666).
- So Go Offline (or a failRuntime Error) followed by an immediate Cmd-Q kills the withdrawals. The challenge can stand and be accepted into a game nobody plays, which is the hazard the shutdown doc names.
- Queued protocol-log, player-notes and outcome-log writes can also be lost.

Fix:
`guard let runtime else { quitReplyPending = true; completeQuitIfPending(quit: true); return .terminateLater }`
- completeQuitIfPending awaits shutdown, then replies. shutdown is idempotent and cheap when idle.

Risks:
- Every app quit now goes through terminateLater, adding only milliseconds when idle.
- AppDelegate checks for the CLI flush first, so that path is unchanged.

Testing needs a seam, because NSApp.reply in a test host could terminate the runner. Add `replyToTerminate: @MainActor (Bool) -> Void` to LichessBotControllerServices (default: NSApp.reply(toApplicationShouldTerminate:)).

Regression test: testQuitWhileOfflineWaitsForChallengeWithdrawals.
- Steps: online, send a challenge, goOffline (the fake holds the cancel response), then applicationShouldTerminate.
- Assert .terminateLater (before the fix: .terminateNow, so it fails) and that reply(true) fires only after the cancel request completed.

## 7. lichess#7 — Injected post-game chat schedule is unvalidated

Verdict: REAL, test-only exposure. Severity LOW, effort S.

Evidence:
- init stores the delays raw (Controller:405). schedulePostGameChatFetches files at `index == lastIndex` (Controller:875-890).
- Empty schedule: no tasks, so the game stays in gamesAwaitingPostGameChat forever. The reconciler sees a live owner, so it is never filed.
- Unsorted schedule: filing happens at the last element's delay, so a later fetch's lines go to an already-filed journal and are dropped by markFinalized (Journal finalized check).
- Production passes the sorted constant [60 s, 300 s]. Only LichessBotPostGameChatFilingTests:55 injects a schedule, and it is sorted.

Fix:
- Add `static func validatedPostGameChatSchedule(_:) throws -> [Duration]`: non-empty, each > .zero, strictly increasing.
- Init calls it under `do { … } catch { preconditionFailure("\(error)") }`, since this is a programmer error.
- Make scheduling one Task per game that sleeps the successive differences, fetches, then calls fileAfterPostGameChat. This also halves the number of tasks.

Regression test: testPostGameChatScheduleValidation. Empty and unsorted inputs throw; [60, 300] passes. It can't exist before the fix because the API is new.

## 8. lichess#8 — Resumed-journal decode runs on the journal queue

Verdict: REAL. Severity LOW, effort S.

Evidence:
- RecordStore.resumedJournal (RecordStore:136-145) reads and decodes the whole journal on journalQueue.
- It decodes twice: LichessBotJSONLines.decode, then each streamLine again in LichessBotResumedJournal.make (Play/LichessBotGameResume.swift:155-170).
- Every session's stream line awaits its journal append on that queue before being handled (GameSession:326 → Journal:225).
- So at go-online, resumed game B's decode delays resumed game A's move handling, by tens to hundreds of ms for a long game.
- Related, more frequent, and out of scope: finalize/fileGame (RecordStore:190-197) does a full decode, build and atomic writes on the same queue at every game end while other games play.

Fix: read only the raw Data on journalQueue (keeps the ordering snapshot after queued appends), then decode and run make on a separate `.utility` DispatchQueue via withCheckedThrowingContinuation.

Regression test (timing-based; flag the flake risk):
- With a ~40k-entry journal, a journal append issued just after resumedJournal starts must return before resumedJournal does. Pre-fix FIFO makes it wait for the decode.
- Alternatively the owner may accept no automated test for this one.
