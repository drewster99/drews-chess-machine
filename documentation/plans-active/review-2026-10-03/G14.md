## Analysis (analyzer, full)

G14 analysis (network reproducibility and safety claims): all 4 items verified at HEAD; none critical.

SUMMARY: net#1 is mostly a docs problem. The repo's own script and test already treat BN running stats as GPU-derived and not bit-exact, but five doc sites say the same seed gives the same network/tensors. net#2 is real: decision D-3 in the plan was never carried into MoveSampler, and the TODO points at P5, which is finished. But GPU logits make cross-machine move reproduction impossible anyway (A5), so the cheap fix is docs; the full fix is M and changes BehaviorFingerprint. net#3 is real: the doc is wrong, and a load's GPU command status is never checked. training#10 is real but latent, and broader than reported: three trainer readers skip the loaded-weights gate. The worst of them is exportTrainerWeights under bf16, which would export all-zero masters and velocities into a save.

1. net#1 — PARTLY REAL (docs only; low; S)
- Evidence: `Network/ChessMPSNetwork.swift:21-26` says "The same seed gives the same network on every machine". The trainables are pure CPU (`WeightInitialization.swift:13-17`, correct). BN running stats come from a GPU forward: `calibrateBNRunningStats` at ChessMPSNetwork.swift:213-257 (exportWeights → trainingNet.loadWeights → computeBatchStats → loadBNRunningStats). The training-mode sibling is built with the default `policyTailPrecision: .process` (`ChessNetwork.swift:591`). For bf16/fp16 models with an intermediate_conv or fc_bottleneck head, `policy_pre_bn` batch stats are computed in fp32 under `fp32_from_pre_bn` and in the compute dtype under `mixed_final_projection` (`ChessNetwork.swift:3146-3158`, `3198-3210`). So the stats depend on the process flag, and on the device/OS through kernel choice (plan A5).
- The project already knows: `scripts/init_reproducibility.sh:8-10` hashes BN stats separately "because GPU kernels need not be bit-identical across chips"; `WeightInitializationTests.testSeededMintIsReproducible` (:190-203) compares BN stats with a 1e-5 tolerance, not bitwise; `NewModelCLI.swift:112-113` writes "BN warm-up under policy tail precision X" into the notes.
- Contradicting docs: ChessMPSNetwork.swift:22-26; `BuildNewModelModel.swift:77-79` ("on every machine"); `BuildInitSeedField.swift:10-13`; `NewModelCLI.swift:12-13` ("re-mints the same tensors"); `DrewsChessMachineApp.swift:2134-2135` ("reproduces a mint exactly … same tensors").
- Nothing in code relies on a bit-exact re-mint. Grafts use the CPU-only init with BN stats at 0/1 (GraftDeriveTests:85-104). Exact resumes load files.
- Fix (recommended, S): reword those five sites to "the trainable tensors are bit-identical on every machine; the BN running statistics are calibrated by one GPU forward pass and match only to float tolerance; across chips or OS builds, and for bf16/fp16 models across `--policy-tail-precision` values, they can differ in the last bits."
- Optional (owner call): remove the flag dependence by building the calibration sibling with `policyTailPrecision: .float32FromPreBatchNorm` explicitly in `calibrateBNRunningStats`. This changes fresh-mint BN stats for bf16 intermediate/fc-bottleneck heads relative to today's default, and the NewModelCLI note at :112-113 would then need rewording. Not needed for correctness.
- Test: none for a docs-only change. If the pin is taken, `calibrateBNRunningStats` needs a precision parameter (`.process` is static) so a test can assert the stats are equal under both values.

2. net#2 — REAL (low–med; S for honest docs, M to implement D-3)
- Evidence: `Network/MoveSampler.swift` still uses `vvexpf` in the softmax on every ply (:148), `powf(u, 1/alpha)` in the α<1 Gamma boost (:257; the Dirichlet α is 0.3, so every noised draw takes this path), `logf` in the Marsaglia–Tsang full acceptance (:288), and `logf`/`cosf` in Box–Muller (:299-303).
- `Utils/DCMNormalMath.swift:15-19` claims "Weight initialization and move sampling must reproduce from a recorded seed on every machine", and plan A5 D-3 (DETERMINISM_RESUME_LINEAGE_PLAN.md:352) decided MoveSampler's log/cos would be replaced. P3's deviations (:1404) say "libm logf/cosf … remain (P5's restricted-domain math)". P5 is marked "Done (3b601c50)" (:1500) but only covered init. The TODO at MoveSampler.swift:51-54 ("part of the per-tensor init work") is stale.
- Practical impact: the logits come from a GPU forward that is not bit-reproducible across machines (A5, and the G9 measurement), so sampled moves cannot reproduce across machines whatever the CPU math does. The only thing the libm calls break is the Dirichlet η vector being a pure function of the stream across OS builds. One more effect: a ULP flip at the Marsaglia–Tsang accept/reject boundary changes how many draws are consumed, which shifts the stream position (probability is negligible).
- Option A (recommended, S): fix the docs. Delete the stale TODO and replace it with the decided state, e.g.: "vForce exp and libm log/pow/cos are platform functions; the inputs are GPU logits that aren't cross-machine reproducible (A5), so only the draw sequence is pinned." Reword the move-sampling clause in DCMNormalMath.swift:15-19. Because this records a deviation from D-3, it needs owner sign-off and a note in the plan.
- Option B (honor D-3, M):
  - (a) `sampleStandardNormal` → `rng.nextStandardNormalPair().0`. Same draw count (2 × `next()`), so stream positions and the K-independence tests are unchanged.
  - (b) For the acceptance test, draw the index `k = next() >> 40`, set `u = Float(k + 1) * 0x1p-24`, use it in both the squeeze and the log test, and take `log u` from `DCMNormalMath.logOfGridUniform(k)`. `log v` needs a general-domain deterministic log; split the exponent with `Double.exponent`/`.significand` (exact) and reuse the same atanh series.
  - (c) The boost `u^(1/α) = exp(ln u / α)` needs a deterministic exp on (−∞, 0]: Cody–Waite reduction with hi/lo ln2 plus a Taylor series in Double, scaled by an exact 2^n.
  - Leave the softmax `vvexpf` as is (GPU-derived inputs; hot path at 200k+ calls/s), with a comment saying why.
- Option B consequences:
  - Every seeded self-play trajectory changes. `BehaviorFingerprint.swift:24/37/203-218` hashes Dirichlet-noised MoveSampler choices, so after this build every existing session's fingerprint mismatches and `--resume-exact` reports a behavior gap. That is technically correct, but interacts with G9.
  - Does not interact with any existing test: none pins exact Dirichlet outputs (MoveSamplerTests and SeededStreamDeterminismTests check statistics and equality between two runs; `test_sampleGamma_momentsMatchTheDistribution` guards the distribution).
- Option B tests (new file `MoveSamplerDeterministicMathTests`):
  - golden bit patterns for the first N `sampleGamma(alpha: 0.3)` draws and `sampleStandardNormal` draws from fixed seeds (these fail before the change because the values differ);
  - `sampleStandardNormal(seed s)` == `DCMRandom(seed s).nextStandardNormalPair().0`, bitwise;
  - accuracy sweeps of the new general log and exp against a Double libm reference, with a stated max-ULP bound.

3. net#3 — REAL (low; S–M)
- (a) Doc: `ChessNetwork.swift:542-546` says awaitingWeightLoad is "Read and cleared only on executionQueue … so the order of a load and a use is the queue's order". `ChessTrainer.swift:4482` and `:4628` read it on the trainer's own queue. The SyncBox makes this memory-safe; the ordering guarantee there actually comes from the caller awaiting `loadWeights` before training. Fix: reword to "cleared only by internalLoadWeights on executionQueue; read from any queue (the network's gates on executionQueue, the trainer's on its own); a use on another queue is ordered after a load only by the caller awaiting the load."
- (b) Status: `internalLoadWeights` (:1937-1981) runs the assigns with synchronous `graph.run(with: commandQueue, …)`, which returns no error status, then sets `awaitingWeightLoad.value = false` (:1980) unconditionally. If the GPU command fails, a zero-filled `overwrittenByLoad` network is marked loaded, which is exactly the "silent garbage" the gate exists to prevent. The codebase already checks status elsewhere: `ChessNetwork.swift:1672` (`gpuCommandFailed`, value baseline) and `ChessTrainer.swift:6883-6900` (working-weight sync uses `graph.encode(to: MPSCommandBuffer, feeds:targetTensors:targetOperations:executionDescriptor:)`, then commit, wait, check status).
- Fix: in `internalLoadWeights`, replace `graph.run` with the same pattern: `guard let cb = commandQueue.makeCommandBuffer()`, wrap it in `MPSCommandBuffer`, `graph.encode(to: mps, feeds: feeds, targetTensors: [allVars[0]], targetOperations: weightLoadAssignOps, executionDescriptor: nil)`, `mps.commit()`, `mps.waitUntilCompleted()`. Then require `.completed` on both `mps.rootCommandBuffer` and `mps.commandBuffer` (MPS may `commitAndContinue`); otherwise throw `ChessNetworkError.gpuCommandFailed(stage: "weight load", status:, error:)`. Clear the flag only after that check.
- Side issue noticed: `internalLoadWeights` does not take `weightAccessLock`, which `internalExportWeights` (:1879-1882) and trainer SGD do take. Trainer loads that go through `loadTrainerWeights` → `network.loadWeights` therefore don't serialize against an in-flight SGD commit. Callers pause training today; flagging it only, not verified as reachable.
- Tests:
  - Status: inducing a real GPU failure in XCTest isn't feasible. Factor the check into a pure `static func requireCompleted(_ statuses: [MTLCommandBufferStatus], errors:, stage:) throws` and test that `.error` throws `gpuCommandFailed` while `.completed` passes. This tests the helper, not the wiring, so the owner needs to accept that as the regression test.
  - Equivalence: existing load round-trips (`WeightInitializationTests` mirror test :175-187, `CheckpointManagerSafetensorsTests` bit-exact round-trips) must still pass. Add `testLoadWeightsViaEncodeMatchesExport`: load random weights, export them, and compare bit-equal.

4. training#10 — REAL, latent, and broader than reported (low–med; S)
- Evidence:
  - `ChessTrainer.readLayerHealthLiveState` / `internalReadLayerHealthLiveState` (:5761-5817) runs `graph.run` on masters or working variables with no `network.requireLoadedWeights`.
  - Same gap in `readMasterValues` (:5657-~5690) and `readVelocityValues` (:5558-~5590), which leaves `exportTrainerWeights` (:5439-5455) unguarded whenever masters exist (bf16 mixed precision). It would return zero masters and zero velocities, i.e. a session or trainer save of zeros. Under fp32 the base part goes through the guarded `network.exportWeights`.
  - `exportVelocitySnapshot` (:5540) is unguarded too. `legalMassSnapshot` is guarded (it goes through `network.exportWeights`/`evaluateBatched`).
  - This contradicts the contract in `WeightInitialization.swift:18-23` ("refuses to evaluate, export or train until a load").
- Reachability today: the GUI trainer is `.drawnSeed()` (`SessionController.swift:1007-1012`), never awaiting a load. CLI trainers built for load are loaded before their loops emit live lines or saves (`CorpusReplayRunner.swift:1379`, `TrainVsUciRunner.swift:359`). So this is latent defense-in-depth.
- Fix: add `try network.requireLoadedWeights("<op>")` as the first statement inside the trainer-queue block of `internalReadLayerHealthLiveState` ("readLayerHealthLiveState"), `readMasterValues` ("readMasterValues", inside the do before `graph.run`) and `readVelocityValues` ("readVelocityValues"). That covers exportTrainerWeights and exportVelocitySnapshot. Placement matches trainStep's gate at :4628.
- Safety check: the writers called during a load (`writeMasterValues`, `writeVelocityValues`, `resetVelocitiesToZero`) never call these readers. `loadTrainerWeights` writes masters before `network.loadWeights` clears the flag, which is fine because those are writes. The only test that builds a trainer `.overwrittenByLoad` is `WeightInitializationTests:216-224`, and it calls only trainStep, so no existing test changes.
- Tests (new file, e.g. `TrainerLoadGateTests.swift`, so no existing test is edited):
  - `testTrainerBuiltForLoadRefusesLiveLayerHealthUntilLoaded`: build `ChessTrainer(dropoutStream: DCMRandom(seed: 1), arch: small, initialization: .overwrittenByLoad)`; `readLayerHealthLiveState()` must throw `ChessNetworkError.weightsNotLoaded(operation: "readLayerHealthLiveState")`. Fails before the fix, which returns zero tensors.
  - `testBF16TrainerBuiltForLoadRefusesTrainerExportUntilLoaded`: same, with `computeDataType = .bFloat16` so masters exist; `exportTrainerWeights()` and `exportVelocitySnapshot()` must throw `weightsNotLoaded`. Fails before the fix, which returns zeros.
  - After `loadBaseWeightsResetVelocity`, all of the above succeed.
- Lead's call: the bf16 export gap is a separate finding beyond the finder's report; regroup it if you want it tracked on its own.
