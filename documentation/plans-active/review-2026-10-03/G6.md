## Analysis (analyzer, full)

G6 analysis (GUI resume verdict + parameter restore): all 6 items confirmed at HEAD, 5 REAL and 1 PARTLY.

SUMMARY: The GUI `[RESUME]` exactness verdict is computed from what the session *file* contains, not from what the resume actually restored. So a conflicting `--seed`, a derivation mismatch, or a failed buffer restore all still log EXACT, and the wrong verdict is written into every later save's lineage `not_exact_items`. Separately, `holdForThisRun` values are never released, so pre-feature values held for one resumed run leak into later fresh runs in the same launch, and every GUI resume prints a false `random_seed` NOT EXACT line. The rest is duplicate and hand-written restore paths.

## 1. app#2: no rng_sampler/serials gap when the saved streams are not continued. REAL.

- Evidence:
  - `SessionController+Lineage.swift:172-174` adds `[.rngSampler, .serials]` only when `resumableRunStreams(of:) == nil`.
  - `startRealTraining` (`SessionController+Training.swift:302-326`) also needs `inheritedRunSeed(...)` to succeed. It returns nil on a `--seed` conflict or a derivation mismatch (`RandomSeedMode.swift:150-156`, logged at `Lineage:204`). The else branch then draws a fresh seed, sets serials and arena count to 0, and skips the sampler restore (:341) and the dropout-stream restore (:1121).
  - `beginLineageSegment` → `guiResumeGaps` (Training:1282 → Lineage:101) still sees streams in the file and reports neither gap.
  - The `inheritedRunSeed` doc (Lineage:195-198) promises "reports rng_sampler / serials NOT EXACT"; nothing does.
- Fix:
  - Make the caller the single source: in `startRealTraining`, capture `let continuedRunStreams = resumedRunStreams` into the training Task.
  - Pass it to `beginLineageSegment(..., continuedRunStreams:)` and on to `guiResumeGaps(resumed:continuedRunStreams:...)`.
  - Replace the check at Lineage:172 with `if continuedRunStreams == nil { gaps += [.rngSampler, .serials] }`.
  - Make the parameter required, with no default.
- Test: `GuiResumeGapsTests.testStreamsInTheFileButNotContinuedAreNamed`. Use a trainer file with streams, a buffer and an arena clock, and `continuedRunStreams: nil`; expect `["rng_sampler","serials"]`. Before the fix it fails: the parameter doesn't exist, and the old logic returns [].
- Risk: the existing `GuiResumeGapsTests.gaps()` helper (line 81) needs one added argument, `continuedRunStreams: SessionController.resumableRunStreams(of: resumed)`. That is a test edit and needs owner approval; the expectations themselves don't change.
- Severity: MEDIUM, because the false EXACT is persisted into lineage. Effort: S.

## 2. app#3 + training#1: random-seed restore and the `holdForThisRun` leak. REAL (both parts).

### (a) False NOT EXACT line

- Training:247-272 always calls `resume.restore(RandomSeedModeParameter, saved: nil …)` and `resume.restore(RandomSeed.self, saved: nil …)`.
- `RandomSeed` is declared `absentValue: .refuseExact` (`TrainingParameters.swift:1349`), so every GUI resume appends random_seed to `notExactParameterIDs`. Training:273 then logs "[RESUME] NOT EXACT: parameters absent … random_seed".
- That line is false in both cases. When streams are inherited, the saved seed *is* continued. When they aren't, neither the current nor the saved seed is used (a seed is drawn).
- The comment at :247-254 ("no session records yet … lands with P9") is stale: P9 streams already exist and are consumed at :294-312.
- This line is separate from the ResumeExactness verdict and doesn't feed lineage, so it is log noise only.

### (b) Mode held at unseeded, and the hold leaks

- `RandomSeedModeParameter` has `.preFeature(0)`, so every resume runs `p.holdForThisRun { p.randomSeedMode = .unseeded }`.
- `holdForThisRun` (`TrainingParameters.swift:2271-2285`) only suppresses persistence. Nothing records or releases the held keys.
- Result: Stop, then a fresh "new session" start in the same launch, runs with the in-memory held values:
  - random_seed_mode=unseeded, so a user on seeded mode silently gets a drawn seed;
  - every pre-feature hold: dropout 0, illegal-mass 0, label smoothing 0, LR cycle off, criterion=score threshold. These go through `TrainerHyperparameters(snapshot)` at :280.
- The holdForThisRun doc ("the user's saved setting still governs the next fresh run") is false within a launch.
- Out-of-range `restoreFromSession` values (:2223-2242, "held for this run only") leak the same way.

### Fix A (seed)

- Delete Training:247-272 entirely; the GUI resume no longer touches `randomSeedMode` / `randomSeed`.
- In the else branch at :313, use `mode: (resumeState != nil && !continueMode) ? .unseeded : p.randomSeedMode`.
- Log `[RESUME] rng: the saved run's seed is not continued; a seed is drawn for this run`.
- Behavior is unchanged: a resume without continued streams still draws, and `--seed` still wins inside `resolve`. The rng gaps from item 1 already report it.

### Fix B (holds)

- In `TrainingParameters`, add a main-actor-only `nonisolated(unsafe) static var runHeldPriorValues: [String: ParameterValue]`, like `suppressPersistence`.
- `holdForThisRun<K>` and the out-of-range branch of `restoreFromSession` record the key's pre-hold raw value; the first hold wins.
- The closure-form `holdForThisRun(_:)` must take the key type. Its 3 callers are Training:266 (deleted by Fix A), :2977 and :3014.
- `commitAssignment` removes `K.id` from the map whenever it actually persists (`!suppressPersistence`), so a user edit during the run is kept.
- Add `func releaseRunHolds() throws`:
  - Apply the recorded prior values under `suppressPersistence`. Prior values may be non-persisted `--parameters` overrides, so restore them rather than re-reading UserDefaults.
  - Then clear the map.
- Call it in `startRealTraining` at the top of the `if !continueMode` block, before the resume block re-resolves. Continue-after-Stop keeps the holds.
- Surface a thrown error via `box.recordError` + `setCheckpointStatus(.error)`, never `try?`.

### Tests

- New `TrainingParametersRunHoldTests`:
  1. dropout 0.7 → resume with saved nil holds 0 → `releaseRunHolds()` → 0.7.
  2. hold, then a persisted user edit to 0.5, then release → 0.5.
  3. a `suppressPersistence` override of 0.3, then hold, then release → 0.3.
  - Before the fix these fail (no API, so a compile failure).
- For the seed:
  - First do a behavior-preserving extraction of Training:108-275 into `SessionParameterResume.applyGuiSession(_ rs: SessionCheckpointState)`. This also helps item 5.
  - Then `testGuiResumeLeavesTheSeedSettingsAlone`: with seeded mode, after applying, `p.randomSeedMode == .seeded` and `notExactParameterIDs` does not contain "random_seed". It fails before Fix A.

### Risks

- No persistence-format change.
- `SessionParameterResumeTests.testLegacySessionWithoutDropout…` still passes, since the hold is still applied for the run.
- The `[RESUME-DIFF]` lines for random_seed* disappear; no parsers consume them (grep: only Swift sources).

Severity: MEDIUM (silent wrong hyperparameters in a later fresh run). Effort: M.

## 3. app#4: a failed buffer restore isn't reported as a buffer gap. REAL; the sampler half is PARTLY.

- Evidence:
  - Training:1190-1227 catches a restore failure, logs "continuing with empty buffer" and keeps training.
  - `guiResumeGaps` checks only `resumed.replayBufferURL == nil` (Lineage:169-171), so a corrupt or mismatched buffer still yields EXACT.
  - The message is also sometimes false: `verifyReplayBufferMatchesSession` (`CheckpointManager.swift:1210-1223`) runs *after* `restore` has already filled the ring (`ReplayBuffer.swift:3484-3591`). On a totalPositionsAdded mismatch the buffer is NOT empty: it keeps positions that probably belong to another session.
  - The sampler restore at :344 is harmless. It continues the stream, and the buffer gap covers the content difference, so no change is needed there.
- Fix:
  - (i) Add `ReplayBuffer.restore(from:expectedTotalPositionsAdded: Int?)`, which checks the header's `ttlFile` against the expected count before the lock, alongside its other pre-mutation checks.
    - The existing `restore(from:)` forwards nil.
    - Call it with `resumedState?.replayBufferTotalPositionsAdded` and drop the post-hoc verify call.
    - A mismatch then leaves the buffer untouched and empty, so the message becomes true.
  - (ii) Track `var replayBufferRestored = resumedBufferURL != nil` in the Task and set it to false in the catch.
    - Pass it into `beginLineageSegment` → `guiResumeGaps(..., replayBufferRestored:)` and replace the check at Lineage:169 with it.
    - With item 1, this changes the `GuiResumeGapsTests` helper again; needs owner approval.
- Tests:
  - `ReplayBufferPersistenceTests.testRestoreWithMismatchedTotalLeavesBufferEmpty`: save N, restore with expected N+1 → throws, `storedCount == 0`.
  - `GuiResumeGapsTests.testFailedBufferRestoreIsNamed`: URL present, `replayBufferRestored: false` → ["buffer"].
- Severity: MEDIUM-LOW. Effort: S-M.

## 4. training#2: the legal-mass grace period is spent during the post-resume buffer refill. REAL.

- Evidence:
  - The live stats box is seeded with `steps = rs.trainingSteps` (Training:76-79).
  - The detector gate `guard trainingSteps > 0` (:2620-2624) therefore passes on the first probe, about 60 s in, during the refill. `graceElapsed` anchors there (:2625), so the refill time is charged against the grace period.
  - This contradicts the box doc (`LegalMassCollapseDetectorState.swift:28-32`: "Refilling the replay buffer after a resume therefore spends none of the grace period").
  - It is the common case now, because saves omit the buffer by default (D-8).
  - Practical impact is small: the resumed network is trained, so it isn't near the random-init illegal mass ≈0.994 that grace protects against.
- Fix:
  - Capture `let graceStepBaseline = continueMode ? 0 : (resumeState?.trainingSteps ?? 0)` on the main actor. Keep 0 on continue so its existing anchor isn't reset.
  - Move the gate into the box: `func graceElapsed(trainingSteps: Int, stepsAtRunStart: Int, at now: Date) -> TimeInterval?`.
    - It returns nil and does `trainingStartAt = nil` while `trainingSteps <= stepsAtRunStart`.
    - Otherwise it behaves like today's `graceElapsed`.
- Test: `LegalMassCollapseDetectorStateTests.testResumedStepCountDoesNotStartGrace`. Restore with grace 90, call with (5000, 5000, t0) → nil, then with (5001, 5000, t0+600) → 90. Fails before the fix (new API). Existing tests are untouched.
- Side note, not fixed here: on continue-after-Stop the old wall-clock anchor stays, so time spent stopped counts as grace.
- Severity: LOW. Effort: S.

## 6. app#10b: `arenaConcurrency` is clamped before the resolver. REAL.

- Evidence:
  - Training:216 passes `rs.arenaConcurrency.map { min(absoluteMaxArenaConcurrency, $0) }`, so the `[RESUME-DIFF]` line reports the clamped value as `saved=`.
  - The ceiling has two sources of truth:
    - The declaration says `range: 1...4096` (TrainingParameters:905-913).
    - `UpperContentView.absoluteMaxArenaConcurrency = 1024` (:313) is enforced by hand in three places: the resume clamp, the parameters loader (UpperContentView:2221-2224), and the popover (`ArenaSettingsPopoverModel:197`).
  - The consumer (`Arena.swift:223`) does not clamp.
  - `arenaConcurrencyDefault = 200` (UpperContentView:303) is dead (no references) and contradicts the declared default of 400.
- Fix:
  - Declare `range: 1...1024` and derive the cap from the declaration.
  - Remove the clamps at Training:216 and UpperContentView:2221-2224. A >1024 value in `parameters.json` then fails validation with an error instead of being clamped silently.
  - Delete `arenaConcurrencyDefault`.
  - Regenerate `documentation/parameters.md`.
- Risk: a stored UserDefaults value above 1024 would now be flagged invalid at launch, but the UI could never write one, so this is effectively nil.
- Test: `testArenaConcurrencyCapIsTheDeclaredRange` asserts `UpperContentView.absoluteMaxArenaConcurrency == ArenaConcurrency.definition.intRange?.max`. Fails today (1024 vs 4096).
- Severity: LOW. Effort: S.
