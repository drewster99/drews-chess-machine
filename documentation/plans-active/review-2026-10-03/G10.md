## Analysis (analyzer, full)

G10 analysis (train-vs-UCI path), verified at HEAD 665095c4.
Summary: all five items are real, but none is high severity. cli#3: the GUI pauses self-play around a save; train-vs-UCI does not pause its driver. The periodic save blocks the driver's cooperative thread for the length of the buffer write, and the run's streams/counters are captured a few moments before the buffer they go with. cli#4 and cli#9 are small CLI inconsistencies. cli#5: session.json makes false claims, but no code reads them. cli#7/training#4: a corrupt lineage counter traps the process instead of throwing an error, on both the vsuci path and the GUI path.

1. cli#3: buffer lock held during a multi-GB write while the driver runs. PARTLY REAL. Medium-low, effort M.
 - Evidence: `ReplayBuffer.write(to:)` holds `lock.withLock { _writeLocked }` for the whole write (Training/ReplayBuffer.swift:2936-2937). `CheckpointManager.saveSession` calls it synchronously in the caller's task (Persistence/CheckpointManager.swift:1507-1509). In TrainVsUciRunner the in-loop periodic save (`saveSession(step:kind:.periodic)`, CLI/TrainVsUciRunner.swift:837-839 → 580-616) runs while `driverTask` (`Task { await driver.run() }`, :673) keeps ticking. `finishGame` → `slot.game.flush(buffer:)` (Training/TrainVsUciDriver.swift:534) → `buffer.append` then blocks a cooperative thread on the unfair lock for the length of the write. The GUI avoids this by pausing self-play through `selfPlayGate.pauseAndWait` before saving (App/SessionController+Checkpoint.swift:380-399). The final/abort save is not affected, because the driver has already been cancelled and awaited (:852-859).
 - Second effect: `trainerSave` reads `gameSerials.nextSerial`, `driver.currentGameIndices()` and the slot game/ply totals (:521-541) before the buffer is written. Games flushed in between end up in `replay_buffer.bin` while the lineage's opponent indices and cum_games describe an earlier instant. A resume then replays an index whose game is already in the buffer, and cum_games disagrees with the buffer. Minor, but the same fix removes it.
 - Restore half: `Task.detached { try buffer.restore(from:) }` (:390-392) is a long synchronous read inside a Task, which breaks the rule. But it runs before the driver or trainer starts, so nothing contends with it, and it is the same pattern the GUI resume uses (App/SessionController+Training.swift:1192-1198). This half is a rule violation only, not a behaviour bug.
 - Fix (minimal, mirrors the GUI):
   - Give `TrainVsUciDriver` a `pauseGate: WorkerPauseGate` init parameter.
   - At the top of each `run()` loop iteration (Training/TrainVsUciDriver.swift:239), before `runOneTick`:
     `if pauseGate.isRequestedToPause { pauseGate.markWaiting(); while pauseGate.isRequestedToPause && !Task.isCancelled { do { try await Task.sleep(for: .milliseconds(5)) } catch { break } }; pauseGate.markRunning() }`
   - In-flight games are kept, not dropped like self-play's; opponent replies queue in `eventBox`.
   - In the runner's `saveSession`, inside the existing `do`, before `syncEvalNet`: when the driver is still live (`!driverDone.value` and teardown has not happened yet; track a `driverStopped` local, or pass `pauseDriver: Bool` true only for the periodic call), call `guard await driverPause.pauseAndWait(timeoutMs: <named constant>) else { throw TrainVsUciError.driverDidNotPauseForSave(timeoutMs:) }` and `defer { driverPause.resume() }`.
   - A timeout is a save failure, so it goes through the existing streak and is never a silent unpaused save.
   - Optional broader cleanup, done once in shared code: in `CheckpointManager.saveSession`, bridge `replayBuffer.write` and the scratch verify `restore` through `withCheckedThrowingContinuation` + `DispatchQueue.global(qos: .userInitiated)` (the pattern in Persistence/ModelFileCatalog.swift:85-89). Do the same at both restore sites. This touches GUI callers too, so treat it as separate.
 - Test: new `TrainVsUciDriverPauseTests` (MPS network built the way other tests build one, plus the perl fake engine from UCIArbiterTests). Start `driver.run()` in a Task, then assert:
   - `pauseAndWait(timeoutMs:)` returns true;
   - while paused, `statsSnapshot()` and `currentGameIndices()` stay unchanged across a ~200 ms wait;
   - after `resume()`, cancel and await.
   Before the fix the gate does not exist, so the test does not compile.
 - Risks:
   - The pause covers the whole session save, including model and buffer verify, so engines sit idle for that time. The trainer is already stalled awaiting the save, so no throughput is lost.
   - Do not pause for the final or abort save; the driver is gone and `pauseAndWait` would time out.
   - No existing test changes.

2. cli#4: a symlinked model file is refused, although the doc says links are followed. REAL. Low, effort S.
 - Evidence: CLI/TrainVsUciSession.swift:72-74 says "A symbolic link is followed". `fileExists` follows the link (:78), but `attributesOfItem` (:90) does not follow a terminal link, so `type == .typeSymbolicLink` and the start is refused at :94-95 as `notAFileOrFolder(kind: "NSFileTypeSymbolicLink")`. I checked this in scratch: on a link to a regular file, `attributesOfItem` returns `NSFileTypeSymbolicLink`, and the same call on `resolvingSymlinksInPath()` returns `NSFileTypeRegular`. A link to a session folder already works, because `fileExists` follows it to a directory. `loadModelFile` uses `Data(contentsOf:)`, which follows links (Persistence/CheckpointManager.swift:1832).
 - Fix: `let attributes = try FileManager.default.attributesOfItem(atPath: url.resolvingSymlinksInPath().path)`. Keep returning `.modelFile(url)`, the link path, so step-file naming stays next to the path the user typed, matching what the session branch returns. A dangling link already fails at :78 as `.missing`.
 - Test: `testStartSourceFollowsASymbolicLinkToAModelFile` in TrainVsUciSessionTests. Create `m.safetensors`, symlink `l.safetensors` to it, and assert `startSource(path: l) == .modelFile(l)`; also assert a link to a FIFO is still refused. Before the fix the call throws `notAFileOrFolder`. Existing tests are unaffected.

3. cli#5: session.json values that the run did not use. PARTLY REAL. Low, effort S.
 - `maxPliesPerGame: p.selfPlayMaxPliesPerGame` (CLI/TrainVsUciSession.swift:193) is REAL. The run's games are capped by `config.maxPliesPerGame` (`--max-plies`, default 400, App/DrewsChessMachineApp.swift:1443/1507; used at TrainVsUciRunner.swift:489/824). The field's doc (Persistence/SessionCheckpointFile.swift:636-642) describes a game-length cap past which a game is dropped without emit, which is exactly what `--max-plies` does here. So the saved value is false, not merely "configured and unused".
 - `replayRatioTarget` / `replayRatioAutoAdjust` / `stepDelayMs` (:159-161) are REAL as an inconsistency. The runner deliberately records `replayRatioTarget: nil` in results.json because "emitting it would be a fresh false claim" (TrainVsUciRunner.swift:825-828). This path has no ratio controller and no step delay. The type doc (:16-19) only allows configured-but-unused values for the self-play and arena fields.
 - `trainingPositionsSeen = steps × current batch` (:130) is NOT REAL as a vsuci defect. It is the GUI's formula exactly (App/SessionController+Checkpoint.swift:1083). Its only reader is the GUI auto-resume display, and the GUI refuses vsuci sessions.
 - Fix:
   - Add `maxPliesPerGame: Int` to `TrainVsUciSession.sessionState(...)` and pass `config.maxPliesPerGame`.
   - Write `nil` for the Optional `replayRatioTarget`, `replayRatioAutoAdjust` and `stepDelayMs`.
   - Update the type doc to name those as not recorded.
   - No reader needs these values: vsuci resume uses `startSession.state` only for `verifyReplayBufferMatchesSession`, and the GUI refuses vsuci sessions.
 - OWNER APPROVAL NEEDED: the signature change requires editing both existing `sessionState(...)` calls in TrainVsUciSessionTests (~:145 and ~:194). The alternative with no test edit is to assign `state.maxPliesPerGame = config.maxPliesPerGame` in the runner (the field is a `var`). That builds the state in two places, so it is not recommended.
 - Test: `testASessionRecordsWhatTheRunPlayedAndNothingItDidNot`. Assert `state.maxPliesPerGame == 123` when 123 is passed, and that `replayRatioTarget`, `replayRatioAutoAdjust` and `stepDelayMs` are nil. The nil assertions fail before the fix.
 - Related, not fixed: `--max-plies` and `--eval-sync-steps` change the training data but are recorded only in the lineage argv, so an exact resume with different values still reports EXACT. Worth raising with the owner; it is not part of this item.

4. cli#9: a `--checkpoint-stem` containing a dot is refused. REAL. Low, effort S.
 - Evidence: `guard url.pathExtension.isEmpty` (CLI/TrainVsUciSession.swift:243) refuses `sf100-lr0.5` (extension "5") with the "names a file" error. The default stem, taken from a start model like `foo.v2.safetensors`, keeps its dot (:253). Corpus replay's `--out-model` accepts dots (CLI/CorpusReplayRunner.swift:1058-1060). `EnumeratedCheckpointNaming` handles dotted stems correctly, since it strips only the final extension of the base `…-vsuci-latest.safetensors` (:409).
 - Fix: refuse only a model or session extension: `guard !["safetensors", "dcmmodel", "dcmsession"].contains(url.pathExtension.lowercased())`. Keep `hasExtension(stem:)` and adjust its message to "names a model file or session". The extension literals are scattered across the codebase; a shared constant is a separate cleanup and not needed here.
 - Test: `testACheckpointStemMayContainADot`. Stem `<tmp>/sf100-lr0.5` should give `naming.url(step: 1000) == <tmp>/sf100-lr0.5-vsuci-step1000.safetensors`. Also assert that `run.DCMMODEL` and `run.dcmsession` are refused. Before the fix the dotted stem throws `hasExtension`. The existing `testACheckpointStemMustNotBeAFileOrAStepName` (`run.safetensors`) still passes unchanged.

5. cli#7 + training#4: `RunStreams` counters are not validated, so bad values trap or overflow. REAL. Low (needs a corrupt or hand-edited file), effort S.
 - Evidence: `nextGameSerial`, `arenasStarted` and `opponentGameIndices` are decoded with no range check (Persistence/LineageRecord.swift:672-674).
   - A negative `next_game_serial` hits `precondition(firstSerial >= 0)` (Training/GameSerialCounter.swift:22) and crashes the process. It is reachable from vsuci resume (TrainVsUciRunner.swift:467) and also from GUI session resume (App/SessionController+Training.swift:303-306). That is a crash on a resume prompt, not an error.
   - `Int.max` overflows in `next()` (`serial += 1`) and in the driver's `slot.gameIndex += 1` (TrainVsUciDriver.swift:573/596).
   - A negative opponent index does not crash: `% 2` gives -1, so the trainer simply plays Black.
 - Fix: validate in `RunStreams.init(from:)` and throw `DecodingError.dataCorruptedError`, the same way the non-decimal `master_seed` check already does (:663-666). Each counter must satisfy `0...RunStreams.maximumRecordedCounter`, a named sanity cap far above any real run, e.g. `Int(UInt32.max)`. This follows the project's precedent of capping on-disk counters "so a corrupted or hostile header cannot coax the decoder into … integer overflow" (ReplayBuffer.swift:2906-2913).
   - A bad value then surfaces as `SafetensorsModelIO.IOError.malformedLineage` (Persistence/SafetensorsModelIO.swift:379-383), the same strictness as other lineage fields, and covers every consumer in one place.
   - Trade-off: such a file becomes unloadable everywhere, play included. That matches today's handling of a bad `master_seed`.
 - Test: `testRunStreamsRefuseOutOfRangeCounters` in ExactResumeCompletionTests, next to `testRunStreamsRoundTripIncludingASeedAboveTwoToThe53`. Encode a valid `streams(...)`, then patch the JSON to `next_game_serial: -1`, `arenas_started: -1`, `opponent_game_indices: [0, -1]`, and a value above the cap. Each `JSONDecoder().decode` must throw. Before the fix all of them decode.
 - Risks: existing fixtures use small values (412/7, 9/2, 12/3, indices [5,0,2]/[3,4]), so no test edits are needed. The encoder writes live counters, which are never negative.
