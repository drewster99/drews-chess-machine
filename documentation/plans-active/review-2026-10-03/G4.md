## Analysis (analyzer, full)

G4 analysis (lineage of derived/champion files), verified at HEAD 665095c4: all 6 items are REAL (item 3 is persist#3 and app#5 merged).

Summary:
- The "is this source trained?" signal is only the raw `training_step` key. Grafts never write it, and Save Champion can leave it out, so derive's guard can be bypassed.
- Champion files carry the trainer's lineage record. Copies of pre-v7 files turn a segment-local step into a cumulative total.
- The GUI decode path is lenient where the CLI path is strict. The Python lineage tools refuse every GUI v7 session folder.
- Fix items 1 and 2 together (item 2 removes one of item 1's evidence signals). Item 3 changes the inputs to item 6.

1. lineage#1, derive's trained-source guard can be bypassed. REAL. Severity: medium-high (it mislabels new files; no data is lost). Effort: S.
- Evidence:
  - `ModelDerivation.requireUntrainedSource` (Persistence/ModelDerivation.swift:483-491, called at :367-369) only reads raw `training_step`. A missing key is treated as fresh.
  - The graft output metadata is built without `training_step` on purpose (ModelGraft.swift:374-388; header :26-33). Its lineage continues the source's totals through `untrainedCopyRecord`.
  - Save Champion writes `trainingStep: trainingStats?.steps` (SessionController+Checkpoint.swift:86-91). That is nil after Load Model with no run (`clearTrainingDisplay` sets it nil, UpperContentView.swift:1976).
  - Result: graft a trained v7 file, or Save Champion a loaded trained file, then run `--derive-model --set-neutral-init` (or any tensor-rewrite op). It rewrites trained tensors, and the file's lineage still continues the trained totals.
  - The docs that state the guard as complete are wrong: ModelDerivation.swift:916-919 and ModelGraft.swift:26-28.
- Fix (positive evidence; needs no test edits): rename to `requireUntrainedSource(_ md:, lineage: LineageRecord.Presence, sourceName:)` and call it after `sourceLineage` is decoded. Refuse when any of these holds:
  - (a) raw `training_step` > 0 (the existing check, malformed value still an error);
  - (b) `record.steps.cumTrainerStep` > 0;
  - (c) `record.parent?.trainerCompletedSteps` > 0, meaning the weights descend from a trained file. This catches grafts and champion copies of pre-v7 sources once item 2 makes their cum null.
  - (d) any `record.derivationHistory` operation with `arguments["source_training_step"]` > 0. This catches a graft followed by an architecture-only derive, then a rewrite.
  - Add `DeriveError.sourceIsTrainedByLineage(source:, evidence:)`. Its message must contain "training_step"; `assertRefusedAsTrained` at DeriveTrainedSourceTests.swift:52-58 greps for it.
  - Update the two doc blocks.
- Stricter rule considered and not recommended: "refuse unless the record states cum == 0". It breaks `DeriveTrainedSourceTests.testDeriveAllowsTensorRewritesOnAnUntrainedSource` and the InitNeutralOptions/InitSeedRecording/SEBeta fixtures, which all use `LineageRecord.forTests(trainerCompletedSteps: nil)` (cum null). Fixing them is a test edit that needs owner approval. It would also refuse legitimate v7 derives of pre-v7 fresh files.
- Remaining gap: a pre-v7 file that was trained but has no `training_step` and no lineage stays undetectable. State this in the docs.
- Also: session save's `trainingStats?.steps ?? 0` (Checkpoint:342, Arena:615) is a silent default that writes "untrained" (0). It is unreachable in practice because of the `realTraining` guard. Item 3's fix replaces it.
- Regression tests (new file DeriveLineageTrainedSourceTests.swift):
  - `testRewriteOnAGraftOfATrainedSourceIsRefused`: v7 source with step 4200 and lineage cum 4200 -> `ModelDerivation.graft` -> derive `SetRezeroAlphaInitDeriveOperation` on the output -> throws. Fails today because the graft output has no `training_step`.
  - `testRewriteOnAGraftOfAPreLineageTrainedSourceIsRefused`: lineage cum nil, step 4200; caught by (c) and (d).
  - `testRewriteOnAChampionCopyOfATrainedFileIsRefused`: file encoded with `trainingStep: nil` and lineage from `untrainedCopyRecord(ParentFile(tcs: 5000, .recorded(cum 5000)))`.
  - `testRewriteOnAGraftOfAFreshMintStaysAllowed`: guards against over-refusal (mint record cum 0, parent nil).
- Existing tests checked and unaffected: the LineageProvenance and LineageRecordTests derives use architecture-only operations; GraftDeriveTests never derives a graft output.

2. lineage#2, `untrainedCopyRecord` uses a segment-local step as the cumulative total. REAL. Severity: medium. Effort: S.
- Evidence:
  - LineageTracker.swift:341-347 falls back to `source.trainerCompletedSteps` when the source has no record.
  - `trainerClock` (SafetensorsModelIO.swift:410-419) falls back to raw `training_step`.
  - Pre-v7 resumed replay segments restart that counter at 1 (documentation/v5-lineage.md §1, "Every resumed segment restarts its step counter at 1").
  - So a derive, graft or GUI Save Champion of such a file stamps `cum_trainer_step` = the segment-local step (for example 300k where the true total is 1.39M). This contradicts "a total a predecessor never recorded is null… never reconstructed", and the comment at :342-344 is false.
- Fix: `sourceStepTotal = sourceRecord?.steps.cumTrainerStep` (nil with no record). Keep `parent.trainerCompletedSteps` as the raw stated step, which is what item 1 (c) uses. Rewrite the comment.
- Risks: derive, graft and Save Champion outputs of pre-v7 sources now show `cum_trainer_step=unrecorded` (mirror key). Branch runs don't read the parent's cum. No existing test asserts the old value (LineageRecordTests:320 is a tracker resume, not a copy).
- Test: `UntrainedCopyRecordTests.testCopyOfAPreLineageFileLeavesTheStepTotalUnrecorded`: `ParentFile(tcs: 300_000, lineage: .unrecorded(6))` -> `cumTrainerStep == nil` and `parent.trainerCompletedSteps == 300_000`. Fails today (300_000).

3. persist#3 + app#5, champion.safetensors is stamped with the trainer's lineage and `championOrigin` is ignored. REAL. Severity: medium. Effort: M.
- Evidence:
  - `CheckpointManager.saveSession` encodes champion and trainer with the same `lineage` (CheckpointManager.swift:1377, 1430-1450). The comment at :1375-1376 says this is intended.
  - The GUI save passes `lineageRecordForSave(trainer's completedTrainSteps, trainer philox, streams)` (Checkpoint:443-462).
  - Save Champion during a run uses the same "now" record (Lineage.swift:296-302).
  - After a promotion the champion holds weights from step P. Arena.swift:552-576 even builds the right record into `championOrigin`, but no save reads it. Later periodic or manual saves claim the trainer's cum T > P, the trainer's games and time totals, and the trainer's dropout and stream state. Champion `training_step` is also the trainer's.
  - On resume, Checkpoint:923 sets `championOrigin` from that champion file, so the wrong totals propagate. A Load Model, branch or derive from it inherits them.
  - Train-vs-UCI is correct: its champion is synced from the trainer at each save (TrainVsUciRunner.swift:596-610).
- Fix:
  - (i) Give `CheckpointManager.saveSession` a required `championLineage: LineageRecord`; `lineage:` stays the trainer and session.json record. Train-vs-UCI passes `save.lineage` for both.
  - (ii) Add one function, `SessionController.championFileLineageRecord(origin: ChampionOrigin?, at:)`, preferably static so it can be tested, used by session save, the arena inline save and Save Champion. It returns:
    - `.built` -> `mintRecord(.gui)`;
    - `.file(src)` with a recorded lineage -> `src`'s record verbatim (exact for promoted or loaded weights; no new run per save);
    - `.file(src)` unrecorded -> `untrainedCopyRecord(.gui)`;
    - nil -> throw `.noChampionOrigin`.
  - (iii) Build the promotion record at Arena:556 with `dropoutPhiloxState: nil, dropoutStreamState: nil`, because a champion file has no trainer state; a branch doesn't restore RNG. On failure, set `championOrigin = nil` and log, instead of the current silent `.unrecorded` fallback (:561-562). Later saves or branches then fail loudly.
  - (iv) Champion `training_step` comes from the origin (`src.trainerCompletedSteps`, or 0 for built) instead of trainer stats, which also removes Save Champion's nil case.
  - Rewrite the comments at CheckpointManager:1375 and Arena:641.
- Risks:
  - The new parameter means mechanical call-site edits to existing tests: ExactResumeTests, TrainVsUciSessionTests, CheckpointHousekeepingTests and CheckpointManagerSafetensorsTests (7 calls). These need owner approval. A defaulted parameter would avoid them but is a silent default.
  - Existing session folders keep the wrong champion record (no migration, per the rules).
  - No loader compares champion and trainer lineage (grep found none).
- Tests:
  - `ChampionLineageRecordTests.testPromotedChampionKeepsItsPromotionRecord`: origin `.file` with a recorded cum-1000 record -> returned record cum 1000.
  - `testBuiltChampionGetsAMintRecord`.
  - `CheckpointManagerSafetensorsTests`-style new test: the champion file decodes to `championLineage` and the trainer file to `lineage`.
  - Caveat: these exercise a new API, so they fail before the fix only by not compiling. Say so plainly.

4. persist#4, `lineageParent` is lenient where `readParentFile` and `trainerClock` are strict. REAL. Severity: low. Effort: S.
- Evidence: `SafetensorsModelIO.decode` uses `md[Key.trainingStep].flatMap { Int($0) }` (:346), `modelID ?? ""` (:353) and `createdAt ?? 0`. `ModelCheckpointFile.lineageParent` (:370-391) then re-derives the clock from that. `readParentFile` (:389-403) throws `missingModelID` and `malformedTrainingStep`. So the GUI paths (Load Model at Checkpoint:730-732, session resume at :921-923, which also sets `champion.identifier = ModelID(value: "")`) accept files the CLI refuses, with a nil clock or an empty model ID. Two rules for one fact.
- Fix: in `decode`, require `model_id` (throw `IOError.missingModelID`) and get the clock from `SafetensorsModelIO.trainerClock(fromMetadata:source:)`. Store it on the file, or keep `metadata.trainingStep` as the strict parse, and have `lineageParent` reuse the one helper rather than repeat the rule. Optionally reject negative values in `trainerClock`.
- Risk: `DeriveTrainedSourceTests.testDeriveRefusesAMalformedRecordedTrainingStep` still passes. derive decodes first, so "twelve" and "1.5" now throw `malformedTrainingStep`, whose text contains "training_step"; "-5" still reaches `requireUntrainedSource`. Run CheckpointManagerSafetensorsTests and the SafetensorsModelIO suites, since any fixture without `model_id` would now fail to decode.
- Test: `SafetensorsDecodeStrictnessTests`:
  - malformed `training_step` -> decode throws (it succeeds today);
  - missing `model_id` -> decode throws;
  - for a valid file, `decode(...).file.lineageParent == readParentFile(...)` (`trainerCompletedSteps`, `modelID`).

6. tools#1, `derive_runs` refuses every GUI v7 session. REAL. Severity: medium (the self-play lineage table is unusable). Effort: S.
- Evidence: scripts/dcm_lineage.py:428-431 requires one model_id per segment. A GUI session folder has champion.safetensors (champion ID) and trainer.safetensors (trainer generation ID, always different) under one record. The trainer ID also changes at every promotion within a segment. So `selfplay.py --lineage-table` (selfplay.py:400) always prints "refused". `_lineage_registry.derive_registry` is only used for replay and vsuci, where one ID per segment does hold, and the existing tests cover only replay.
- Fix:
  - In `derive_runs`, apply the single-model_id rule only to path kinds `{"replay", "vsuci"}` (`SINGLE_MODEL_PATH_KINDS`).
  - For "gui", leave `model_id` out of the per-file view and set a segment field `model_ids = sorted(set)`; still refuse a None model_id. Add "model_ids" to `DERIVED_SEGMENT_FIELDS` and `segment_table`.
  - Also make `print_lineage_table` scan only `trainer.safetensors` in session folders. After item 3, a champion record can describe an earlier segment, or a mint or copy run, not the run's progress.
- Risk: the replay refusal test (test_lineage.py:234) still passes.
- Test: `test_gui_session_folder_with_differing_champion_and_trainer_ids_derives` in documentation/dashboards/tests/test_lineage.py. Write two v7 files with the same `path_kind` "gui" record and different model_ids -> `derive_runs` succeeds and `model_ids` lists both (raises `LineageError` today). Also add a two-trainer-IDs-in-one-segment case.
