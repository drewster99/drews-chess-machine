## Analysis (analyzer, full)

G11 analysis (corpus recording + validator): 4 of 5 items are REAL and 1 is PARTLY.
SUMMARY: The one finding that matters is #1. It is medium severity: when a shard rotation fails, the rest of a run's self-play recording is quietly lost. A related bug I found while checking it (a torn partial write) can also corrupt a whole 64 MB shard, and the same fix covers it. #8 is a real but narrow lost-update. #5, #7 and #9 are low-severity cleanup and doc/message fixes. None of the fixes needs an existing test changed. All proposed tests are new.

1. persist#1: rotation seal failure leaves the source stuck — REAL (MEDIUM, M)
 Evidence:
 - GameCorpus.swift:319-325 sets currentWriter=nil, then calls `try writer.seal` and then `try openNewShard()`. If either throws, currentSourceID stays set and currentWriter stays nil.
 - Every later append hits :310-311 and throws `invalidState("no source in progress; call beginSource first")`, which is both misleading and permanent.
 - CorpusRecorder.swift:54-60 only logs and counts. It writes one `[CORPUS] append failed` line for every remaining game of the run, and each of those games is dropped.
 - finishSource (:330-343) skips the nil writer and still sets `complete = true` (:340). gamesAdded counts games that sit in the unsealed .open shard (counted at :316, before the seal).
 - ShardWriter.seal's closeAfterFailure (GameCorpusShard.swift:334/340) releases the lock, so the .open shard is a recoverable leftover. That part is fine.
 - Realistic triggers: disk full during the trailer write or fsync, or the rename refusing because the final name already exists (GameCorpusShard.swift:338).
 - Related bug, same root cause: if ShardWriter.appendFramed (GameCorpusShard.swift:303-308) fails part-way through a write (for example on a full disk), the torn bytes stay in the file while `hasher` excludes them, and the writer keeps being used. The eventual seal then produces a shard whose body fails its SHA check (shardSHAMismatch), so readSealed rejects the whole shard.
 Fix (GameCorpus.swift, CorpusRecorder.swift, PGNImporter needs no change):
 - Add `private var stoppedSourceFailure: String?` to GameCorpus. Treat any failure inside append(framed:) as ending the source:
   ```
   if let cause = stoppedSourceFailure { throw GameCorpusError.sourceStopped(sourceID: <current source id>, cause: cause) }
   do { try writer.appendFramed(frame, plyCount: plyCount) }
   catch { throw stopSource(writer, cause: "append to \(writer.openURL.lastPathComponent): \(error.localizedDescription)") }
   <count games/plies>
   if writer.byteCount >= shardSoftLimitBytes {
       currentWriter = nil
       do { _ = try writer.seal(...); try openNewShard() }
       catch { stoppedSourceFailure = "rotation after \(writer.openURL.lastPathComponent): \(error.localizedDescription)"; throw GameCorpusError.sourceStopped(...) }
   }
   ```
   stopSource(writer, cause:) calls closeWithoutSealing (releasing the lock so `--validate-corpus --fix` can cut the torn tail), sets currentWriter=nil, records the cause and returns the `.sourceStopped` error to throw. If closeWithoutSealing itself fails, that failure is added to the error's text.
 - Add one new enum case: `GameCorpusError.sourceStopped(sourceID:cause:)`.
 - finishSource: set `complete = true` only when stoppedSourceFailure == nil. Otherwise leave it false and write the cause into a new Optional field `CorpusSource.stoppedReason: String?`. This is an additive schema change, consistent with the struct's own doc. nil is omitted by JSONEncoder, so existing corpus.json bytes and tests don't change; the memberwise init gets a nil default, so existing call sites still compile.
 - CorpusRecorder: on the first append error, log one loud line, `[CORPUS] recording stopped: <error>; later self-play games are not recorded (unsealed shard recoverable with --validate-corpus --fix)`. After that, only increment a `droppedAfterStop` counter (no further logging). The finish line reports recorded, dropped and the cause.
 - Add `parentDirectory: URL? = nil` to CorpusRecorder.create, mirroring GameCorpus.create, so tests stay out of Application Support.
 Tests:
 - (a) GameCorpusTests.testRotationFailureStopsTheSourceAndDoesNotMarkItComplete:
   - Setup: shardSoftLimitBytes=1 in a temp dir; beginSource; plant a regular file at `shard-00000.dcmgames` so the seal's rename refuses.
   - append(game0) throws.
   - append(game1) throws `.sourceStopped`. Before the fix it throws `.invalidState("no source…")`, so this fails.
   - After finishSource, corpus.json has `complete == false` and `stoppedReason != nil`. Before the fix it has true, so this fails.
   - The .open shard's lock is free (FileSafety.openExistingRegularFileWithExclusiveLock returns .locked).
 - (b) Partial-write test: hard to inject a partial write without a seam. Either add an internal write-failure seam to ShardWriter or skip this test and rely on (a). I'd skip it and cover the behavior with (a).
 - (c) CorpusRecorderTests.testRecordingStopsOnceAfterRotationFailure (new file): same setup through the recorder. After finishAndSeal, assert the dropped count and that `complete` is false.
 Risks:
 - The PGN importer (PGNImporter.swift:619-623, :142) already stops on the first append error and then calls finishSource. It will now record complete=false and stoppedReason. That is more honest; its tests don't cover that state.
 - Existing rotation tests (CorpusValidatorLiveWriterTests :106/:127) only use rotations that succeed, so they are unaffected.
 - The validator's `sealed-source-incomplete` check now fires correctly for a stopped source if someone later seals the corpus.
 - Single-writer and serial-queue discipline is unchanged.
 - Alternative considered and rejected: retry by opening a fresh shard after a failure. A full disk would just fail again on every game, and the retry hides the failure.

2. persist#8: validator rewrites corpus.json under a live writer during the create-to-lock window — REAL (LOW, S)
 Evidence:
 - FileSafety.swift:435-453 already says that `open(O_CREAT|O_EXCL|O_EXLOCK)` creates the file before taking the lock and that "the other side sees an empty file, which no recovery treats as a shard".
 - recoverOpenShard (GameCorpus.swift:498-521) gets `.locked` on the empty file. Then readToEnd → nil/empty throws `truncatedHeader` (GameCorpus.swift:513, or GameCorpusShard.swift:577).
 - The validator's catch (CorpusValidator.swift:180-187) reports `open-shard-unrecoverable` as an .error and does NOT set writerActive.
 - So `repairCounts` (:291) is true. corpus.json is always stale mid-recording (counts are only written at beginSource/finishSource), so the validator rewrites it (:341-342) from metadata it loaded at :115. If the writer runs finishSource in between, its complete=true and final counts are lost.
 - The creator is blocked in open() while recovery holds the lock, then writes its header normally, so the shard itself is never damaged.
 - The same throw also hits real leftovers: a no-lock volume leaves an empty file behind (FileSafety doc), and so does a crash before the header write. Those are reported as a misleading .error.
 Fix:
 - Add `case headerIncomplete(openShard: URL, byteCount: Int)` to OpenShardRecovery, with a summary. In recoverOpenShard, after reading under the lock, return it when `contents.count < GameCorpusShardFormat.frontHeaderSize`, without throwing and without touching the file.
 - Validator: on this case set writerActive=true (it means a writer may be active). Add a finding with code `open-shard-header-incomplete`, severity = openShardSeverity, fixable false, and the message "shorter than a shard header (N bytes): a writer's shard in the instant before its lock, or a leftover from a writer that died or could not lock; left untouched — if nothing is writing to this corpus remove it by hand and rerun --fix".
 - GameCorpus.recoverOpenShardsIfPresent: throw invalidState for this case.
 - Update the FileSafety doc sentence to name this case.
 - A structural alternative: ShardWriter creates the shard under a FileSafety temporary sibling name with O_EXLOCK, writes the header, then calls `renameWithoutReplacing` to `.open` (the lock survives the rename), so a `.open` name never points at an unlocked live file. It's cleaner but larger and harder to test deterministically. Recommend the minimal fix.
 Test: CorpusValidatorLiveWriterTests.testFixLeavesAShardShorterThanAHeaderAndDoesNotRewriteCorpusJson (new method).
 - Setup: create the corpus, append games, finishSource, then persistMetadata with gamesAdded=0 so the counts are stale. Plant an empty unlocked `shard-00009.dcmgames.open`. Run validate(fix:true).
 - Assert corpus.json bytes are unchanged, the empty file still exists, and both `open-shard-header-incomplete` and `counts-not-repaired-writer-active` are present.
 - Fails before the fix because corpus.json is rewritten.
 Risk: a permanent empty leftover now blocks count repair until it is removed by hand. That's acceptable because the message tells the operator exactly that, and it's the conservative direction. No existing test plants a sub-header `.open` file.

3. persist#5: shard trailer parsed in several places — REAL, and worse than reported (LOW, S)
 - The trailer is encoded once (GameCorpusShard.swift:324-329) but decoded three times: inline in readSealed (:425-431), decodeTrailer (:454-461) and readSealedTrailer (:512-519).
 - The comment at :452-453 ("the trailer layout lives in exactly one place") is false.
 - readSealedCounts (:470-486) has no caller in the app or tests. It is dead code.
 - readSealedCounts :474 and readSealedHeaderAndCounts :533 use `defer { try? handle.close() }`, which breaks the no-`try?` rule.
 - CorpusReplayRunner.swift:1144 relies on readSealedTrailer's SHA matching what readSealed checks, so a drift between the parsers would silently break exact resume.
 Fix:
 - In GameCorpusShardFormat, add `struct Trailer { gameCount, plyCount, sealUnix, sha256: Data }` with `encodeTrailer(_:) -> Data` and `decodeTrailer(_:) throws -> Trailer`, next to the front-header codec.
 - seal, readSealed, readSealedTrailer and readSealedHeaderAndCounts all use it, plus one private `readTrailerBlock(handle:url:)` for the seek-and-read.
 - Delete readSealedCounts.
 - Replace both `try?` closes with the logged close pattern from :498-502.
 - Fix the comment.
 Tests (refactor, so these are pins rather than fail-first):
 - GameCorpusShardTests.testTrailerEncodeDecodeRoundTrip: 64 bytes, fields equal, bad magic throws.
 - GameCorpusShardTests.testCheapTrailerReadsAgreeWithVerifiedRead: readSealedTrailer's SHA equals SHA256 over the file minus its trailer, and the counts match readSealed and readSealedHeaderAndCounts.
 Risk: none to the on-disk format, since the bytes are identical.

4. persist#7: validator severity doc contradicts --fix — REAL (LOW, S, doc only)
 - CorpusValidator.swift:5-6 says `.error` is "Never auto-fixed (fixing would mean … discarding game data)".
 - But at :150 an `.open` shard in a corpus whose state is "sealed" is reported at `.error`. With fix it is recovered and marked `fixed: true` (:162-165), and recovery drops the torn tail or deletes a header-only shard.
 - Fix: reword the doc: "A data/integrity problem. --fix never changes a sealed shard's bytes; the one error it repairs is an unsealed `.open` shard (in a corpus marked sealed), recovered by sealing its complete games and dropping only an incomplete final record."
 - Changing the behavior instead would be wrong, because the recovery is deliberate and documented at :62-75.
 - No test needed for a doc-only fix. Optionally pin with CorpusValidatorOpenShardRecoveryTests.testFixRecoversAnOpenShardInASealedCorpusAsAFixedError.

5. persist#9: GameCorpus.open(directory:) is test-only, and the vanished-shard message is wrong — PARTLY (LOW, S)
 Test-only — REAL:
 - Its own doc (GameCorpus.swift:213-214) says "No app path opens an existing corpus for writing today".
 - grep finds callers only in tests: GameCorpusTests:47/87/112, GameCorpusReadOnlyOpenTests:117, PGNImporterTests:96 and CorpusValidatorLiveWriterTests:152.
 - Removing it would mean editing six tests, which needs owner approval.
 - Recommendation: keep it (it works, it isn't a stub, and it shares recoverOpenShard) and put the call to the owner. PGNImporterTests:96 could use openReadOnly in any case.
 Message — PARTLY:
 - recoverOpenShardsIfPresent (:465-468) gives `.inUseByLiveWriter` and `.vanishedBeforeRecovery` the same text, "belongs to a writer still running on this corpus".
 - A vanished shard could also have been sealed or removed by a concurrent `--validate-corpus --fix` in another process, with no writer involved. The `.vanishedBeforeRecovery` summary (:119-120, "most likely its writer sealed it") has the same blind spot.
 - The refusal itself is correct, because something else is touching the corpus.
 - Fix: split the two cases. For in-use: "is held by a writer still running on this corpus; a corpus has one writer at a time". For vanished: "disappeared while the corpus was being opened (sealed or discarded by its writer, or recovered by another --validate-corpus --fix); something else is using this corpus". Use the same wording in `summary`.
 - Test: optional and low value, since a deterministic vanish needs a race. The message change alone doesn't justify a test seam.
