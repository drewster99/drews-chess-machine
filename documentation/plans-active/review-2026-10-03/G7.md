## Analysis (analyzer, full)

G7 analysis (GUI lineage lifecycle): both items are PARTLY real. The finders overstated how each one surfaces.
SUMMARY: app#6 is real as a state inconsistency. ensureChampionBuilt drops the trainer but keeps lineageTracker, while buildNetwork clears it. The "later start aborts / false continuity" outcome cannot happen, though: the rebuild also nils replayBuffer, so the next start always takes .freshOrFromLoadedSession, and that mode always makes a new tracker. Where it does show up is Save Champion, after a demo trainer (Train Once / Continuous Training / Sweep) has re-created `trainer`. app#7 is real: a lineage-start failure consumes pendingLoadedSession. But the next start does not reset the trainer by default. The 3-way dialog appears; "Continue" keeps the restored weights but permanently loses the session's lineage (it is re-recorded as unrecorded history). Only "reset from champion" loses the trainer state, and then only in memory: the files on disk are untouched. Both fixes are small (S).

1. app#6. Verdict: PARTLY.
 Evidence:
 - SessionController.swift:1159: ensureChampionBuilt calls onDropTrainer() and onClearTrainingDisplay(). It does NOT reset lineageTracker or lineageFedCarry.
 - buildNetwork does reset both at :1097-1100, with the comment "The dropped trainer's lineage segment ends with it". So the two rebuild paths disagree.
 - Why no later start sees the stale tracker:
   - clearTrainingDisplay (UpperContentView.swift:1987) sets replayBuffer = nil.
   - hasResumableInMemorySession is `pendingLoadedSession == nil && replayBuffer != nil` (UpperContentView:2762), so the Continue / KeepTrainer dialog cannot appear.
   - The start is therefore .freshOrFromLoadedSession. beginLineageSegment (SessionController+Lineage.swift:99-122) always builds a new tracker there: championLineageStart, or .resume from the loaded session.
   - So "negativeSegmentCount abort / false continuity at start" is NOT reachable.
 - Where it IS reachable: lineageRecordForChampionSave (Lineage.swift:297) takes the tracker path whenever `lineageTracker != nil, let trainer`. Sequence:
   1. Train, then Stop.
   2. Load Model or Load Session of a different architecture: rebuild, trainer dropped, tracker kept.
   3. Train Once / Continuous Training / Sweep: ensureTrainer (SessionController.swift:912, 940; +Sweep.swift:17) builds a new trainer with completedTrainSteps 0 or a few.
   4. Save Champion (+Checkpoint.swift:97).
 - The outcome of that Save Champion:
   - If the old segment started from a resume (segmentStartTrainerStep > 0): segmentLocalStep is negative, LineageTracker.swift:230 throws, and the save fails with "Save failed (lineage): lineage: segment steps is negative (-N)".
   - If the old segment started at step 0 (any fresh or branch run): the newly loaded champion is saved stamped with the OLD run's lineage_run_id, parent, cum totals and segments. That is silent false provenance in a permanent file.
   - championOrigin, which is correct here, is ignored.
 - About `onDropTrainer` itself: it is a leftover indirection. The trainer already lives on SessionController (SessionController.swift:247; UpperContentView:371 just proxies it). Its doc at :355-356 says "until the trainer migrates here", and the trainer has migrated. In XCTest the closure defaults to a no-op, so a test controller never drops its trainer.
 - About the ensureTrainer comment (SessionController.swift:999-1003): "every Play-and-Train start replaces these weights (a reset + load)". It is imprecise but not wrong in any state you can reach today. .continueAfterStop and .newSessionKeepTrainer do not replace the weights (+Training.swift:1047). They just cannot follow a trainer build, because every path that builds a trainer has nil'd replayBuffer. The comment depends on that invariant without saying so.
 Fix:
 - Add SessionController.dropTrainerEndingLineageSegment() with one doc comment: "The trainer's lineage segment ends with the trainer: a later save must not attribute another trainer's (or the champion's) weights to it". Body:
   - trainer = nil
   - lineageTracker = nil
   - lineageFedCarry = LineageFedCarry()
 - Call it from buildNetwork (replacing :1097-1101) and from ensureChampionBuilt (replacing :1159).
 - Delete the `onDropTrainer` property (:355-357) and its wiring (UpperContentView.swift:1819). This leaves one source of truth for "trainer gone ⇒ segment gone".
 - Reword the comment at :999-1003, e.g. "A trainer is built only when none exists — at first use, or after a build/rebuild dropped it, which also cleared the replay buffer and with it the keep-trainer start modes — so the next Play-and-Train start resets and loads these weights."
 - Do not touch the same-architecture Load Model path, which keeps both trainer and tracker. Stamping the champion with the trainer's lineage on that path is app#5 / persist#3, in another group.
 Regression test (new file GuiLineageLifecycleTests.swift, @MainActor):
 - testRebuildingTheChampionForAnotherArchitectureEndsTheTrainersLineageSegment:
   - Setup: `let c = SessionController()`. Set c.lineageTracker to a LineageTracker(start: .resume(parent: recorded via LineageRecord.forTests(trainerCompletedSteps: 50…)), pathKind: .gui, …, segmentStartTrainerStep: 50). Leave network nil.
   - Rebuild: `_ = await c.ensureChampionBuilt(arch: <small preset>)`.
   - Assert c.lineageTracker == nil and c.trainer == nil.
   - Then set c.championOrigin = .built(ModelInitRecord(...)) and call _ = c.ensureTrainer().
   - `let r = try c.lineageRecordForChampionSave(at: Date())`. Assert r.run.start == .fresh and r.segments is empty.
   - Before the fix this fails twice over. The tracker survives the rebuild. lineageRecordForChampionSave then throws negativeSegmentCount(steps, -50), because the new trainer is at step 0 against the old segment's start of 50.
 - Second case: the same test through buildNetwork is already correct, so the test is not needed there; optional.
 Risks:
 - Removing onDropTrainer is a compile-checked change and has no other users (grep shows only :1097, :1159, :1819).
 - No existing test references it.
 - No persistence format changes.
 Severity: LOW. It needs a long manual sequence, but one branch writes false lineage into a model file. Effort: S.

2. app#7. Verdict: PARTLY.
 Evidence:
 - +Training.swift:1278-1300: inside the lineageStart MainActor.run block, `pendingLoadedSession = nil`, `pendingLoadedSessionAcceptedReplacements = []` and `championLoadedSinceLastTrainingSegment = false` run unconditionally, even when segmentResult is .failure.
 - The failure branch (:1304-1316) logs, sets status, sets realTraining=false and returns. It does not tear down.
 - By that point the run has already:
   - restoreExactly'd the session trainer state (:1049-1086);
   - set replayBuffer (:347) and restored its contents (:1189-1206);
   - set runRandomSeed and selfPlayGameSerials (:302-308);
   - seeded trainingBox.
 - Next Play and Train: pendingLoadedSession is nil and replayBuffer is non-nil, so hasResumableInMemorySession is true and the 3-way dialog shows. It is NOT an automatic trainer reset:
   - "Continue" (continueAfterStop) keeps the restored weights. If lineageTracker was not set, beginLineageSegment takes the "continuing a trainer with no tracked lineage" path (Lineage.swift:79-94). That path is .resume with an `.unrecorded` parent and gaps rngSampler/serials/buffer/clocks. So the session's lineage_run_id, segment index, cum totals and derivation history are lost permanently for every later save, continues_unrecorded_history=true, and the real parent file is lost.
   - "New session — trainer reset" discards the restored trainer from memory.
   - Reloading the session from disk recovers everything, because no file is touched.
 - It is also inconsistent with the sibling early-failure returns in the same Task, e.g. tactical probe init (:1001-1007) and "Networks missing after setup". Those happen before the consume, so they leave the pending session intact.
 - A second facet: beginLineageSegment is not atomic. It assigns `lineageTracker = try LineageTracker(...)` and resets lineageFedCarry (Lineage.swift:125-129), then can still throw at `guard runRandomSeed` (:134) or in lineageRecordForSave (:136). A failure there leaves a half-begun tracker, which Save Champion (Lineage.swift:297) would then use. checkpoint?.runResumeExactness may also already be set (:106).
 - What actually triggers a failure today:
   - BehaviorFingerprint.compute failing (GPU work, :1268-1273);
   - parameter-snapshot encoding failing;
   - LineageTracker.legacyTotalsWithRecordedLineage: session.json has no lineage but the trainer file does;
   - internal guards.
   These are rare.
 Fix:
 - (a) In the lineageStart block, move the three consumption lines into the success branch only. After a failure, the next Play and Train then sees pendingLoadedSession != nil, takes .freshOrFromLoadedSession, and redoes the whole resume from the still in-memory LoadedSession. That means resetNetwork + restoreExactly, a new ReplayBuffer re-restored from replayBufferURL, the seed re-inherited from the streams, and a new tracker. All of that is idempotent: SessionParameterResume re-applies the same saved values, and the [RESUME-DIFF] "current=" will just show them already applied. The menu label stays "Continue Training" (pendingLoadedSessionExists), which is now accurate.
 - For testability, extract the lineage part of that block into `func beginRunLineage(mode:trainer:fingerprintResult:) -> Result<LineageTracker, Error>` on SessionController (+Training or +Lineage). It does the trainer.identifier switch, then beginLineageSegment, and consumes the pending load only on .success. The MainActor.run closure calls it.
 - (b) Make beginLineageSegment atomic:
   - At entry, capture `let previous = (lineageTracker, lineageFedCarry, checkpoint?.runResumeExactness)`.
   - Wrap the body in `do { … } catch { lineageTracker = previous.0; lineageFedCarry = previous.1; checkpoint?.runResumeExactness = previous.2; throw error }`.
   - This also protects .continueAfterStop: a failed [RUN] record no longer leaves a replaced or reset carry.
 - Adjacent, out of scope, flag only: none of the Task's early-failure returns run the normal teardown (+Training.swift:2757-2788). That leaves parallelWorkerStatsBox and checkpoint currentSessionID set and the active training segment open; the next start closes the segment as "restart-without-stop". That should be a separate shared "abortStart" helper.
 Regression tests (new file, same GuiLineageLifecycleTests.swift; its LoadedSession builder replicates GuiResumeGapsTests' private helpers, since that file may not be edited without approval):
 - testALineageStartFailureKeepsThePendingSessionForTheNextStart:
   - Setup: c.pendingLoadedSession = loaded; c.pendingLoadedSessionAcceptedReplacements = ["x"]; build a trainer via c.ensureTrainer().
   - Call `c.beginRunLineage(mode: .freshOrFromLoadedSession, trainer:, fingerprintResult: .failure(TestError()))`.
   - Assert .failure, c.pendingLoadedSession != nil, accepted replacements == ["x"], and c.lineageTracker == nil.
   - Fails before the fix because the session is consumed.
 - testAFailedLineageSegmentStartLeavesTheRunningSegmentUnchanged:
   - Setup: c.lineageTracker = trackerA; c.lineageFedCarry = carry with games 7; c.championOrigin = .built(...); c.runRandomSeed = nil (forces noRunSeed after the tracker is built).
   - Call `try c.beginLineageSegment(mode: .newSessionResetTrainerFromChampion, trainer:, resumed: nil, behaviorFingerprint: .init(recipe: BehaviorFingerprint.recipe, sha256: "ab"))`.
   - XCTAssertThrows, then assert c.lineageTracker === trackerA and c.lineageFedCarry == carry.
   - Fails before the fix because the tracker is replaced by a half-begun one and the carry is reset.
 - Success-path sanity: with a fingerprint .success and runRandomSeed set, the pending session is consumed and the tracker is set.
 Risks:
 - Keeping the pending session means a user who wanted the in-memory Continue now gets a full re-resume instead. That is correct: it is the session they loaded, and they never actually trained.
 - A failure that is deterministic, e.g. legacyTotalsWithRecordedLineage, will fail again on every start, each time with a visible error. That is better than silently degrading the lineage. The user can still Load Model or Load Session to move on.
 - No persistence-format change and no existing tests touched.
 Severity: LOW–MEDIUM. The trigger is rare, but "Continue" silently, permanently and irrecoverably downgrades the run's lineage in every later save. Effort: S.
