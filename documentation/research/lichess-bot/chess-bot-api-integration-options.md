# Lichess opens the door; everyone else keeps it shut

A custom UCI engine like DrewsChessMachine has exactly one mainstream, officially sanctioned path onto the open internet to play real opponents while a human watches: **Lichess's Bot API**, a token-authenticated REST + NDJSON-streaming interface that any engine speaking UCI over stdin/stdout can be bridged into, most commonly via the community-standard Python bridge `lichess-bot` ([lichess-bot GitHub](https://github.com/lichess-bot-devs/lichess-bot)). The integration itself is straightforward — mint a scoped OAuth token, upgrade a brand-new account to BOT status, and drive two layers of NDJSON streams — but the account-level commitment is absolute: the BOT upgrade is explicitly irreversible and requires an account that has never played a single game, permanently forfeiting normal lobby/pool play on that identity ([lichess-org/api spec](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-account-upgrade.yaml)). Concurrency is generous (unlimited human-vs-bot games, capped only at 100/day for bot-vs-bot pairs) but every other major platform is closed: Chess.com is read-only-only and explicitly bars external engines from live play, and FICS/ICC offer only legacy or nonexistent bot-play channels ([Chess.com PubAPI docs](https://www.chess.com/news/view/published-data-api)). Lichess also turns out to be a genuinely low-maintenance target for building a durable spectator-facing archive: it persists a full PGN-equivalent record — moves, clocks, termination reason, opponent identity and rating — retrievable after any game via its export API, but it retains essentially nothing about the *plumbing* (disconnects, 429s, stream drops), which is squarely the bridge's job to log in real time.

## Getting a bot connected: tokens, streams, and the reference bridge

Authentication for a Lichess bot uses a simple personal OAuth2 access token, not a full three-legged authorization flow — appropriate since the bot operator and account owner are the same person. Tokens are minted at `https://lichess.org/account/oauth/token/create`, shown to the user exactly once, and scoped to `bot:play`, which the UI labels "Play with the Bot API. Only for Bot accounts" ([lichess-api.yaml scope list](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml); [token-creation wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/How-to-create-a-Lichess-OAuth-token)). The full endpoint surface was verified directly against the primary-source OpenAPI YAML (not the JS-rendered Swagger page, which returns only shell HTML to non-browser fetchers) at `raw.githubusercontent.com/lichess-org/api/master/doc/specs/` ([lichess-api.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml)). The architecture has two layers of persistent NDJSON connections plus short-lived POSTs: an account-level event stream at `GET /api/stream/event` delivers `gameStart`, `gameFinish`, `challenge`, `challengeCanceled`, and `challengeDeclined` events (with an empty keep-alive line sent every 7 seconds, and only one such stream permitted per token — opening a new one silently closes the old) ([api-stream-event.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/board/api-stream-event.yaml)); a per-game stream at `GET /api/bot/game/stream/{gameId}` opens once a challenge is accepted, delivering a single initial `gameFull` message followed by incremental `gameState`, `chatLine`, and `opponentGone` messages ([api-bot-game-stream-gameId.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-game-stream-gameId.yaml)); and the bot pushes its moves back via `POST /api/bot/game/{gameId}/move/{move}` using plain UCI notation (e.g. `e2e4`), with an optional `offeringDraw` flag ([api-bot-game-gameId-move-move.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-game-gameId-move-move.yaml)). Sibling endpoints round out game management: `POST /api/bot/game/{gameId}/resign`, `/abort`, `/chat` (plus `GET .../chat` to read messages), `/draw/{accept}`, `/takeback/{accept}`, `/claim-victory`, and `/claim-draw`, all scoped to `bot:play` ([tags/bot/ endpoint files, e.g. api-bot-game-gameId-resign.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-game-gameId-resign.yaml), [api-bot-game-gameId-chat.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-game-gameId-chat.yaml), [api-bot-game-gameId-draw-accept.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-game-gameId-draw-accept.yaml), [api-bot-game-gameId-takeback-accept.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-game-gameId-takeback-accept.yaml), [api-bot-game-gameId-claim-victory.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-game-gameId-claim-victory.yaml)). Challenges are accepted or declined through the shared Challenge API — `POST /api/challenge/{challengeId}/accept` and `/decline`, the latter taking a structured `reason` enum (`generic, later, tooFast, tooSlow, timeControl, rated, casual, standard, variant, noBot, onlyBot`) — and notably these two endpoints, plus the event stream, accept *any one* of `challenge:read`/`challenge:write`, `bot:play`, or `board:play`, meaning the Bot-vs-Board distinction lives entirely in the `/api/bot/game/...` vs `/api/board/game/...` move-management endpoints rather than in challenge/event handling ([api-challenge-challengeId-accept.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/challenges/api-challenge-challengeId-accept.yaml), [api-challenge-challengeId-decline.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/challenges/api-challenge-challengeId-decline.yaml)). A no-auth `GET /api/bot/online` endpoint lists currently online bots ([api-bot-online.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-online.yaml)).

The community-standard bridge for wiring a UCI engine into this API is `lichess-bot` (`github.com/lichess-bot-devs/lichess-bot`), a Python project that spawns the engine as a subprocess and speaks UCI (or XBoard/CECP, or hand-rolled "Homemade" logic) over its stdin/stdout via `python-chess`'s engine layer ([lichess-bot README](https://github.com/lichess-bot-devs/lichess-bot)). It is configured entirely through a `config.yml`, requires Python 3.10+, runs on Windows/Linux/macOS/Docker, and bundles matchmaking, tournament participation, draw/takeback handling, PGN game logging, and opening-book/tablebase support out of the box ([lichess-bot README](https://github.com/lichess-bot-devs/lichess-bot); [config.yml.default](https://github.com/lichess-bot-devs/lichess-bot/blob/master/config.yml.default)). No Swift-native bridge exists anywhere in the ecosystem — the alternatives found were all Python (`asyncLio-bot`, an async/await variant; the older `lichess-uci-bot`) or a Rust API client (`litchee`) that covers the general endpoint surface but isn't purpose-built as an engine bridge ([asyncLio-bot](https://github.com/Heiaha/asyncLio-bot); [ornicar/lichess-uci-bot](https://github.com/ornicar/lichess-uci-bot); [obazin/litchee](https://github.com/obazin/litchee)). Because DrewsChessMachine already exposes a `--uci` mode over stdin/stdout, the lowest-risk integration path is running that mode as a subprocess under the existing, actively-maintained `lichess-bot` — evidenced by live GitHub Actions CI (Python Build/Test/Mypy) and ongoing issue/PR activity as of this research (September 2026) — rather than writing a bespoke Swift networking layer that would have to reimplement every edge case below ([lichess-bot GitHub activity](https://github.com/lichess-bot-devs/lichess-bot)).

Long-running unattended operation surfaces a specific, well-documented failure class: stream termination is an *ambiguous* signal. `lichess-bot` has an open issue where the per-game stream ending (`StopIteration`) is treated unconditionally as "game over," even when it was actually a network blip or a server-side connection close — the bot then abandons an in-progress game and flags on time ([Issue #1184](https://github.com/lichess-bot-devs/lichess-bot/issues/1184)). A related restart-time bug means that after the bot process restarts while several games are running, "not all games are picked up again," again risking timeouts on the orphaned games ([Issue #1101](https://github.com/lichess-bot-devs/lichess-bot/issues/1101)). A separate report describes ISP-driven client IP rotation silently breaking the long-lived stream connections without the server noticing the disconnect ([careless25/lichess-bot Issue #135](https://github.com/careless25/lichess-bot/issues/135)). Lichess's own NDJSON convention compounds this: both streams send blank keep-alive lines (every 7 seconds on the event stream, per the spec) that a correct client must skip rather than misread as data or as an end-of-stream signal ([api-stream-event.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/board/api-stream-event.yaml)). The engineering lesson generalizes beyond the reference bridge: any bot client, Python or Swift, needs to distinguish "stream ended because the server sent a genuinely terminal game state" from "the TCP/HTTP connection just died," reconcile its in-memory game list against Lichess's authoritative state on every restart, and apply an idle/heartbeat timeout independent of what the OS reports about the socket.

## The BOT account is a one-way door

Both the primary-source OpenAPI spec and the `lichess-bot` wiki state the upgrade rule in nearly identical, unambiguous language. The `POST /api/bot/account/upgrade` operation description reads, verbatim: "Upgrade a lichess player account into a Bot account. Only Bot accounts can use the Bot API. The account **cannot have played any game** before becoming a Bot account. The upgrade is **irreversible**. The account will only be able to play as a Bot" ([api-bot-account-upgrade.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/tags/bot/api-bot-account-upgrade.yaml)). The bridge's own wiki echoes this with "WARNING: This is irreversible" on its upgrade walkthrough page, which instructs running `python3 lichess-bot.py -u` to perform the conversion, after which the account begins playing automatically ([Upgrade-to-a-BOT-account wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/Upgrade-to-a-BOT-account)). No source anywhere — official docs, the wiki, or community forums — describes a downgrade path, a support-ticket exception, or any mechanism to revert a BOT account to normal human play; forum thread titles like "How to make a bot not a bot?" exist precisely because users have asked and found no answer, which combined with the absolute framing of "irreversible" in the primary source should be read as "not possible," not merely "undocumented" ([How to make a bot not a bot? — Lichess forum](https://lichess.org/forum/lichess-feedback/how-to-make-a-bot-not-a-bot)). Practically, this means the only safe procedure is: register a brand-new account, verify its email, and upgrade it to BOT status *before* ever touching the normal lobby, pool, or a single rated/casual game — any prior game history on the account, even one, blocks the upgrade outright, per the spec's "cannot have played any game" clause. Once upgraded, the account loses standard lobby/pool matchmaking entirely; all games must originate via Bot API challenges, described in the reference bridge's own purpose statement as the reason the bridge exists in the first place — bot accounts do not play through the ordinary web lobby UI at all ([lichess-bot GitHub](https://github.com/lichess-bot-devs/lichess-bot)).

Because a Lichess account is a strict one-to-one mapping of account, username, email, and BOT identity, there is no way to host multiple differently-branded bot personalities under a single account or token. Lichess enforces one distinct email address per account ([Lichess forum on multi-account email rules](https://lichess.org/forum/general-chess-discussion/can-we-create-multiple-accounts-with-same-email)), and its Terms of Service treat multiple accounts as a discretionary exception rather than a right: "creating an excessive number of accounts (typically any more than three) will generally not be allowed, regardless of reasons," with untitled players permitted a second account only for narrow, stated purposes like hiding opening preparation ([Lichess Terms of Service](https://lichess.org/terms-of-service)). No source specifically addresses whether clearly-labeled engine bots get more leeway under this policy than ordinary duplicate human accounts — that remains an open question worth a direct support confirmation before scaling to multiple branded identities, but the baseline rule is unambiguous: each additional bot personality needs its own account, its own unique email, and its own independently-upgraded BOT status and token.

## Concurrency is generous for humans, capped hard for bot-vs-bot

A single Lichess bot account can play many games at once, and there is no Lichess-side numeric ceiling on how many *human*-vs-bot games it may run concurrently — concurrency is purely a client-side policy choice, exposed in `lichess-bot`'s config as `concurrency: 1  # Number of games to play simultaneously`, alongside knobs like `games_reserved_for_humans` and `max_simultaneous_games_per_user: 5` that let the operator shape how slots are allocated ([config.yml.default](https://github.com/lichess-bot-devs/lichess-bot/blob/master/config.yml.default)). The one hard, documented platform-level cap is specifically aimed at automated bot-vs-bot pairings: a `lichess-org/lila` commit introduced a `BotLimit` class that rejects further challenges once a bot-vs-bot pairing hits **100 games per day**, with the commit message explaining the motivation plainly — "limit to 100 bot-vs-bot games per day to reduce game farming using lichess-bot automated matchmaking. We have millions of games piling up that no-one cares about" ([lichess-org/lila commit eeefdcf](https://github.com/lichess-org/lila/commit/eeefdcf48bc2b8b2a740b2254a8e4c589ff10802)). For a project like DrewsChessMachine, where the goal is to be watched playing real people, the practical concurrency ceiling will be set by how many games the engine process can itself serve at acceptable per-move latency, not by any Lichess account-level limit.

Challenge acceptance and matchmaking logic lives entirely on the client side — Lichess exposes only the raw challenge stream and accept/decline endpoints, with all filtering and opponent-selection policy left to the bot operator's software. `lichess-bot`'s config demonstrates the breadth of what a bridge typically implements: accept/reject toggles for bot-originated challenges (`accept_bot`, `only_bot`), allow-lists for variants (standard, chess960, atomic, crazyhouse, etc.), time controls (bullet through correspondence), and rated-vs-casual mode, plus a `max_takebacks_accepted` cap, and a dedicated `matchmaking` block that lets the bot proactively *seek* opponents by rating range, time control, and variant rather than only reacting to inbound challenges ([config.yml.default](https://github.com/lichess-bot-devs/lichess-bot/blob/master/config.yml.default)).

Beyond the 100/day bot-vs-bot rule and the ordinary API-wide rate limiting (discussed below), bots face a specific, longstanding set of platform restrictions. They are excluded from Arena and Swiss tournaments — confirmed by two still-open, multi-year `lichess-org/lila` feature requests asking Lichess to relax this for bot-only or private tournaments, which as of this research had not shipped ([Issue #7580](https://github.com/lichess-org/lila/issues/7580); [Issue #16960](https://github.com/lichess-org/lila/issues/16960)). Bots cannot post in the Lichess forums, lack a dedicated own-rating leaderboard, and have been explicitly barred from UltraBullet since August 2020 for a stated technical reason: "When playing ultrabullet, bots send too many requests to the server — it is often hard for the server to handle" ([Lichess forum synthesis on the ultrabullet ban](https://lichess.org/forum/lichess-feedback/why-arent-bots-allowed-to-play-ultrabullet)). Correspondence time control is unsupported too, though for a client-limitation reason rather than an explicit policy ban — bot profiles on the official directory self-describe as able to "play any variant and time control other than ultrabullet (not allowed for bots) and correspondence (not supported by the client)" ([Lichess online bots directory](https://lichess.org/player/bots)). That leaves bullet, blitz, rapid, and classical direct challenges — bot-vs-human unconstrained, bot-vs-bot capped at 100/day per pairing — as the available surface for real, watchable games.

On rate limiting generally, Lichess deliberately does not publish per-endpoint numeric quotas. The OpenAPI spec's global guidance states verbatim: "All requests are rate limited using various strategies... Only make one request at a time. If you receive an HTTP response with a 429 status, you have exceded one of the rate limits. In most cases, waiting one minute before retrying will be sufficient, but some limits may require longer" ([lichess-api.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml); consistent wording independently confirmed on the human-readable [API Tips page](https://lichess.org/page/api-tips)). Lichess does return a `Retry-After` header on 429s, but a cited cautionary example shows a third-party client that ignored it and retried on a fixed schedule instead, risking account restriction ([GitHub issue on a third-party fetcher](https://github.com/obajecollinsmicheal-cmd/smile4money/issues/1712)); community reports also describe real users hitting 429s unpredictably — one after roughly 4,000–5,000 requests over about two hours — underscoring that the effective limit is load-dependent and not a number to engineer against precisely ([Lichess Feedback forum thread](https://lichess.org/forum/lichess-feedback/lichess-api-returning-me-a-429-too-many-requests-despite-waiting-over-a-minute)). A separately-documented, if unconfirmed-for-the-bot-endpoint-specifically, streaming ceiling of "maximum 8 concurrent game streams per IP address" was found for the sibling spectator/export stream endpoint, and should be treated as indicative rather than verified for `/api/bot/game/stream/{gameId}` until tested directly ([DeepWiki Game Export and Streaming](https://deepwiki.com/lichess-org/api/5.3-game-export-and-streaming)). No source requires artificial move-timing delays to "seem human" — that is left entirely to operator discretion, not a platform rule.

## Every other major platform is closed, legacy, or first-party-only

Chess.com's only public interface is the read-only Published-Data API (PubAPI, base `https://api.chess.com/pub/`), whose own announcement states flatly: "This is read-only data. You cannot send game-moves or other commands to Chess.com from this system" ([Chess.com Published-Data API announcement](https://www.chess.com/news/view/published-data-api)). A staff member confirmed in an October 2018 forum thread that an internal "Interactive API" exists (the same channel Chess.com's own apps use) but "is still well in the future" for third parties and would require a developer application process — and as of the most recent evidence found (a November 2024 reply in the same thread), it has never shipped ([Interactive API release — Chess.com forum](https://www.chess.com/clubs/forum/view/interactive-api-release)). Site rules independently forbid engine assistance against real human opponents; the only "bot" opponents on Chess.com are first-party personalities (Martin, Mittens, etc.), not a slot external engines can occupy ([Mittens (chess) — Wikipedia](https://en.wikipedia.org/wiki/Mittens_(chess))). Chess.com staff, asked directly where to run an engine bot instead, answered: "the two sites I'm aware of that support bot accounts are lichess and FICS" ([Interactive API release — Chess.com forum](https://www.chess.com/clubs/forum/view/interactive-api-release)).

FICS (freechess.org) remains operational in 2026, self-describing as one of the oldest and largest internet chess servers with over 300,000 registered users ([freechess.org](https://www.freechess.org/)), and unlike Chess.com it has a genuine, if dated, path for engines: WinBoard/XBoard (and other legacy clients like Babaschess and Raptor) act as protocol adapters between a UCI/XBoard-speaking engine and the plain-text Internet Chess Server (ICS) protocol, typically fronted by the Timeseal lag-compensation helper, with community-maintained UCI-to-FICS bridge scripts also available ([FICS Interface comparison](https://www.ficsgames.org/interfaces); [GitHub: raschu/UCI-FICS-bot](https://github.com/raschu/UCI-FICS-bot)). This is tooling from the ICS era, not a modern REST/NDJSON developer API, and its currency (whether FICS still officially labels and segregates "computer accounts" today) could not be confirmed from any 2025/2026-dated source. ICC (chessclub.com) is also active — it relaunched in 2024 with a modern browser client and mobile apps ([About ICC](https://www.chessclub.com/about)) — but no public developer API or engine-bot protocol was found for it at all; its bot-adjacent features (TrainingBot, "Featured Bot of the Week") are first-party curated content, not an integration point ([TRAININGBOT](https://www.chessclub.com/help/TrainingBot)). Engine-vs-engine rating circuits like TCEC and CEGT are a different category entirely — they connect engines to each other through local UCI tournament-manager software such as Cutechess, not a networked API for playing human opponents, and don't substitute for "watch it play real people online" ([Top Chess Engine Championship — Wikipedia](https://en.wikipedia.org/wiki/Top_Chess_Engine_Championship)). No evidence was found of any modern open-protocol successor to the Lichess Bot API, nor of a public bot-play API on chess24. Lichess is, in short, essentially unique among major platforms in offering this capability at all.

## Lichess remembers the game; only the bridge remembers the plumbing

Lichess persists every finished game server-side and exposes a comprehensive, structured record afterward, meaning a bot bridge does not need to reconstruct move/clock/result history itself — it can always pull it back later. `GET /game/export/{gameId}` returns PGN or JSON (content-negotiated) with opt-in boolean flags including `moves`, `pgnInJson`, `tags`, `clocks`, `opening`, `evals`, and `accuracy`; the bulk equivalent, `GET /api/games/user/{username}`, streams the same fields as NDJSON with filters for date range, opponent, rating status, and performance type ([Lichess API DeepWiki summary](https://deepwiki.com/lichess-org/api/5.3-game-export-and-streaming)). Because `clocks`, `opening`, `evals`, and `accuracy` are opt-in rather than default-on, a reconciliation job that wants the full picture must explicitly request them — a historical Lichess forum complaint about missing clock data in exported PGNs is consistent with this default-off behavior ([Lichess forum thread](https://lichess.org/forum/lichess-feedback/export-games-does-not-have-clock-information-in-pgn-files?page=2)). Internally, `lila` stores the move list as SAN strings and clock histories via a compact quantized binary encoding, and builds a full PGN tag set — event, site, date, round, result, and termination reason — from that record ([Game Persistence & Export DeepWiki](https://deepwiki.com/lichess-org/lila/4.4-game-persistence-and-export)). The game-end reason itself surfaces as a structured `status` field (values including `mate`, `resign`, `stalemate`, `timeout`, `draw`, `outoftime`, `aborted`, `noStart`, `cheat`, `variantEnd`, `unknownFinish`) present on both the export payload and the live `gameFull`/`gameState` stream messages — though a documented gap means the *live* stream does not always reliably deliver a final `gameState` for resignation endings specifically (an issue filed and closed as "not planned"), so a bridge that needs same-second certainty about a resignation must fall back to calling the export endpoint after the stream ends rather than trusting the live signal alone ([Issue #60, lichess-org/api](https://github.com/lichess-org/api/issues/60)). Opponent identity — username and rating — is a standard, reliable field on every export's `players` object; whether the opponent was itself a bot is best determined from the account-level `title: "BOT"` field (bot accounts can earn even higher titles like BOTCM/BOTNM/BOTFM after 500+ rated games at sufficient rating) rather than a dedicated per-game "is-bot" flag, which was not independently confirmed to exist in the export schema itself ([BOT Title — lichess.org](https://lichess.org/team/bot-title)).

What Lichess does *not* retain, and has no mechanism to hand back later, is anything at the protocol/transport layer. Two open `lichess-org/lila` issues document that even the *live* signal for opponent presence is unreliable: one requests an "opponentGone" event because a reconnecting client currently has no way to tell whether its opponent is present or absent mid-game, and a related issue reports that once a `gone:true` presence flag arrives, the client may never receive the corresponding `gone:false` when the opponent returns ([Issue #18664](https://github.com/lichess-org/lila/issues/18664); Issue #18665, per research-note synthesis). There is no endpoint to query past 429 events, illegal-move rejections, or stream disconnect timestamps after the fact — the API Tips guidance describes only how to *avoid* 429s in the moment, with no retrieval mechanism for a client wanting to audit "was I rate-limited last Tuesday" ([API Tips](https://lichess.org/page/api-tips)). This is the one category of data where the answer is unambiguous: if the bridge doesn't log it live, it's gone permanently. Notably, even the reference bridge itself doesn't rely on Lichess's archive for its own operational record — `lichess-bot` ships a `--logfile` option for full run logs and a `pgn_directory` config that writes a local PGN of every game as it's played, with optional `[%eval s,d]` engine-evaluation annotations that Lichess has no way to know about at all since they're the bot's own internal search output, never submitted to the server ([config.yml.default](https://github.com/lichess-bot-devs/lichess-bot/blob/master/config.yml.default); [Configure lichess-bot wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/Configure-lichess-bot)). The clean division of responsibility, then, is: treat Lichess's export API as the authoritative source for the canonical move list, clocks, and result once a game is finished, and treat local, real-time logging as the only source of truth for connection health, HTTP error codes, and anything about the engine's own internal state during play.

## Conclusion

The research converges on a single, low-ambiguity architectural fact: Lichess is not merely the *best* option for making a home-built engine watchable against real opponents — for a solo Swift-based project without an existing partnership channel, it is the *only* option among mainstream platforms, since Chess.com forbids the use case outright and FICS/ICC offer nothing comparable to a modern, documented, actively-maintained bridge ecosystem. The one decision point genuinely worth deliberate care before writing any code is upstream of the API entirely: which brand-new, never-played, uniquely-emailed account becomes the permanent BOT identity, since that choice cannot be undone and cannot be shared with any account used for ordinary human play. Everything downstream of that decision — the streaming architecture, the concurrency model, the rate-limit posture, and the reconciliation-after-the-fact pattern for game records — is well-trodden ground with a hardened reference implementation (`lichess-bot`) whose known failure modes (ambiguous stream termination, restart-time game-tracking gaps) are documented well enough to design around rather than discover the hard way during a live, spectated game.

## Deeper dig: operational pain points, configurability, and alternatives (2026-09-28 update)

A follow-up research pass dug specifically into real operator experience (GitHub issues across `lichess-org/lila`, `lichess-org/api`, `lichess-bot-devs/lichess-bot` and forks, plus the Lichess Feedback forum) and a full enumeration of `lichess-bot`'s tunable surface, verified against `config.yml.default`, `lib/lichess_bot.py`, and `lib/engine_wrapper.py` source. Full detail and citations: `notes/lichess_bot_pain_points_config_and_alternatives.md`.

**Snags and red flags, ranked by relevance to DCM.** The dominant real-world failure class remains stream-drop mishandling, now with more depth: beyond the previously-found "stream ending treated as game-over" bug ([Issue #1184](https://github.com/lichess-bot-devs/lichess-bot/issues/1184)) and the restart-time game-tracking gap ([Issue #1101](https://github.com/lichess-bot-devs/lichess-bot/issues/1101)), there's a still-open outright *crash* on timeout/reconnect with no built-in self-healing ([Issue #1120](https://github.com/lichess-bot-devs/lichess-bot/issues/1120)), and a multi-week-uptime report of accumulating connection timeouts unrelated to CPU/RAM pressure ([lila Issue #12356](https://github.com/lichess-org/lila/issues/12356)) — collectively, `lichess-bot` has no built-in process supervisor, so unattended operation requires wrapping it in one (launchd/systemd/Docker restart policy). A closed but instructive move-submission bug shows a UCI en passant capture (`bxa3` in Atomic) getting rejected as illegal by the engine layer despite being independently verified legal by three other means — a concrete example that castling/en-passant/underpromotion are exactly the code paths most likely to silently desync a hand-rolled UCI move encoder from true board state ([careless25/lichess-bot Issue #98](https://github.com/careless25/lichess-bot/issues/98)), reinforcing the case for leaning on `python-chess`'s UCI layer (via `lichess-bot`) rather than a bespoke Swift UCI move formatter for the bot bridge specifically. On clocks: `move_overhead` is real but blunt, and a structurally-similar bot hit a hard floor of ~0.1s/move purely from bot-side processing + HTTP round-trip latency, flagging a *winning* 1+0 bullet game on time — a risk inherent to any HTTP-round-trip-per-move architecture (DCM's single-forward-pass speed doesn't help, since the bottleneck is network/API latency, not search time) ([stefanobaghino/chessbot Issue #36](https://github.com/stefanobaghino/chessbot/issues/36)). On opponent-abandonment: the `opponentGone` signal is confirmed unreliable across a bot-side reconnect — if the bot itself drops and reconnects while the opponent also reconnects during that gap, the bot never receives the "opponent is back" (`gone:false`) message and has no way to confirm it's safe to claim victory, an issue still open as filed (November 2025) ([lila Issue #18665](https://github.com/lichess-org/lila/issues/18665)). Most notably for DCM's specific situation: the clearest documented case of a bot-adjacent account action wasn't a false-positive anti-cheat flag against the bot's own play — it was *human opponents* exploiting a weak, low-rated bot (`RandomMoverBot`) for rating sandbagging/boosting, which led Lichess to restrict some bots from rated play as a countermeasure ([Lichess forum thread](https://lichess.org/forum/general-chess-discussion/why-does-it-say-that-randommoverbot-violated-the-tos)) — a real argument for launching DCM's bot in casual-only mode (`modes: [casual]`) until its playing strength is no longer a trivial rating-farming target.

**Configurability is broader than the original pass covered, and directly answers the fixed-time-per-move question.** `lichess-bot`'s `engine.go_commands.movetime` option is a first-class, documented mechanism for exactly DCM's situation — an engine with no depth/node search concept, just a fixed think time per move. Source-level inspection of `add_go_commands()` in `engine_wrapper.py` confirms `movetime` acts as a ceiling layered on top of (not a replacement for) the normal clock-derived `wtime`/`btime`/`winc`/`binc` limit construction, and that `depth`/`nodes` settings, if left unset, are simply never sent — no special accommodation is needed for an engine that ignores them. The draw/resign automation block (`resign_score`, `offer_draw_score`, etc.) is calibrated for a classical centipawn eval and would need DCM's W/D/L-derived value scalar translated into a comparable centipawn-equivalent to mean anything, or — the lower-risk default — left disabled, letting the opponent/Lichess's own game-end handling govern draws/resignations instead. Logging/diagnostics turned out to default to more than expected: confirmed directly from `lichess-bot.py`'s argument parser, the bot automatically writes a full `lichess_bot_auto_logs/lichess-bot.log` plus a `config.log` snapshot on every startup *without* any flag — `--disable_auto_logging` opts **out**, rather than requiring an opt-in — while `-v` raises verbosity to include all Lichess communication and `-l`/`--logfile` adds a second, separate mirrored log file. PGN archiving (`pgn_directory`) is a distinct, `config.yml`-level opt-in that annotates each move with the engine's own `[%eval s,d]` score/depth, data that exists only locally and is never visible to Lichess. The full enumerated config surface (opening books, matchmaking, challenge filters, chat greetings, correspondence handling, etc.) is in the research note; most of it (books, tablebases, correspondence) is a non-goal for DCM per the project's existing no-book/no-search design.

**Alternatives, briefly.** BotLi (`github.com/Torom/BotLi`) is the one credible, currently-maintained alternative — as actively pushed as `lichess-bot` itself as of this research (`pushed_at` 2026-09-12 vs. 2026-09-15), with a feature set aimed at per-color/per-variant engine selection, richer book/tablebase support, bot-vs-bot matchmaking, and live console control. None of BotLi's differentiators are currently relevant to DCM's stated goal (watch it play real people; no books, no tablebases, no bot-vs-bot tournaments), and `lichess-bot`'s larger install base means its documented edge cases (Section above) are more thoroughly triaged — a smaller project's quieter issue tracker isn't evidence of fewer bugs, just less exercised surface area. `lichess-bot` remains the recommended default; BotLi is worth revisiting only if the roadmap later grows to want autonomous matchmaking or interactive live control.
