# Deep-dive pass: pain points, configurability, and alternatives (2026-09-28)

This note extends the original research pass with three additional questions, all scoped to real operator experience rather than marketing/docs copy. Sources are GitHub issues (lichess-org/lila, lichess-org/api, lichess-bot-devs/lichess-bot and its forks), the Lichess Feedback/General-Discussion forums, and primary-source config/code inspection (raw GitHub file fetches + `curl`/`grep` against `lib/lichess_bot.py`, `lib/engine_wrapper.py`, `config.yml.default`).

---

## 1. Snags, red flags, and common operational issues

### Stream disconnect/reconnect handling — the dominant real-world failure class
- **`Bot abandons game mid-play when stream drops (StopIteration)`** — the per-game NDJSON stream ending is treated unconditionally as "game over" by the bot's game loop; a transient network blip or a server-side connection close both look identical to a legitimate game-end signal, so the bot exits the loop mid-game and flags on time. A secondary bug compounds it: an internal `move_attempted` tracking flag resets to `False` at the top of every loop iteration, so if the disconnect fires one iteration after a real move was made, the flag is already stale and the reconnect path mishandles it — [Issue #1184](https://github.com/lichess-bot-devs/lichess-bot/issues/1184) (open at last check).
- **`After reconnecting (restart/internet connection), not all running games are picked up again`** — after the bot process restarts with several games in flight, some games are silently dropped from tracking. This can push the bot over its configured `concurrency` limit and reliably produces timeouts/forfeits on the orphaned games — [Issue #1101](https://github.com/lichess-bot-devs/lichess-bot/issues/1101) (open).
- **`lichess-bot crashes sometimes on a timeout or reconnect attempt`** — a related, still-open report where the process crashes outright (not just mishandles state) during reconnection, with the reporter suspecting VPN-driven IP churn as a trigger; a "long error log" precedes the crash but no root cause is confirmed in the thread. No documented workaround beyond restarting the process is described — the implication is that operators are relying on an external supervisor/watchdog rather than any built-in self-healing — [Issue #1120](https://github.com/lichess-bot-devs/lichess-bot/issues/1120) (open).
- **`Lichess server doesn't reconnect when client IP changes`** — ISP-driven public IP rotation (e.g., once a day) silently breaks the bot's long-lived stream connections without an explicit error surfaced to the client; keep-alive/heartbeat pinging was suggested as a mitigation in discussion but no fix has shipped — [careless25/lichess-bot Issue #135](https://github.com/careless25/lichess-bot/issues/135).
- A separate forum-adjacent report (`lichess API times out`, filed against `lila`) describes running a bot for "a few weeks" before hitting "multiple timeouts," with CPU/RAM both sitting around 50% (ruling out a local resource bottleneck) — consistent with the same class of long-lived-connection fragility rather than a client-side resource leak — [lichess-org/lila Issue #12356](https://github.com/lichess-org/lila/issues/12356).
- **Net takeaway for a from-scratch Swift bridge (not just a reason to use the Python bridge as-is):** stream termination must never be treated as an implicit "game over." A correct client needs to (a) distinguish a stream ending with a genuinely terminal `status` field from a stream ending with no such payload (network/server-side close), (b) reconcile its own in-memory "active games" set against Lichess's authoritative account state on every reconnect/restart rather than assuming zero games are active, and (c) run under a process supervisor (launchd/systemd-style) that restarts on crash, since even the mature reference bridge has open, unresolved crash-on-reconnect reports.

### Move submission edge cases
- **`Illegal uci error` on an en passant capture (`bxa3`) in an Atomic game** caused the bot to enter an infinite retry/error-print loop. Independent verification (python-chess PGN replay, manual board replay, Lichess's own analysis board) all accepted the move as legal — the failure was specifically in how the UCI layer's internal state diverged from the actual game position, not a genuine illegal move. The issue is closed with no visible fix/PR discussion in the thread, so treat it as a rare, likely environment/version-specific edge case rather than a currently-open bug, but it is a concrete example of the general risk class: **special moves (castling, en passant, underpromotion) are exactly where a UCI move-notation encoder/decoder is most likely to silently desync from the true board state**, since they're the least-exercised code paths — [careless25/lichess-bot Issue #98](https://github.com/careless25/lichess-bot/issues/98).
- For DCM specifically, this is a direct hit on `PolicyEncoding.swift`'s move↔UCI bridging: any custom Swift UCI-notation encoder must be exhaustively tested against castling (including Chess960 notation differences, irrelevant here since DCM is standard-chess-only), en passant, and all four underpromotion pieces before being trusted against a live opponent, exactly the kind of invariant the project's existing `PolicyEncoding.swift` bijection tests already emphasize — this is a strong argument for reusing `python-chess`'s UCI parsing (via `lichess-bot`) rather than hand-rolling a Swift-side UCI move formatter for the bot bridge specifically.

### Clock/time handling gotchas
- **`move_overhead`** (default 2000 ms in `config.yml.default`, called out separately again under the engine `go_commands` UCI-options block as a 100 ms default subtracted from search time) exists specifically to buffer against HTTP/network round-trip latency, but is a blunt instrument — it doesn't adapt to actual measured latency.
- **Fixed per-bot-processing-and-HTTP-round-trip floor**: an operator report (on a different but structurally similar bot, `stefanobaghino/chessbot`) documents flagging a *winning* 1+0 bullet game on time because the clock had a hard floor of roughly 0.1s/move purely from bot-side processing + HTTP round trip overhead — once the remaining clock drops to a couple of seconds, a long no-increment game becomes unwinnable regardless of engine strength, because the fixed per-move overhead eats the remaining budget faster than moves can be made — [stefanobaghino/chessbot Issue #36](https://github.com/stefanobaghino/chessbot/issues/36). This generalizes directly to any Bot-API bridge, DCM's included: **bullet and 0-increment time controls are structurally risky for any engine that must round-trip a full HTTP POST per move**, independent of engine think-time, and DCM's `--uci` single-forward-pass architecture doesn't reduce this floor since the constraint is network/API latency, not search time.
- **`Bot periodically spends about 1 second on a move`** — closed issue describing intermittent ~1s per-move stalls despite a configured 5000ms `move_overhead`, affecting (per the reporter) "all bots on the platform," suggesting a server-side or platform-wide cause rather than a bug specific to one bot's code; no resolution detail was visible in the closed issue — [Issue #94](https://github.com/lichess-bot-devs/lichess-bot/issues/94). Operators should expect occasional unexplained ~1s latency spikes as a baseline noise floor, not necessarily a client bug to chase.
- **Lag-compensation UX complaint (`lila` side, not bot-specific)**: users report lag compensation "feels unfair" specifically on low time controls, i.e., Lichess's own server-side lag-compensation logic is itself imperfect at the extremes — relevant context for why a bot's own clock bookkeeping shouldn't assume the server's reported remaining time is perfectly synced to wall-clock reality at very low `wtime`/`btime` — [lichess-org/lila Issue #14444](https://github.com/lichess-org/lila/issues/14444).

### Draw offer / takeback / resignation / opponent-abandonment bugs
- **`opponentGone` is unreliable across a client reconnect**: if the bot's own client disconnects and reconnects, and the opponent's *own* client reconnects during that window, the bot never receives the `opponentGone → gone:false` message that would tell it the opponent is back — it only ever saw `gone:true`. This leaves the bot unable to determine whether it's safe to claim victory after the abandonment timeout, since it has no confirmation the opponent didn't return. Filed November 2025, **still open** as of this research pass (Sept 2026) — [lichess-org/lila Issue #18665](https://github.com/lichess-org/lila/issues/18665).
- **Bot takeback handling was undocumented for a long time**: a contributor found the takeback-accept endpoint (`/api/bot/game/{gameId}/takeback/{accept}`) worked (mirroring the Board API's endpoint shape) but had no corresponding documentation in the API spec — filed and fixed via a linked PR, so this is now resolved, but it's a reminder that **the Bot API's docs have historically lagged the actual endpoint surface**, and something similar could recur for less-common actions — [lichess-org/api Issue #321](https://github.com/lichess-org/api/issues/321).
- `lichess-bot`'s own config exposes `max_takebacks_accepted` (default 0, i.e., takebacks declined by default) — so out of the box a fresh bot setup will *not* silently grant takebacks; this has to be deliberately opted into.
- No evidence was found of a currently-open bug specifically in `lichess-bot`'s *own* draw-offer or resignation logic (the `offer_draw_*`/`resign_*` config knobs) — the known-bad territory is specifically the opponent-presence/`opponentGone` signal on the Lichess server side, not the bridge's local draw/resign decision code.

### Rate limiting: real-world reports
- No confirmed report of a *permanent* ban resulting purely from rate-limit violations was found; the documented failure mode is temporary 429 responses with a `Retry-After` header, and Lichess's own guidance ("wait a full minute") is the standard remediation — [Lichess API Tips](https://lichess.org/page/api-tips) (previously verified).
- The one concrete "risked account restriction" example found is a third-party client that ignored `Retry-After` and retried on a fixed schedule instead — cited as a cautionary anti-pattern, not a confirmed ban outcome — [GitHub issue on a third-party fetcher](https://github.com/obajecollinsmicheal-cmd/smile4money/issues/1712) (previously verified; no update found this pass).
- `lichess-org/api` Issue #264 independently confirms rate limiting for specific *actions* (e.g., challenge creation) is "not clearly documented," consistent with the qualitative-only guidance posture described in the original report.

### Legitimate bots getting banned/suspended — the real risk is rating manipulation by opponents, not false-positive cheat detection
- The most concrete, bot-specific account-action case found is **not** an anti-cheat false positive against the bot's own play — it's third-party abuse *of* an easy/low-rated bot. `RandomMoverBot` was reported as flagged for "sandbagging and rating boosting" — i.e., *human opponents* exploited its weak play to inflate or deflate their own ratings, and Lichess's response was to restrict some bots from playing *rated* games as a countermeasure — [Lichess General Chess Discussion forum thread](https://lichess.org/forum/general-chess-discussion/why-does-it-say-that-randommoverbot-violated-the-tos). This is directly relevant to DCM: **early in training, before the network is meaningfully strong, a weak bot rated openly on Lichess is a plausible rating-farming target**, and Lichess's demonstrated countermeasure is to restrict/flag the bot account itself rather than only punishing the exploiting humans — an argument for starting in casual-only mode (`modes: [casual]` in `lichess-bot`'s config) until the engine's strength is no longer trivially exploitable, or accepting only from an allow-list initially.
- General Lichess cheat-detection false-positive reports exist in volume (`lila` Issues #10390, #20612, #18552, and multiple Feedback-forum threads titled "False positives" / "Cheat detected false positive"), but none found in this pass are specifically about a **Bot-API bot's own moves** triggering the engine-assistance detector against itself — the false-positive reports are uniformly about human players being flagged. This is a meaningful *absence* of evidence rather than a confirmed non-issue: bot accounts are already known/labeled as computer players (the `title: BOT` flag is public and expected), so it's plausible Lichess's human-cheating heuristics simply don't apply the same way to an account that's declared as a bot from the start — but no source confirms this explicitly, so it remains an open question.
- The account-suspension appeal path, for whatever cause, is `lichess.org/appeal`; moderators "rarely overturn or discuss banned accounts... to avoid revealing how Lichess' internal detection systems work," per forum-thread synthesis — meaning an operator has little visibility or recourse if the bot account does get flagged, beyond a generic appeal.

### Long-running unattended operation: what's documented
- No confirmed, attributable *memory leak* report specific to `lichess-bot` itself was found (searches surfaced an `Error R15 (Memory quota vastly exceeded)` issue, but that was filed against a different, Heroku-hosted fork/deployment — `oivas000/lichess-bot` — and reflects a Heroku dyno memory-quota problem rather than a demonstrated leak in the reference bridge's own code) — [oivas000/lichess-bot Issue #116](https://github.com/oivas000/lichess-bot/issues/116).
- The two most substantive multi-week/long-running-operation problems found are the ones already covered above under stream handling: the restart-time "not all games picked up" bug (#1101) and the "few weeks → multiple timeouts" report (lila #12356) — both point to **connection-layer staleness accumulating over long uptimes**, not memory growth, as the primary long-run risk. No documented supervisor pattern is bundled with `lichess-bot` itself (no built-in watchdog/self-restart); operators are implicitly expected to run it under an external process manager (systemd, launchd, Docker restart policy, etc.) — this is inferred from the absence of any self-healing code path and the nature of issues #1101/#1120/#1184, not from an explicit maintainer recommendation found in this pass.

## 2. Configurability / tunable options (comprehensive enumeration)

Source: direct fetch of [`config.yml.default`](https://raw.githubusercontent.com/lichess-bot-devs/lichess-bot/master/config.yml.default) and the [Configure lichess-bot wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/Configure-lichess-bot), cross-checked against `lib/lichess_bot.py` and `lib/engine_wrapper.py` source.

### Connection / account
- `token` — OAuth token (required).
- `url` — base URL (default `https://lichess.org/`), overridable for testing against a self-hosted lila instance.

### Engine process
- `engine.dir`, `engine.name` — subprocess location/binary.
- `engine.protocol` — `uci` / `xboard` / `homemade` (the last being a Python-side hand-rolled move-picker plugin point, not a wire protocol — relevant if a future DCM integration ever wanted to skip UCI entirely and call into a thin Python shim, though the existing `--uci` mode makes this unnecessary).
- `engine.ponder` — think on opponent's time (default true).
- `engine.silence_stderr`, `engine.interpreter`, `engine.working_dir`.
- **`engine.go_commands`** — `{nodes, depth, movetime}`. This is the direct answer to "how does a fixed-time-per-move, no-depth-concept engine fit lichess-bot's model": **`movetime` is a first-class, documented option**, separate from the default `wtime`/`btime`/`winc`/`binc` clock-based `go` command. Per the wiki: "movetime: 1000 will append `movetime 1000`" to the engine's `go` command. Source-level confirmation (`lib/engine_wrapper.py`, `add_go_commands()`): if `go_commands.movetime` is set and is *shorter* than the time the clock-based logic would otherwise allocate, the fixed movetime wins (`if time_limit.time is None or seconds(time_limit.time) > movetime: time_limit.time = movetime`) — i.e., it acts as a ceiling on think time, layered on top of (not instead of) the normal clock-tracking `Limit(white_clock=..., black_clock=..., white_inc=..., black_inc=...)` construction that's always sent. There is no config to *disable* clock-based `Limit` construction entirely — the engine (via `python-chess`'s UCI engine class) always receives clock info, but `go_commands.depth`/`go_commands.nodes` can additionally be set and "apply regardless of engine type, including custom engines that may ignore search depth entirely" (i.e., DCM's single-forward-pass engine can simply ignore `depth`/`nodes` UCI options it's handed, the same way any UCI engine is free to ignore options it doesn't implement — no config-side accommodation is *required* beyond leaving those unset and controlling behavior purely via `movetime`).
- Per-UCI-option engine tuning (`engine.uci_options` block): arbitrary key/value pass-through to the engine's UCI `setoption` — sample defaults shown for `Move Overhead` (100), `Threads` (4), `Hash` (512 MB), `SyzygyPath`, `UCI_ShowWDL` (true). This is exactly the mechanism by which a `--uci`-mode DCM binary would receive e.g. a `Model` or `Temperature` option (per the project's existing `documentation/UCI.md` design), fully generic and not bot-specific.

### Opening books / online move sources / tablebases (all independently toggleable)
- **Local Polyglot book**: `enabled`, per-variant `book` file paths, `min_weight`, `selection` (`weighted_random`/`uniform_random`/`best_move`), `max_depth` (ply cutoff), `normalization`.
- **ChessDB cloud book**: `enabled`, `min_time`/`max_time` (game-length gating), `move_quality` (`all`/`good`/`best`), `min_depth`.
- **Lichess Cloud Analysis**: `enabled`, `min_time`/`max_time`, `move_quality` (`good`/`best`), `max_score_difference`, `min_depth`, `min_knodes`.
- **Lichess Opening Explorer**: `enabled`, `min_time`/`max_time`, `source` (`lichess`/`masters`/`player` + `player_name`), `sort` (`winrate`/`games_played`), `min_games`.
- **Online tablebases**: `enabled`, `min_time`/`max_time`, `max_pieces` (default 8), `source` (`lichess`/`chessdb`), `move_quality` (`best`/`suggest`).
- **Local Syzygy**: `enabled`, `paths`, `max_pieces` (default 7), `move_quality`.
- **Local Gaviota**: `enabled`, `paths`, `max_pieces` (default 5), `min_dtm_to_consider_as_wdl_1`, `move_quality`.
- Cross-cutting: `max_out_of_book_moves` (stop trying online sources after N consecutive misses, default 10), `max_retries` (default 2) for online-source HTTP calls.
- **None of this applies to DCM** — the project has no opening book and no tablebase integration by design (per `CLAUDE.md`: "no opening book and no human training data"), so this entire configuration surface would stay disabled; flagged here purely for completeness of the enumeration.

### Draw / resign automation (engine-eval-driven)
- `resign_enabled` (default false), `resign_score` (centipawn threshold, default -1000), `resign_for_egtb_minus_two` (default true), `resign_moves` (consecutive qualifying moves required, default 3).
- `offer_draw_enabled` (default true), `offer_draw_score` (default 0 cp), `offer_draw_for_egtb_zero` (default true), `offer_draw_moves` (default 10), `offer_draw_pieces` (only offer when ≤N pieces remain, default 10).
- **Direct friction with DCM's architecture**: this entire block is designed around a classical centipawn eval stream from the engine. DCM's UCI mode would need to translate its W/D/L-softmax-derived value scalar (`p_win − p_loss ∈ [−1, +1]`, per the project's `documentation/UCI.md`/engine design) into a centipawn-equivalent number for `lichess-bot`'s resign/draw thresholds to mean anything comparable to how they're calibrated for classical engines — or these knobs should simply stay disabled and resignation/draw-offer left to the opponent/Lichess's own game-end detection, which is the lower-risk default given `resign_enabled` and its counterpart already default to a conservative posture (resign off, draw-offer on but gated by both a favorable score *and* low piece count).

### Correspondence-specific
- `move_time` (search seconds per correspondence move, default 60), `checkin_period` (default 300s), `disconnect_time` (default 150s), separate `ponder` override (default false) — moot for DCM since correspondence isn't a relevant time control for a real-time engine.

### Game-level timing/behavior
- `abort_time` (seconds before auto-aborting a stalled game, default 30), `fake_think_time` (artificially pad response time, default false — confirms no platform requirement to "seem human"; purely a bridge-level cosmetic option), `rate_limiting_delay` (extra ms inserted between moves, default 0), `move_overhead` (ms subtracted as a latency buffer, default 2000), `max_takebacks_accepted` (default 0), `quit_after_all_games_finish` (default false).

### Challenge acceptance policy
- `concurrency` (simultaneous games, default 1), `games_reserved_for_humans` (slots held back from bot challengers, default 0), `sort_by` (`best`/`first`), `preference` (`none`/`human`/`bot`), `accept_bot` (default true), `only_bot` (default false), `max_increment`/`min_increment` (default 20/0s), `max_base`/`min_base` (default 1800/0s), `max_days`/`min_days` (correspondence, default 14/1), `variants` (allow-list, default standard-only), `time_controls` (allow-list, default bullet/blitz/rapid/classical), `modes` (`casual`/`rated`, both by default), `bullet_requires_increment` (default false), `max_simultaneous_games_per_user` (default 5, i.e., a per-opponent concurrency cap layered under the account-wide `concurrency`).
- Blocklists/allowlists: `block_list`, `online_block_list` (remote URL), `allow_list`, `include_challenge_block_list` (whether matchmaking-originated challenges also respect the block list).

### Proactive matchmaking (bot initiates challenges)
- `allow_matchmaking` (default false), `allow_during_games` (default false), `challenge_variant` (`random` or specific), `challenge_timeout` (idle minutes before self-challenging, default 30), `challenge_initial_time`/`challenge_increment`/`challenge_days` (option lists to sample from), `opponent_rating_difference` (max delta, default 300), `rating_preference` (`none`/`high`/`low`), `challenge_mode` (`casual`/`rated`/`random`), `challenge_filter` (`none`/`coarse`/`fine` — how aggressively to avoid re-challenging users who've declined before).

### Chat / greeting
- `hello`/`goodbye` (opponent-facing), `hello_spectators`/`goodbye_spectators` — simple templated strings sent via the chat endpoint at game start/end.

### Logging / diagnostics — confirmed by direct source inspection (`lib/lichess_bot.py`)
This category is **not well covered by the wiki's config-file documentation** — it's entirely CLI-flag-driven, not `config.yml`-driven, confirmed by fetching `lichess-bot.py`'s argument parser directly:
- `-v` — verbose flag; raises log level to `DEBUG` and includes *all* communication with Lichess (vs. `INFO` by default).
- `--config <path>` — alternate config file (defaults to `./config.yml`).
- `-l`/`--logfile <path>` — mirror console output to a file (off/None by default — console-only unless explicitly requested).
- `--disable_auto_logging` — opt *out* of a separate, automatic logging path.
- **Default (no flags) behavior, confirmed from source**: even without `-l`, the bot **automatically** creates a `lichess_bot_auto_logs/` directory and writes `lichess-bot.log` plus a `config.log` snapshot of the resolved config on every startup — i.e., structured logging to disk happens by default and must be explicitly opted out of via `--disable_auto_logging`, not opted into. This is a materially better default posture than "console-only unless you remember a flag."
- **PGN archiving** is a separate, `config.yml`-level opt-in (`pgn_directory`, `pgn_file_grouping` = `game`/`opponent`/`all`) — not automatic, and distinct from the auto-log directory. When enabled, each move is annotated with a `[%eval s,d]` comment carrying the bot's own internal score/depth — data that only exists locally and is never sent to or knowable by Lichess, reinforcing the original report's conclusion that connection-health/internal-engine-state logging is entirely the bridge's responsibility.
- No built-in crash/restart supervisor, health-check endpoint, or alerting hook was found in the source paths inspected — logging is purely passive (writes to disk); an operator wanting alerts on crash/disconnect needs to layer that on top (e.g., watch the log file, or wrap the process in a supervisor that pages on unexpected exit).

## 3. Alternatives to `lichess-bot` — brief

- **BotLi** (`github.com/Torom/BotLi`) is the one credible, currently-maintained alternative found. As of this research pass (checked via the GitHub API): `pushed_at` 2026-09-12, `open_issues_count` 0, 69 stars, not archived — actively maintained on a comparable cadence to `lichess-bot` itself (`pushed_at` 2026-09-15, 1089 stars, 15 open issues) — [Torom/BotLi](https://github.com/Torom/BotLi).
- BotLi's design is explicitly derived from `lichess-bot` but adds: per-color and per-time-control/per-variant engine selection (distinct engine binaries selectable by appending `_white`/`_black`, or configured differently per time control/variant), a broader online-book/tablebase feature set (multiple opening-book selection strategies, online + local endgame tablebase querying), autonomous bot-vs-bot challenging with configurable delays, tournament auto-join with team support, and an interactive console command interface for live control (pause matchmaking, join/leave tournaments) while running — features aimed more at competitive/matchmaking-heavy bot operation than at `lichess-bot`'s broader engine-protocol compatibility (UCI + XBoard + "homemade").
- BotLi's own README explicitly discourages using it just to run "another Stockfish bot," framing itself as aimed at operators with a custom engine or a genuinely novel bot concept — which describes DCM's situation reasonably well, but the *marginal* value over `lichess-bot` for DCM specifically is smaller than it might first appear, since DCM doesn't need opening books, tablebases, or bot-vs-bot matchmaking tournaments (non-goals per the project's own design), and `lichess-bot`'s `movetime`-based `go_commands` already cleanly accommodates a single-forward-pass engine (see Section 2). The features where BotLi pulls ahead (tournament auto-join, interactive console control, per-color/per-variant engine selection) are not currently relevant to DCM's stated goal of "watch it play real people."
- No other actively-maintained bridge was found in this pass beyond the two already covered in the original report (`asyncLio-bot`, an async/await Python variant, and the legacy `ornicar/lichess-uci-bot`) — neither showed recent-maintenance signals comparable to `lichess-bot` or BotLi.
- **Recommendation unchanged from the original report's direction, refined**: `lichess-bot` remains the lower-risk default given its larger install base (1089 vs 69 stars) and correspondingly larger number of independently-reported/triaged edge cases (the entire Section 1 above is possible precisely because `lichess-bot` has enough real-world usage to generate a paper trail of issues) — a smaller, newer project's *absence* of similar bug reports is not evidence of fewer bugs, just less exercised surface area. BotLi is worth a second look specifically if/when DCM's roadmap grows to want autonomous bot-vs-bot matchmaking or live console control during a run, neither of which is currently in scope.
