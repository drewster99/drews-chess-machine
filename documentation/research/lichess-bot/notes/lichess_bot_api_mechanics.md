# Lichess Bot API — End-to-End Technical Architecture and Integration Mechanics

## How does OAuth / personal access token creation work for Lichess bots, and what scope is required?

### Takeaway
Lichess bot auth uses a simple personal OAuth2 access token (not a full OAuth authorization-code flow) created from the account's Settings > API access tokens page, scoped to `bot:play`; the token is shown only once and the account must be upgraded to BOT status before or immediately after minting the token, and that upgrade is only possible for an account that has never played a rated/unrated game as a normal account.

### Cited Findings
- Personal access tokens are created at `https://lichess.org/account/oauth/token/create` (or a pre-filled deep link such as `https://lichess.org/account/oauth/token/create?scopes%5B%5D=bot:play&description=lichess-bot`), reached via the UI path: username (top right) → Preferences → API Access tokens → the blue "+" button — [How to create a Lichess OAuth token wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/How-to-create-a-Lichess-OAuth-token); [WebSearch result summary](https://lichess.org/account/oauth/token/create?)
- The exact scope required for bot play is displayed in the UI as **"Play games with the bot API"**, machine name `bot:play` — [lichess-bot wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/How-to-create-a-Lichess-OAuth-token)
- Tokens are shown only once at creation time: "You won't see this token again on Lichess, so do save it" — [lichess-bot wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/How-to-create-a-Lichess-OAuth-token)
- The Bot API's `/api/bot/account/upgrade` (POST) endpoint upgrades a normal account to a bot account — [lichess-api.yaml via WebFetch extraction](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml)
- Account irreversibility caveat, directly relevant to token/account setup ordering: "If you have previously played games on an existing account, you will not be able to use it as a bot account" — [lichess-bot wiki](https://github.com/lichess-bot-devs/lichess-bot/wiki/How-to-create-a-Lichess-OAuth-token) (Note: per task constraints this account-status rule is covered by a separate researcher — flagged here only because it directly gates the token/upgrade sequencing.)
- Token storage in the reference bridge: either the `token:` field in `config.yml`, or the environment variable `$LICHESS_BOT_TOKEN` — [config.yml.default search summary](https://github.com/lichess-bot-devs/lichess-bot/blob/master/config.yml.default)
- Board API play (as distinct from Bot API) uses a `board:play` scope instead of `bot:play` — [lichess-api.yaml extraction](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml)
- Broader event-stream reads may require an additional scope: one search result noted the general event stream endpoint accepting scopes like `challenge:read` alongside `bot:play` — [Stream Incoming Events reference](https://www.mintlify.com/lichess-org/lila/api/streaming/events)
- General token security guidance: "Keep your tokens secret and do not share them in public repositories or public forums. Your tokens can be used to make your account perform arbitrary actions (within the limits of the tokens' scope)" — [WebSearch summary of Lichess docs](https://lichess.org/account/oauth/token/create?)

### Inferences
- Unlike a full three-legged OAuth "Login with Lichess" flow (used for multi-user apps), a single self-hosted bot only needs the simpler personal-access-token path since the bot operator and the account owner are the same person; a full OAuth app registration/authorization-code + PKCE flow exists for Lichess generally (evidenced by third-party clients like `litchee` supporting OAuth2 PKCE) but is not the documented/expected path for a single bot account.
- Because tokens are single-shot-displayed and scoped, operational practice is to mint one long-lived `bot:play` token per bot account and store it as a secret (env var or gitignored config file), never regenerate casually since regenerating likely invalidates the old token (not explicitly confirmed in sources).

### Gaps
- Whether/how a `bot:play` token can be scoped with an expiration date, or whether Lichess supports token revocation/rotation workflows, was not found in the sources retrieved.
- The exact full list of scopes needed for a minimal Bot API integration (just `bot:play` vs. `bot:play` + `challenge:read`/`challenge:write` for the event/challenge flow) was not conclusively pinned down from primary docs; one secondary search result mentioned `challenge:read` being associated with the generic event stream, but this wasn't independently confirmed against the OpenAPI spec's per-endpoint `security` blocks.

## What are the Lichess Board/Bot API endpoints used for bot play, and what is the general flow?

### Takeaway
The flow is: authenticate with a bearer token → open a persistent NDJSON event stream (`/api/stream/event`) to receive `challenge` and `gameStart`/`gameFinish` events → accept/decline challenges via the Challenge API → for each accepted game, open a second persistent NDJSON stream (`/api/bot/game/stream/{gameId}`) that first emits a full game state (`gameFull`) then incremental `gameState`/`chatLine` events → the bot posts moves back via `POST /api/bot/game/{gameId}/move/{move}`, with sibling endpoints for chat, abort, resign, draw, takeback, and victory/draw claims.

### Cited Findings
- Endpoint table extracted from the official OpenAPI spec (`lichess-api.yaml`), Bot API group — [lichess-api.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml):
  - `GET /api/bot/online` — list online bots
  - `POST /api/bot/account/upgrade` — "Upgrade a normal account to a bot account"
  - `GET /api/bot/game/stream/{gameId}` — "Stream incoming chess moves" (the per-game NDJSON state stream)
  - `POST /api/bot/game/{gameId}/move/{move}` — "Play chess moves"
  - `POST /api/bot/game/{gameId}/chat` — "Write in player/spectator chats"
  - `POST /api/bot/game/{gameId}/abort` — terminate game
  - `POST /api/bot/game/{gameId}/resign` — resign game
  - `POST /api/bot/game/{gameId}/draw/{accept}` — offer/accept draw
  - `POST /api/bot/game/{gameId}/takeback/{accept}` — propose/accept takeback
  - `POST /api/bot/game/{gameId}/claim-victory` — claim victory (e.g., on opponent disconnect/timeout)
  - `POST /api/bot/game/{gameId}/claim-draw` — claim draw
- The equivalent Board API set (for human-supervised, non-engine play — kept here only for architectural contrast) mirrors the same shape under `/api/board/...`, plus a `POST /api/board/seek` to create an open seek and `POST /api/board/game/{gameId}/berserk` — [lichess-api.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml)
- Restriction noted in the spec extraction: Bot API says "Engine assistance is allowed"; bots are "restricted to challenge games only" and cannot play UltraBullet (¼+0); Board API explicitly forbids engine assistance — [lichess-api.yaml](https://raw.githubusercontent.com/lichess-org/api/master/doc/specs/lichess-api.yaml)
- The top-level real-time event feed is `GET /api/stream/event`, which streams "incoming events reaching a Lichess user in real time" as NDJSON, one JSON object per line with a `type` field; documented event types include `gameStart`, `gameFinish`, and `challenge` — [Stream Incoming Events reference](https://www.mintlify.com/lichess-org/lila/api/streaming/events)
- Challenge accept/decline is handled via the Challenge API, e.g. `POST /api/challenge/{challengeId}/accept` — [WebSearch summary citing lichess-api.yaml](https://github.com/lichess-org/api/blob/master/doc/specs/lichess-api.yaml)
- Per-game streaming uses two logical message shapes distinguished by a `type` field: a `gameFull` message (full game description, sent once at stream start, and again in some cases) and a `gameState` message (incremental move/clock updates) — [DeepWiki Game Export and Streaming summary](https://deepwiki.com/lichess-org/api/5.3-game-export-and-streaming) (Note: this page documented the related but distinct `/api/stream/game/{id}` spectator/export stream — the shape it describes, `gameFull` at start + `gameState` deltas, matches the documented Board/Bot game stream convention, but should be double-checked against the Bot-specific schema in the OpenAPI spec directly since this citation was for a sibling endpoint.)
- Chat lines arriving mid-game on the per-game stream are delivered as `chatLine` events within the same NDJSON stream — [general Bot API knowledge corroborated by lichess-bot feature list](https://github.com/lichess-bot-devs/lichess-bot) (chat handling is a listed capability of the reference bridge)
- NDJSON streaming convention across Lichess endpoints: "you must buffer incoming chunks and split them by newlines to decode each JSON object individually," and clients commonly skip/ignore empty lines used to keep the HTTP connection alive — [WebSearch summary](https://toolloom.com/qa-articles/how-to-stream-and-parse-lichess-ndjson-data-in-real-time-with-native-php-and-curl-79981475); corroborated separately — [WebSearch summary on stream/event keep-alive handling](https://www.mintlify.com/lichess-org/lila/api/streaming/events)
- Concurrency ceiling relevant to running multiple game streams at once: "Maximum 8 concurrent game streams per IP address," with a 429 error returned if the stream limit is exceeded — [DeepWiki Game Export and Streaming](https://deepwiki.com/lichess-org/api/5.3-game-export-and-streaming) (again sourced from the sibling `/api/stream/game/{id}` doc page; treat as indicative for the general streaming subsystem rather than confirmed bit-for-bit for `/api/bot/game/stream/{gameId}`).

### Inferences
- The two-stream architecture (one long-lived account-level event stream + one long-lived stream per active game) means a bot process must manage at least two concurrent persistent HTTP connections whenever a game is in progress, plus issue short-lived POST requests for moves/chat/etc. This is the natural architecture reflected in the reference bridge's design (it spawns a per-game handler/thread that owns the game stream while a single top-level loop owns the event stream).
- Because both stream types are NDJSON over a kept-open HTTP connection (not WebSockets), a bot must treat "stream ended" as an ambiguous signal (game truly over vs. transient disconnect) rather than a hard authoritative game-over signal — this is corroborated in the gotchas section below.

### Gaps
- The exact JSON schema (field names) for `gameFull`, `gameState`, and `chatLine` on the Bot-specific `/api/bot/game/stream/{gameId}` endpoint was not directly pulled from the OpenAPI spec body (only endpoint summaries were extracted); a full field-level schema (e.g., `moves`, `wtime`, `btime`, `winc`, `binc`, `wdraw`, `bdraw`, `status`) should be verified directly against `lichess-api.yaml`'s response schemas if exact parsing code is being written.
- Whether `/api/stream/event` requires the `bot:play` scope alone or also `challenge:read`/`challenge:write` was not conclusively confirmed from a primary source in this pass (see Gap above under the OAuth section).

## What is the official `lichess-bot` reference Python bridge, how does it wrap a UCI engine, is it still the standard as of 2026, and are there Swift-friendly alternatives?

### Takeaway
`lichess-bot` (github.com/lichess-bot-devs/lichess-bot) is the community-standard, actively-maintained free Python bridge between the Bot API and local engine subprocesses, supporting UCI, XBoard/CECP, and custom "Homemade" engines via `python-chess`'s engine-communication layer; there is no dedicated Swift-native bridge, but since the integration surface is plain HTTP/NDJSON + a UCI subprocess, a Swift engine can either be driven by the Python bridge (as a UCI subprocess) or a from-scratch Swift bridge can be written directly against the documented REST/NDJSON API.

### Cited Findings
- `lichess-bot` describes itself as "a free bridge between the Lichess Bot API and chess engines" — [lichess-bot GitHub README extraction](https://github.com/lichess-bot-devs/lichess-bot)
- It supports three engine integration modes: **UCI engines**, **XBoard (CECP) engines**, and **"Homemade" engines** (custom Python implementations) — [lichess-bot README extraction](https://github.com/lichess-bot-devs/lichess-bot)
- Engine subprocess communication is implemented via `python-chess`'s engine-communication code, i.e., the bridge spawns the engine binary as a subprocess and speaks UCI/CECP over its stdin/stdout — [lichess-bot GitHub extraction](https://github.com/lichess-bot-devs/lichess-bot)
- Configuration is driven by a `config.yml` (templated from `config.yml.default`) specifying the engine path, protocol, and bot behavior parameters — [lichess-bot README/config.yml.default search summary](https://github.com/lichess-bot-devs/lichess-bot/blob/master/config.yml.default)
- Feature list: "Every variant and time control," matchmaking, tournament participation (Arena/Swiss), draw offers, resignation, accepting move takebacks, PGN game saving, and local/online opening books and endgame tablebase support — [lichess-bot README extraction](https://github.com/lichess-bot-devs/lichess-bot)
- Platform support: Python 3.10+ (one extraction) — note a separate, possibly-stale mirror repo description says "Python 3.9 and later" — cross-check before relying on a specific minimum version; runs on Windows, Linux, macOS, and Docker — [lichess-bot README extraction](https://github.com/lichess-bot-devs/lichess-bot); [WebSearch summary of a lichess-bot fork description](https://github.com/lichessbot/lichess-bot-1)
- Repository activity signal (as observed during this research pass, September 2026): multiple active GitHub Actions workflows (Python Build, Python Test, Mypy) and open issues/PRs, consistent with ongoing maintenance — [lichess-bot GitHub extraction](https://github.com/lichess-bot-devs/lichess-bot). This is circumstantial evidence of active maintenance, not an explicit maintainer statement about 2026 status.
- No Swift-native or Swift-oriented Lichess bot bridge was found. Known community bridges are: **lichess-bot** (Python, the canonical/most-referenced one), **asyncLio-bot** (Python, async/await variant — "A bridge between UCI chess engines and Lichess") — [asyncLio-bot GitHub](https://github.com/Heiaha/asyncLio-bot); **lichess-uci-bot** (older/other Python bridge, "A bridge between Lichess API and UCI bots," with at least one fork under a different maintainer) — [ornicar/lichess-uci-bot](https://github.com/ornicar/lichess-uci-bot), [ana-ka/lichess-uci-bot fork](https://github.com/ana-ka/lichess-uci-bot); **chessio** (Scala-based bridge for UCI engines) — [Fashionablylatte/chessio](https://github.com/Fashionablylatte/chessio); and a Rust API client, **litchee**, offering full endpoint coverage, NDJSON streaming, and OAuth2 PKCE, though described as a general API client rather than a dedicated engine bridge — [obazin/litchee](https://github.com/obazin/litchee)
- Multiple forks of `lichess-bot` exist under different organizations/usernames (e.g., `CSSLab/lichess-bot`, `careless25/lichess-bot`, `dolegi/lichess-bot`), indicating the codebase is widely reused/forked as a base rather than there being one single monolithic canonical maintainer lineage — [WebSearch results listing forks](https://github.com/CSSLab/lichess-bot)

### Inferences
- Because the Bot API integration surface is just HTTP + NDJSON + bearer-token auth, and the engine side is just a subprocess speaking UCI over stdin/stdout, a Swift engine (like the one in this repo) does not strictly need the Python bridge: the two realistic integration paths are (a) wrap the Swift engine in a thin UCI-protocol shim (stdin/stdout loop) and run it as a subprocess under the existing, actively-maintained `lichess-bot` Python bridge — lowest engineering risk, reuses all of lichess-bot's edge-case handling (reconnects, matchmaking, tournament flows); or (b) write a small native Swift bridge directly against `/api/stream/event`, `/api/bot/game/stream/{gameId}`, and the move/chat/abort/resign endpoints using `URLSession` streaming — more engineering work and re-implementing edge cases the Python bridge has already hardened (see gotchas below), but keeps the whole stack in Swift.
- Given this project's existing UCI support (`--uci` CLI flag per this repo's `documentation/UCI.md`), option (a) — running the existing UCI mode as a subprocess under `lichess-bot` — is the lower-risk path to "watch it play real opponents on Lichess" without writing a new networking layer.

### Gaps
- No explicit 2026-dated maintainer statement ("this is still the standard/maintained bridge in 2026") was found; the "actively maintained" conclusion is inferred from repository activity signals (open issues/PRs, CI workflows) observed during this research pass rather than a dated announcement, and this should be flagged as time-sensitive/inferential rather than a hard confirmed fact.
- No Swift-specific bridge or SDK was found in any search; this is reported as a genuine absence rather than an oversight, though the search was not exhaustive of every possible small/unlisted GitHub repo.

## What known gotchas, disconnect/reconnect behaviors, or failure modes occur when running a Lichess bot unattended for long periods?

### Takeaway
The dominant class of real-world failure reported against the reference bridge is stream-drop handling: the bot's game-stream reader can misinterpret a transient network blip as "game over" and abandon an in-progress game (risking a loss on time), and there are known issues with picking all games back up correctly after a bot process restart when many games are running concurrently; IP changes from an ISP can also break the long-lived stream connections.

### Cited Findings
- Reported bug: "Bot abandons game mid-play when stream drops (StopIteration)" — when the per-game stream ends (`StopIteration`), the bot "unconditionally exits the game loop — even if the game is still in progress," which "causes the bot to flag on time" — [lichess-bot-devs/lichess-bot Issue #1184](https://github.com/lichess-bot-devs/lichess-bot/issues/1184)
- A stream ending is an ambiguous signal — it does not necessarily mean the game ended; it can be caused by "a network blip, Lichess closing the connection, etc." — [lichess-bot-devs/lichess-bot Issue #1184](https://github.com/lichess-bot-devs/lichess-bot/issues/1184)
- A related implementation-level footgun noted in the same issue thread: a `move_attempted` tracking flag "is reset to False at the top of each loop iteration," so if a move was made on iteration N and the disconnect exception fires on iteration N+1, the flag is already stale/false, compounding the mishandling of the reconnect path — [lichess-bot-devs/lichess-bot Issue #1184](https://github.com/lichess-bot-devs/lichess-bot/issues/1184)
- Reported bug: after restarting `lichess-bot.py` while many games are running in parallel, "not all games are picked up again," which can cause the bot to exceed its allowed concurrency and results in timeouts/forfeits on the games that weren't resumed — [lichess-bot-devs/lichess-bot Issue #1101](https://github.com/lichess-bot-devs/lichess-bot/issues/1101)
- Reported bug/discussion: "Lichess server doesn't reconnect when client IP changes" — an ISP that rotates the client's public IP (e.g., once a day) can break the bot's long-lived connections; keep-alive signals were suggested in discussion as a potential mitigation — [careless25/lichess-bot Issue #135](https://github.com/careless25/lichess-bot/issues/135)
- General (non-bot-specific) Lichess-side disconnect behavior is covered in the official Disconnection FAQ, which explains normal disconnect/reconnect semantics for the platform overall — [Lichess Disconnection FAQ](https://lichess.org/page/disconnection-faq) (useful background, but this page is about human clients/browser sessions rather than the Bot API specifically, so treat its applicability to bot streams as partial/indirect).
- NDJSON streams use blank keep-alive lines to hold the HTTP connection open; client code is expected to skip blank lines rather than treat them as data or as a stream-end signal — [WebSearch summary on stream/event handling](https://www.mintlify.com/lichess-org/lila/api/streaming/events); [WebSearch summary on NDJSON parsing practice](https://toolloom.com/qa-articles/how-to-stream-and-parse-lichess-ndjson-data-in-real-time-with-native-php-and-curl-79981475)

### Inferences
- Robust long-running bot operation requires the client (whether the Python bridge or a custom Swift bridge) to explicitly distinguish "the per-game stream ended because Lichess sent a terminal game-state message with a final `status`" from "the underlying TCP/HTTP connection simply dropped," and to re-open (`GET /api/bot/game/stream/{gameId}` again) on the latter rather than treating any stream termination as game-over. This is exactly the class of bug reported in Issue #1184.
- On process restart, a bot needs to reconcile its own idea of "active games" against Lichess's authoritative list (e.g., by re-querying account/game-in-progress state or replaying the event stream) before assuming zero games are active, to avoid the concurrency/timeout failure mode in Issue #1101.
- Because ISP-driven IP churn can silently break a long-lived stream without an explicit error, a production bot should implement an idle/heartbeat timeout on both the event stream and each game stream (i.e., if no line — including keep-alive blank lines — has been received within some threshold, proactively tear down and reconnect) rather than relying solely on the OS/HTTP layer to notice the dead connection.

### Gaps
- No official Lichess documentation was found that specifies a guaranteed keep-alive interval (e.g., "expect a blank line every N seconds") for either `/api/stream/event` or `/api/bot/game/stream/{gameId}`, which would be needed to set a precise heartbeat-timeout value; this should be measured empirically or asked about in the Lichess API Discord channel referenced in the API tips page.
- Chat-spam handling specifics (e.g., documented rate limits or muting behavior for the `/api/bot/game/{gameId}/chat` endpoint, or Lichess-side spam filters bots should anticipate) were not found in the sources retrieved during this pass.
- Move-timing/clock-sync edge cases (e.g., how `wtime`/`btime` fields in `gameState` messages should be reconciled with local wall-clock timing, lag compensation, or Lichess's own move-time correction) were not directly documented in the sources found; the reference bridge's actual clock-handling code was not inspected in this pass (README/wiki summaries did not cover it in the depth needed).

## What are Lichess's API rate limits relevant to bot play, and how should 429s be handled?

### Takeaway
Lichess does not publish precise per-endpoint rate-limit numbers; official guidance is qualitative — make requests sequentially (one at a time) rather than in parallel, and on receiving an HTTP 429 back off for a full minute before retrying — and community reports show that naive fixed-schedule retry loops that ignore the `Retry-After` header risk triggering repeated 429s or even account restrictions.

### Cited Findings
- Official guidance (Lichess API Tips page) states two core rules: "Only make one request at a time" and on a 429 response, "please wait a full minute before resuming API usage" — [Lichess API Tips](https://lichess.org/page/api-tips)
- The API Tips page explicitly states Lichess uses "a complex array of separate rate limiting factors" to protect against DDOS, and does not specify per-endpoint numeric limits because they are "varied and ever changing" — [Lichess API Tips](https://lichess.org/page/api-tips)
- If persistent rate-limit problems occur despite following the two core rules, Lichess staff indicate willingness to work with developers via the Discord `#lichess-api-support` channel — [Lichess API Tips](https://lichess.org/page/api-tips)
- Lichess does return a `Retry-After` header on 429 responses specifying the wait duration, but at least one third-party client's fetcher was observed to ignore this header and instead "retries on a fixed schedule, which can cause the account to be banned" — a cautionary example of what NOT to do, not an official Lichess-side behavior — [GitHub issue on a third-party Lichess API fetcher](https://github.com/obajecollinsmicheal-cmd/smile4money/issues/1712)
- Separately, community forum threads document real users hitting 429s unexpectedly despite believing they were within a "wait 1 second" self-imposed limit, and open `lichess-org/api` GitHub issues note that rate limiting for specific actions (e.g., challenge creation) is "not clearly documented" — [Lichess Feedback forum thread](https://lichess.org/forum/lichess-feedback/lichess-api-returning-me-a-429-too-many-requests-despite-waiting-over-a-minute); [lichess-org/api Issue #264](https://github.com/lichess-org/api/issues/264)
- A separate open issue requests that Lichess "delay excessive requests instead of serving 429s" outright, indicating the current behavior (as of when that issue was filed) is to hard-reject with 429 rather than queue/throttle server-side — [lichess-org/api Issue #139](https://github.com/lichess-org/api/issues/139)
- Streaming-specific concurrency limit found for a sibling streaming endpoint: "Maximum 8 concurrent game streams per IP address," else 429 — [DeepWiki Game Export and Streaming summary](https://deepwiki.com/lichess-org/api/5.3-game-export-and-streaming) (documented for `/api/stream/game/{id}`; treat as indicative rather than confirmed identical for `/api/bot/game/stream/{gameId}`, per the caveat in the endpoints section above).

### Inferences
- Because exact numeric limits are deliberately undocumented and "varied and ever changing," the correct engineering posture for an unattended bot is defensive: serialize outgoing requests (never fire moves/chat/abort concurrently against the same or multiple games without a queue), honor `Retry-After` when present, and fall back to a flat ≥60-second backoff on any 429 without a usable header — matching the two official rules from the API Tips page plus the documented `Retry-After` behavior.
- A single-bot-account setup (one engine, modest game concurrency) is unlikely to be the primary target of Lichess's DDOS-oriented rate limiting; the more relevant risk for this project's use case is likely the per-IP concurrent-stream ceiling (if it also applies to bot game streams) if many games are ever run in parallel, plus ordinary move-POST pacing during very fast time controls (bullet/blitz), where a bug causing duplicate/retry move POSTs could plausibly trip a limit.

### Gaps
- No official documentation confirms whether the "8 concurrent game streams per IP" limit found for `/api/stream/game/{id}` also applies verbatim to `/api/bot/game/stream/{gameId}`; this needs to be verified directly against the OpenAPI spec's rate-limit annotations (if any exist) or by empirical testing, since bots (unlike spectators) may be expected/allowed a different ceiling given they by design only run games they're playing in (concurrency limited elsewhere by account-level "max concurrent games" rules, which are out of this researcher's scope per the task constraints).
- No documented numeric limit was found specifically for the move-POST endpoint (`/api/bot/game/{gameId}/move/{move}`) under very fast time controls (e.g., bullet), which is the most latency/throughput-sensitive path for a bot; this is a meaningful gap for anyone tuning move-submission retry logic.
