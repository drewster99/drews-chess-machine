# CLAUDE.md

## What this project is

A from-scratch chess engine trained in a Swift/SwiftUI macOS app; the network runs on MetalPerformanceShadersGraph (MPSGraph) on Apple Silicon.

**No search of any kind** — no Monte Carlo Tree Search (MCTS), alpha-beta, minimax or rollouts. A move is one forward pass: 4864 policy logits + the value head; the CPU masks illegal moves, temperature-scales, softmaxes and samples. Strength comes entirely from the network. Search is an explicit non-goal: do not add it or suggest "for MCTS you'd…" edits (rationale: `documentation/chess-engine-design.md` "My Goal", `documentation/sampling-parameters.md` "Sampling method"). No opening book. Training data: GUI self-play, corpus replay of imported PGN games (`--import-pgn` → `--replay-corpus`), and `--train-vs-uci` distillation from external engines.

The main window is an interactive training console (auxiliary windows: combined-loss, log analysis): build a network, run Play-and-Train (N self-play games feeding a replay buffer while a trainer consumes batches), run arenas (candidate vs champion) and promote by `arenaPromotionCriterion` (SPRT by default).

## Build / run

- Build/run only through **drews-xcode-mcp**; never `xcodebuild` / `swift build`.
- Project `DrewsChessMachine/DrewsChessMachine.xcodeproj`, scheme `DrewsChessMachine`, macOS only.
- A pre-Compile Run Script (`DrewsChessMachine/generate-build-info.sh`) bumps `DrewsChessMachine/build_counter.txt` and regenerates `DrewsChessMachine/DrewsChessMachine/App/BuildInfo.swift` every build. Both show as modified after any build; never hand-edit `BuildInfo.swift` or fight the counter.
- XCTest target `DrewsChessMachineTests` covers pure logic and many MPSGraph graph-level behaviors. Add tests for any new pure-logic component with correctness invariants. What XCTest can't reach is checked with the Run Engine Diagnostics menu command and the session log.

### Running the tests

The full suite is slow — about an hour cold (mostly the cold build-for-testing; execution ~19 min, measured 2026-06-29 at 865 cases; ~3,390 test methods now).

- **Usually run only the class/method you're touching** (`DrewsChessMachineTests/<Class>[/<method>]`); once the target is warm, those runs are quick. Run the full suite before merging, or after changes to graph builders (`ChessNetwork`), training math (`ChessTrainer`), persistence/serialization or move generation.
- **Forensic suites are gated** behind env var `DCM_RUN_SLOW_TESTS` (`1`/`true`; `DrewsChessMachineTests/SlowTestGate.swift`): `MacOS27NaNIsolationTests` (~11.6 min, ~60% of execution; precision×batch×step NaN matrix) and `ConvKernelExecutionPathNumericsTests` (~37 s, Winograd-blowup refutation). They are bug maps, not correctness gates; gating both cuts execution from ~19 to ~7 min. **The scheme's test plan turns them ON**: `DrewsChessMachine/DrewsChessMachine.xctestplan` "Test Scheme Action" sets `DCM_RUN_SLOW_TESTS=1`, so scheme runs (Xcode or `run_project_tests`) include them; disable that entry (Edit Test Plan ▸ Configurations ▸ Environment Variables) to leave them out.
- **Heavy core suites stay ungated** (they assert correctness): `PolicyHeadCorrectnessTests` (~92 s), `CheckpointManagerSafetensorsTests` (~89 s, bit-exact round-trips), `MomentumOptimizerTests` (~86 s), `RuntimeArchReachTests` (~52 s). Trim slow cases rather than gating a class.
- **Private `UserDefaults` in tests:** use `makeTemporaryDefaultsSuite()` / `makeTemporaryDefaults()` (`DrewsChessMachineTests/TemporaryDefaultsSuite.swift`; suite in its own temp folder, removed at teardown). Never `UserDefaults(suiteName:)` + `removePersistentDomain(forName:)`: it leaves an empty plist in `~/Library/Preferences` that `cfprefsd` writes back even after deletion.
- **Gating a new forensic suite:** `override func setUpWithError() throws { try SlowTestGate.requireEnabled("<label>") }` (skips with a reason naming the env var). Never gate a suite that pins a correctness invariant.

## Where to look for runtime state

The terminal console has only SwiftUI chart warnings and bring-up noise. Telemetry goes to the session log:

- `~/Library/Logs/DrewsChessMachine/dcm_log_YYYYMMDD-HHMMSS.txt`, one per launch (same-second launches get `-2`, `-3`, …). A test run never writes there: an XCTest host (`XCTestHostDetection`, the one test-run signal) logs to `$TMPDIR/DrewsChessMachine-XCTest-SessionLogs/run-<stamp>-pid<pid>/`, left in place (`SessionLogger.Location.forProcess`).
- `get_runtime_output` returns output only after the app terminates; while running, read the log file.
- Lines are timestamped. Tags:
  - `[APP]` launch banner (build + git); `[BUTTON]` user actions.
  - `[STATS]` training snapshot on the shared step-line cadence (`Training/TrainingStepLineSchedule.swift`): first observed trainer step, every 50 steps through 1000, every multiple of 1000, and the first step ≥ `step_line_interval_sec` (default 180 s, live) after the previous line. `[REPLAY]` / `[VS-UCI]` step lines use the same schedule keyed on the trainer step; every line after a segment's first carries the diagnostics. `[BATCH-STATS]` is written only with step lines.
  - `[ARENA]` start/end, W/L/D, kept vs promoted. `[ALARM]` (e.g. policy entropy below threshold).
  - `[CHECKPOINT]` saves; each session-save line ends `buffer=included replay=…` or `buffer=omitted`.
  - `[RESUME]` one `EXACT` or `NOT EXACT: <gaps>` verdict per resume; corpus replay and train-vs-UCI `--resume-exact` refuse unless `--accept-inexact <gaps>` names every gap. A changed build/OS/Mac (hardware model, chip, VM flag, GPU name) logs `[RESUME] build|OS|device changed …` and is a `build` / `os` / `device` gap when the behavior fingerprint doesn't match (including unrecorded or not comparable). Corpus replay also logs `[RESUME] replay buffer capacity: …` (a `params` gap) or `[RESUME] buffer fill not checked: …`.
  - `[REPLAY] refused:` / `[VS-UCI] refused:` — CLI run refused at launch, exit 2.
  - `[ARCH] size guidance (<event>)` — parameter count vs this Mac's memory, `verdict=within_recommended|trains_at_batch_N|likely_too_large|exceeds_physical_memory` (`--new-model`, `--derive-model`, GUI builds).
  - `[RUN]` run provenance (see "Run provenance").
  - `[LAYER-HEALTH]`, `[HEALTH]`, `[ALARM] health …` — see "Training observability".
  - `[GRAD-CLIP]` relative gradient-norm cap (`Training/RelativeGradientCap.swift`): `config mode=… k=… N=… W=… floor=… hardMax=…` at each run start, then one line per step whose pre-clip norm exceeded the cap fed to the graph (`applied=true`, hard-max clips included) and, in log-only mode, per step the rule would have clipped (`applied=false`). Step lines carry `gNormMax=` / `clips=` / `gCap=` since the previous line.
  - GPU faults (see "GPU faults"): `[GPU-ERR]` a checked submission failed (stage, first / last command-buffer status, completion-handler error, Metal domain/code/text); `[GPU-SLOW]` a command buffer ran ≥ 5 s on the GPU; `[GPU-SYSLOG]` macOS's own fault message for this process (hang / discarded buffer), or the monitor's start / unavailability; `[GPU-FAULT]` the GUI acting on one; `[SP-TICK] GPU fault reported: abandoned …`; `[ARENA] voided: GPU fault`.
  - `[MEM]` memory and thermal state (`Utils/MemoryStatusMonitor.swift`): footprint, GPU allocated / recommended max, swap used / total, pressure, thermal, and the GPU fault monitor's poll cost; at start, every 10 min, and on every pressure or thermal change.
  - `[BATCH-HASH] trainerStep=N batchHash=<16 hex> batchChain=<16 hex | partial>` every 100 trainer steps (`Training/BatchHashChain.swift`); compare two runs with `scripts/compare_batch_hashes.py`.
  - `[CRASH-DUMP]` / `[CRASH-DUMP-ERR]` a crash dump written (or not); read one with `scripts/dcm_crash_dump.py`.

## Training parameters

All tunable training parameters (108; 89 `liveTunable`) live in the `@MainActor @Observable` singleton `TrainingParameters.shared` (`DrewsChessMachine/DrewsChessMachine/Training/TrainingParameters.swift`). Each is declared with the `@TrainingParameter` macro (local SwiftPM package `DrewsChessMachine/Packages/TrainingParametersMacro/`), which generates `id`, `definition` (range, category, liveTunable), `encode` / `decode` and `absentValue`. Persistence is hand-written per property.

### Adding / removing / renaming a parameter — full checklist

Several touchpoints are manual, and drift between them fails silently at runtime, not at build. **Walk all of these every time:**

1. **Declare it.** `@TrainingParameter(...) public enum FooBar: TrainingParameterKey {}`, add it to `allKeys`. **Declare `absentValue:`** (required by the protocol) — what a resume applies when a checkpoint lacks the key (`TrainingParameterAbsence`): `.preFeature(<value the run factually used before the feature existed>)`, `.declaredRangeMaximum` (pre-feature behavior was "unbounded"), `.currentSetting` (operational knob, no effect on training math), or `.refuseExact` (training math with no known value: exact resumes refuse; the GUI uses the live setting and reports NOT EXACT).
2. **Wire the singleton.** Stored property with `didSet` → `commitAssignment`, the `init` read (`self.fooBar = Self.read(FooBar.self)`), entries in `collectValues` / `applyOne`, and the snapshot's read accessor.
3. **`parameters.json`.** Confirm the key appears in `--show-default-parameters` and that `--create-parameters-file` → manual edit → reload round-trips (macro-generated, but check nothing is hand-listed in the CLI path).
4. **Session save/load (`.dcmsession`).** Optional field on `SessionCheckpointState` (`Persistence/SessionCheckpointFile.swift`; Optional so older sessions decode), pass it through `buildCurrentSessionState` (`SessionController+Checkpoint.swift`), and add one `restore(FooBar.self, saved: rs.fooBar, into: \.fooBar)` line (`savedFloat:` for a trainer `Float`) in `SessionParameterResume.applyGuiSession(_:acceptedReplacements:)` (`App/SessionParameterResume.swift`, the GUI resume's one parameter block). It resolves through `TrainingParameterResolution` (the key's `absentValue` decides when the session is silent) and logs one `[RESUME-DIFF] <id>: saved=… applied=… current=… (<reason>)` line. Session values are saved; pre-feature values are held for the run only (never written to `UserDefaults`) and released (`TrainingParameters.releaseRunHolds`, logged `[PARAM] values held for the previous resumed run released …`) when the next Play-and-Train start that isn't a continue after Stop begins; any other assignment of the key during the run ends its hold; live-setting sources are untouched. The trainer is configured from the settings through `TrainerHyperparameters`, so trainer-level parameters need no extra resume wiring beyond step 2.
5. **`results.json` / `CliTrainingRecorder`.** If it affects sampling, training math or anything a CLI/autotrain run compares, surface it in the recorder snapshot (e.g. `BatchStatsSnapshot.samplingConstraints`).
6. **Runtime log.** Make its value (or a derived observable) visible in `[STATS]`, `[SAMPLER]`, `[BATCH-STATS]` or similar, so a misconfiguration is visible mid-run.
7. **UI position.** Place it in `TrainingSettingsPopover.swift` (or another popover/control if not a training-loop knob) with a binding + validation entry in `TrainingSettingsPopoverModel.swift`. No UI = reachable only via `parameters.json`; make that choice deliberately.
8. **Live tunability.** If `liveTunable: true`, confirm the consumer reads `TrainingParameters.shared` live (a periodic reconcile loop, or a `ControlSideEffectsProbe` `.onChange` push) instead of caching a session-start snapshot.
9. **Renames.** Change the `id` (snake_case `UserDefaults` / JSON key) **and** the Swift property name. Old `UserDefaults` entries are then ignored and the preference silently resets to default — say so in the commit message; no migration code unless asked.

Reading values:
- **SwiftUI:** read `TrainingParameters.shared` directly (it's `@Observable`; e.g. `UpperContentView`'s `private let trainingParams = TrainingParameters.shared`). Settings popovers edit drafts through `TrainingSettingsPopoverModel` / `ArenaSettingsPopoverModel`.
- **Off-main / structured concurrency:** `let p = await TrainingParameters.shared.snapshot()` at a session boundary (`Sendable`, immutable, lock-free; UI changes appear in the next snapshot). Long-running consumers that must follow live edits read `.shared` instead — e.g. `selfPlayConcurrency`, `trainingStepDelayMs`, `selfPlayDelayMs`, `replayRatioTarget`, `replayRatioAutoAdjust`, `periodicAutosaveIntervalSec`, `stepLineIntervalSec`, the arena interval/threshold/game count, `sessionSaveIncludeReplayBuffer`.

Caps on self-play workers, `self_play_delay_ms` / `training_step_delay_ms` (0…3000) and `arena_concurrency` (1…1024) are the declarations' upper bounds (the `UpperContentView` statics derive from them). Change the declaration, never a separate constant; no loader or resume clamps them.

Persistence: `didSet` → `commitAssignment`, which validates (a bad value logs `[PARAM-REJECTED]` and reverts), writes `UserDefaults` under the id unless `suppressPersistence` is set (CLI loads, run holds), and keeps out-of-range session values in memory only; `init` reads back (validated). No `@AppStorage` for training parameters.

CLI:
- `--help` / `-h` prints usage to stdout, exit 0.
- `--show-default-parameters` — flat snake_case JSON to stdout, descriptions to stderr; no GUI.
- `--create-parameters-file [path] [--force]` — writes `parameters.json` and `parameters.md`. `path` is a folder (existing, or ending in `/`) or the `.json` file (a `.md` extension in any case is refused). An existing file needs `--force`, which replaces regular files only and refuses anything else.

### Run provenance (`[RUN]`)

Every run path logs exactly one `[RUN]` line at start, formatted by `RunProvenanceLine` (`Logging/RunProvenanceLine.swift`; determinism plan D4): GUI Play-and-Train / `--train` at every start (including a continue after Stop), `--replay-corpus`, `--train-vs-uci`, `--derive-model`, `--uci`. Fields: path; lineage run ID and segment index with how the segment began (fresh, branch from / exact resume of / derived from `<model_id> sha=<12>`, or a not-exact resume with its gaps); build/git/dirty/`git_diff`; device/VM/OS; seed fields (`seed=… mode=seeded|seeded(--seed)|unseeded(drawn)|resumed(<origin>) derivation=v1`); parameter-snapshot hash; `policy_tail`; starting totals `cum_step` / `cum_games` / `cum_train_sec` (`unrecorded` where no predecessor recorded one); redacted argv. Inapplicable values are `none`. The seed's `[PARAM]` notes come just before it; a continue after Stop also logs `[RUN-SEED] continuing …` with the game serials. `results.json` (CLI runs and GUI `--train`) carries the run's last-save lineage as top-level `lineage` (the record minus `segments` / `derivation_history` / `ancestry`, plus `checkpoint_sha256`; GUI `--train` reports the record at its last stats tick, no file hash) and per-row `cum_trainer_step` / `cum_train_step_sec` / `cum_games`. A file's `derivation_history` is in its lineage record, carried verbatim by every later save (only `--derive-model` appends), with a flat `derivation_history` metadata mirror.

### Run seed

Every training run (GUI Play-and-Train, `--replay-corpus`, `--train-vs-uci`) resolves one **master seed** at start via `RunRandomSeed.resolve` (`Training/RandomSeedMode.swift`), logged on `[RUN]` and in `results.json` (`random_seed` / `random_seed_mode` / `rng_stream_derivation`). Settings (Sessions tab): `random_seed_mode` (`0` = draw a seed, default — still logged, so any run can be repeated with `--seed`; `1` = use `random_seed`) and `random_seed` (`UInt64`, JSON decimal **string** so values above 2^53 survive). `--seed <n>` (with `--train`, `--replay-corpus` or `--train-vs-uci`) overrides both for the process. Digits only: a sign (`+5`, `-0`) is refused everywhere (`UInt64(strictDecimal:)`, the one parser). Every training-relevant draw comes from a named stream (`DCMRandomStreams`, plan Part A3): `sampler`, `selfplay.game.<serial>`, `arena.<arenaIndex>.game.<g>`, `vsuci.game.<serial>`, the trainer's `dropout` (the GUI trainer outlives runs; each run hands it its stream via `ChessTrainer.beginDropoutStream`), `probe.entropy_by_bucket.<step>`. Game serials are assigned in serial passes in slot order, never inside the parallel tick, so a game's moves don't depend on how many games run beside it. **Never add a draw from `SystemRandomNumberGenerator` / `Int.random` / `.shuffled()` to a training path** — take a stream and pass the generator explicitly (no defaulted generator arguments). Interactive play, UCI, the Lichess bot and network-load scratch containers deliberately use the system (`DCMRandom.seededFromSystem()`, `NetworkInitMode.overwrittenByLoad`). Stop + continue keeps seed and serials. A GUI session resume continues the saved seed, serials, arena count, sampler and dropout positions when the trainer file's record carries them and the seed can be inherited; otherwise (no streams, `--seed` naming another seed, another derivation) it draws (or uses `--seed`), logs `[RESUME] rng: the saved run's seed is not continued; …`, and reports `rng_sampler` / `serials` NOT EXACT. It never changes the seed settings.

## Saved model state

`CheckpointManager` writes model files (`.safetensors`; legacy `.dcmmodel` readable) as `<YYYYMMDD-HHMMSS>-<modelID>-<trigger>.<ext>` under `~/Library/Application Support/DrewsChessMachine/Models/`, and session folders as `<YYYYMMDD-HHMMSS>-<sessionID>-<trigger>.dcmsession` under `…/Sessions/`. **`CheckpointManager` never overwrites** — every save is new (the CLI rolling `--out-model` is the one replaced-in-place file; see "Run tracking"). Design and bit-exact save verification: ROADMAP.md (completed save/load items).

GUI `.dcmsession` triggers (disk tag in the folder name):

- **`manual`** — File ▸ Save Session.
- **`promote`** — automatic after each arena promotion (`autosaveSessionsOnPromote`, a hard-coded `true`), reusing the weight snapshots taken under the arena's pauses; logged `Saved session (post-promotion)`. Train ▸ Promote Trainee Now writes the same tag (`SessionSaveTrigger.promotionDiskTag`, via `saveSessionInternal` with fresh exports), is treated like an arena promotion, and logs `Saved session (promote)`.
- **`periodic`** — interval autosave during Play-and-Train (`periodicAutosaveIntervalSec`, default 6 h, live from the Sessions tab; the heartbeat re-anchors `PeriodicSaveController` via `updateInterval`). A deadline inside an arena is deferred, then swallowed if a post-promotion save landed meanwhile, else fired late. Any successful save resets the clock.
- **`sigusr2`** — SIGUSR2 signal save.

**`--train-vs-uci` saves session folders** (same `CheckpointManager.saveSession`, into `--out-session-dir`, tags `vsuci-periodic` / `vsuci-final` / `vsuci-abort` / `vsuci-health-stop`, `path_kind` `vsuci`; the GUI refuses to load them via `SessionCheckpointState.guiLoadRefusal`). Full rules: `documentation/UCI.md` "Output: session folders".

**Automatic-save retention is off by default and forced off in this build.** Pruning runs only when `CheckpointPaths.automaticSavePruningDecision` allows: kill switch `CheckpointPaths.automaticSavePruningForcedOff` unset, `automatic_save_pruning_enabled` (default `false`; Sessions tab "Prune old autosaves") on, and `maxPeriodicAutosavesKept` > 0. **The kill switch is `true` by owner decision 2026-10-01**, pending D-8 (saves omit the replay buffer by default) and more confidence in automatic deletion, so no automatic save is ever deleted; the toggle shows disabled ("Disabled in this build"), and `AutomaticSavePruningGateTests` pins the constant. Each periodic/`-promote` save that doesn't sweep logs `[PRUNE] skipped after <folder>: off: <reason> (…)`; Play-and-Train start logs `[PRUNE] automatic-save pruning at Play-and-Train start: …`. When allowed: after each successful periodic or `-promote` save (`scheduleAutomaticSaveRetentionSweep`, kind from the disk tag via `CheckpointPaths.AutomaticSaveKind`), `CheckpointPaths.pruneAutomaticSaves` keeps the newest `maxPeriodicAutosavesKept` of one global pool of `-periodic` / `-promote` folders, sorted by full folder name (timestamp first). Never deleted: `-manual` / `-sigusr2`, the just-written save, the `LastSessionPointer` target (a protected folder beyond the cap keeps its rank). Deletion uses `FileSafety.removeOwnedItem` with the identity recorded at inspection. A failure logs `[PRUNE-ERR]` and doesn't abort the sweep, except an unreadable `LastSessionPointer`, which aborts it before listing. Membership checks, log lines and history: `documentation/disk-cleanup.md`.

**Every model file carries its weights' puzzle test-set results** (owner decision 2026-10-07; `documentation/plans-completed/TEST_SET_RESULTS_METADATA_PLAN.md`). `__metadata__["dcm_test_set_results"]` is one JSON object (`ModelTestSetResultsField`, schema 1): per bundled set (`LichessProbeData.modelFileTestSets`: `lichess-200`, `lichess-wide`, each with title, description and a puzzle-list `fingerprint_sha256`), pElo (or a `pelo_bound` when every answer is right or wrong), NLL, positions, top-1 / top-5 counts, average probability and rank of the right move, and per-theme correct / total. Every writer evaluates the exact weights it writes **before** encoding (`ModelTestSetEvaluator`, a fresh inference network per evaluation; the same fold as `--probe-model`), so the results are in the file's only write: `SafetensorsModelIO.encode` requires `testSetResults:`, `CheckpointManager.saveModel` / `saveSession` require a `ModelTestSetEvaluating` (a session save evaluates `champion.safetensors` and `trainer.safetensors` each on its own weights, after the replay buffer is written so held self-play doesn't wait), and derive / graft require a `testSetEvaluation` (source results are never copied). A failed evaluation never fails a save: the file records `status: failed` with the reason and the log says `[CHECKPOINT-ERR] test sets …`; a success logs `[CHECKPOINT] test sets <file> (<ms> ms): …`. Older files read as not recorded; an unreadable value is reported, never a load error. Pickers show the largest set's pElo / NLL / top-1 / top-5 (`ModelTestSetSummary`); `manifest.json` carries both files' summaries; Python: `scripts/dcm_lineage.py` `test_set_results`. No backfill of existing files (owner, 2026-10-07). Each writer checks everything else first (`SafetensorsModelIO.prepare`, before any evaluation and, in a session save, before the replay buffer), and identical base weights are evaluated once per process (`ModelTestSetMemo`: a session's champion when it equals the trainer's base weights, a train-vs-UCI final save, an unchanged GUI champion), logged "reused the evaluation made for <file>". A non-finite forward pass is a failed evaluation, never numbers. Tests that write files directly (`SafetensorsModelIO.encode`, `CheckpointManager.saveModel`/`saveSession`, derive, graft) use `ModelTestSetFixtures` overloads that record an explicit "test fixture: not evaluated"; the corpus-replay and train-vs-UCI runners evaluate for real in their tests.

Every save stages under `<final>.tmp`, created exclusively — a pre-existing staging path fails with `stagingPathAlreadyExists` and is left alone; a save removes only staging it created. The GUI-launch orphan sweep (`CheckpointPaths.cleanupOrphans`) removes only expected-type staging debris (`.dcmsession.tmp`, `.safetensors.tmp`, `.dcmmodel.tmp`) and `FileSafety`'s hidden `.<name>.<UUID>.tmp` files (regular files, `FileSafety.destinationName(ofTemporarySiblingName:)`) in `Models/` and `Sessions/`, untouched for `orphanStagingMinimumAge`, so a second instance can't delete live staging; removals are identity-checked. Staging elsewhere is never auto-cleaned (`documentation/disk-cleanup.md`).

**GUI session saves include `replay_buffer.bin` (7–11 GB observed) only when asked** (#8, decision D-8, `documentation/plans-active/DETERMINISM_RESUME_LINEAGE_PLAN.md`): automatic saves (periodic, post-promotion, Promote Trainee Now, SIGUSR2) follow `session_save_include_replay_buffer` (default off; Sessions tab "Include replay buffer"); File ▸ Save Session's sheet checkbox starts from it. A resume without a buffer refills from new games, `[RESUME] NOT EXACT: buffer`. Train-vs-UCI omits the buffer unless `--save-replay-buffer` (the GUI parameter doesn't apply); an exact resume from a session with one restores it. Per D-1, GUI and train-vs-UCI resumes are state-exact at most; only corpus replay continues the uninterrupted run's random streams and feed exactly; weights match bit for bit only where MPSGraph steps are deterministic, not on a shared GPU (determinism plan, seventh pass). Corpus-replay `--resume-exact` refuses when the run already used the epoch budget (`--epochs`, default 1, counted from the lineage start), the saved corpus position is outside the corpus, the rebuilt buffer holds fewer positions than the saved one, the re-feed ends early, or a shard is unreadable.

**File lineage (`LineageRecord`, architecture format v7, session.json v2).** Every model file a training path, `--new-model` or `--derive-model` writes carries one `LineageRecord` as JSON in `__metadata__["dcm_lineage"]`, plus write-only flat mirrors (`lineage_run_id`, `lineage_segment_index`, `cum_trainer_step`, `cum_games_fed`, `cum_train_step_sec`, `git_dirty`, `lineage_segment_local_step`, `derivation_history`). A session's `trainer.safetensors` and `session.json` carry the run's record at the save; `champion.safetensors` carries the champion weights' own record — a mint record if built in-process, else its load or promotion record without trainer state, or `untrainedCopyRecord` for a champion loaded from a pre-lineage file (`SessionController.championFileLineageRecord`); a champion with no recorded origin fails the save. No record or file carries a placeholder model ID: a missing or empty file `model_id` (`__metadata__`) is a decode error. The record holds:
- run and segment: `lineage_run_id` minted on fresh / branch / derive and on a resume of a pre-lineage file, inherited by every exact resume; `segment_index` +1 per resume;
- the parent file (`model_id` + `content_sha256`);
- **this run's** totals, continuous across its sessions (a branch restarts them, a derive continues its source's): `cum_trainer_step` (on a trainer-state file equal to `trainer_completed_steps`), `cum_games`, `cum_positions`, `cum_train_step_sec` (Σ measured trainer-step time), `cum_wall_sec`. Totals behind the weights themselves, including branched-from runs in `ancestry`: `scripts/dcm_lineage.py` `weights_totals`;
- the corpus position for corpus replay (what `--resume-exact` resumes from; pre-v7 files keep `replay_*` keys);
- the full parameter snapshot, build, argv (secrets redacted), device;
- `rng.dropout_philox_state` captured with the trainer snapshot (restored by every exact resume; `null` without trainer state; a promotion rewinds it with the trainer's weights and clock);
- a summary of every earlier segment.

Built in one place: `LineageTracker` (one per segment per path; GUI wiring in `SessionController+Lineage.swift`). A total a predecessor never recorded is JSON `null` forever, never reconstructed; a pre-v7 file reports lineage unrecorded. A resume lists what it did not restore in `not_exact_items` (`ResumeGap` tokens, `Training/ResumeExactness.swift`). Design: determinism plan Part D.

**Lineage schema 3 (hyperparameter recording P4).** `LineageRecord.currentSchema` is 3; schema 2 is still read (`oldestDecodableSchema`) and never written back as 2 (`withoutTrainerState`, a tracker or a copy converts it). A record with training behind it adds, beside `parameters` (whose snapshot never holds the seed settings, O-9):
- `configuration`:
  - `path_kind` and `policy_tail_precision`.
  - `budget`: the limits the path enforces. Corpus replay refuses a parameters file's `training_time_limit` (O-21).
  - `parameter_changes`: every committed GUI settings edit, with the trainer step it takes effect at, from the `TrainingParameters` commit hook. A key captured at run start is journalled at the next start's recapture. A promotion re-stamps later edits to the rewound step and keeps `restamped_from`.
  - `champion_changes`: `segment_start`, `arena`, `manual`, `loaded_model`.
  - `vsuci`: ply cap, eval-sync cadence, the trainer's move selection, and for each opponent pool its command, executable SHA-256, options and handshake `id` lines.
  - `self_play_dirichlet` and `start_value_head_recentered`.

## High-level architecture

### The self-play → train → arena loop

One Play-and-Train run runs in parallel:

1. **N self-play games** in the tick-based `BatchedSelfPlayDriver` (live Stepper, bounded by `UpperContentView.absoluteMaxSelfPlayWorkers`). One task runs the loop; each *tick* advances all K games one ply in lockstep: parallel-encode K positions, one batched `network.evaluateBatched(...)`, parallel sample + apply one move per game, then a serial game-end pass flushes finished games into `ReplayBuffer` in one bulk copy. Per-game state is an `ActiveGame` (no per-game `Task`, no actor barrier; grow = append, shrink = `removeLast`). The removed per-slot batcher's history: `BatchedSelfPlayDriver`'s class doc.
2. **One trainer** (`ChessTrainer`) sampling minibatches from `ReplayBuffer.sample(count:)` and running MPSGraph SGD steps on a training-mode copy of the network.
3. **`ReplayRatioController`** — when `replayRatioAutoAdjust` is on (default off), drives `cons/prod` toward `replayRatioTarget` (default 0.48) by adjusting either the training-step delay or the per-game self-play delay, one at a time (`computedDelayMs` / `computedSelfPlayDelayMs`). `[STATS]` reports it in `ratio=(target=… cur=… prod=… cons=… auto=on/off delay=…)`.
4. **Arena** (`TickTournamentDriver`) every `arena_auto_interval_sec` (default 900 s) or on Train ▸ Run Arena. Self-play (`selfPlayGate`) and training (`trainingGate`) pause briefly at arena start while the trainer's weights go into `candidateInferenceNetwork` and the champion's into `arenaChampionNetwork`; both then keep running during the tournament, played with the arena `SamplingSchedule`. Promotion rule `arenaPromotionCriterion`: **SPRT** by default (`elo0` vs `elo1`, plays until a bound is crossed; `documentation/arena-sprt.md`), or score threshold (`arenaGamesPerTournament` games, promote if score ≥ `promoteThreshold`, default 0.53). On promotion (self-play briefly re-paused), the candidate's weights go into the live champion, and the trainer rewinds to its arena-start state — candidate weights (fp32 masters re-seeded), velocity, clock, dropout state, gradient-norm history (`trainer.rewindToArenaStart`) — so both converge on the arena-validated snapshot.

### Networks are singular

- `network` — the live champion; self-play's evaluator; source of the arena-champion snapshot.
- `trainer.network` — inside `ChessTrainer`, training-mode BN; the only source of arena-candidate weights. Forked from `network` on a fresh start, loaded from the session's trainer safetensors on resume, rewound to the arena-start candidate on promotion.
- `candidateInferenceNetwork` / `arenaChampionNetwork` — inference-mode, lazily built on first Play-and-Train start and reused across sessions (rebuilt when the champion's architecture changes); receive the trainer's / champion's weights at each arena start.

No per-worker inference networks: the original design ran one self-play worker against `network`; going to N workers added the shared batched evaluator instead.

### MoveEvaluationSource abstraction

Interactive single-game players (`MPSChessPlayer`) hold a `MoveEvaluationSource`, not `ChessMPSNetwork`: `DirectMoveEvaluationSource` → single-position `network.evaluate(board:)`, used by Play Game / Human-vs-Network and `--uci` (via `UCIEngine`; `LiveTrainerMoveEvaluationSource` / `UIGatedMoveEvaluationSource` wrap it). **Self-play and the arena don't use it:** their tick drivers (`BatchedSelfPlayDriver` / `TickTournamentDriver`) call `evaluateBatched` once per tick and sample inline via `MoveSampler`.

### Board encoding and policy space

- **Input** (per model, `NetworkArchitecture.inputEncoding`; a model keeps its encoding), always from the side to move. Encodings: `basic20`, `basic24`, `basic30`, `full10ply200`, `full10Ply10Reps210`. **`basic30`** (built-in presets and most existing models): 30 planes × 8 × 8 NCHW — 0-15 pieces + castling, 16 en passant, 17 halfmove clock `min(clock, 99) / 99` (Leela), 18-19 threefold-repetition counts (≥1×, ≥2× before), 20-29 repetition pattern (plane `20 + i` all-1 iff the position `i + 1` plies ago is a strict duplicate — PositionKey: board + STM + castling + EP); the 10-ply history clears on any irreversible move. Planes 20, 21, 22, 24, 26, 28 can never be 1 (issue #10). Plane 19 never fires in a self-play sample (the threefold draw is adjudicated first) but does, rarely, in corpus replay and wherever an outside authority decides draws (Lichess bot, `--uci`). **New models default to `basic24`** (`NetworkArchitecture.newModelDefault`, used by Build New Model / Build Network): planes 0-19 unchanged, 20-23 = repetition 4, 6, 8, 10 plies ago (`InputEncoding.possibleRepetitionPlyDistances`). Plane tables: `BoardEncoder.swift` and the `InputEncoding` docs.
- **Policy:** 4864 logits = 76 channels × 64 squares, AlphaZero shape: 56 queen-style (8 directions × 7 distances) + 8 knight + 9 underpromotion + 3 queen-promotion; index `channel * 64 + row * 8 + col` in the encoder frame (vertically flipped for black). Every move ↔ index conversion goes through `PolicyEncoding.swift`; there is deliberately no `policyIndex` on `ChessMove`, so callers must think about the side to move.
- **Value:** 3-logit W/D/L head (`[win, draw, loss]`), categorical cross-entropy against a label-smoothed one-hot of the result (`value_label_smoothing_epsilon`, default 0.013). The scalar `v = softmax(logits)·[+1, 0, −1] = p_win − p_loss ∈ [−1, +1]` (no tanh), relative to the side to move. W/D/L since 2026-05-12, replacing a `tanh` scalar + MSE that went silent on a draw-heavy buffer (`documentation/wdl-value-head.md`, CHANGELOG 2026-05-12); `scalar_tanh` (MSE) remains a supported `ValueHeadStyle`, unused by presets.
- **Architecture is per model, runtime-configurable** — every model embeds its `NetworkArchitecture` (single source of truth; `NetworkArchitecture.swift`, `documentation/plans-active/RUNTIME_ARCHITECTURE_CONFIG_PLAN.md`). Shape: stem → ordered **block groups** (`blockGroups: [BlockGroup]`, each a count + per-group recipe: channels, both conv kernels, SE style/ratio/β init, SE FC1 activation (`se_activation`, independent of the main path, issue #2), `use_rezero`, ReZero α init (`rezero_alpha_init`; `0` is legal) and cap (`rezero_alpha_cap`, asymptote C of `C·tanh(α/C)`; `documentation/rezero-alpha-clamp.md`), activation function/style, skip merge, `output_norm`, dropout multiplier, init-neutral options `se_gamma_bias_init` / `branch_output_init` / `skip_projection_init`) → tower-end BN + activation (pre-act tail only) → policy + value heads, with an optional stem→heads feature skip. Towers may be **heterogeneous** (WRN-style width staircase): a width change gets a bias-free 1×1 skip projection. The engine consumes the flattened `expandedBlocks`; uniform towers build byte-identically to the pre-block-groups code. Policy head styles: simple_conv / intermediate_conv / fc_bottleneck. Default preset `v4_5block_7x7` (5 blocks, 7×7, 128 ch, ~8.45M params). Build via Build New Model (per-group editor + `ArchitectureDiagramView`). SE blocks match modern lc0 practice. Design: `documentation/plans-completed/ARCHITECTURE_EXPANSION_PLAN.md`; graph builders: `ChessNetwork.swift`.
- **Architecture format** (`Network/ArchitectureFormat.swift`, current v12): fields added later are gated by the carrier's format version. An older file without a field resolves to the pre-field behavior, logged once as `[ARCH] legacy file …`; a current-version file without it is a load error. v4 requires `se_beta_init`; v5 `se_activation`; v6 `rezero_alpha_cap` (older files: `rezero_alpha_init × rezeroTanhCeilingMultiple`, the C the engine derived before); v7 adds no field but requires a `dcm_lineage` record in every safetensors model file; v8 requires the init-neutral options (per group `se_gamma_bias_init`, `branch_output_init`, `skip_projection_init`; heads `policy_head_final_init`, `value_head_final_init`, `value_head_draw_prior`) — older or pre-block-groups uniform-tower files resolve to the standard init; set by Build New Model's Neutral init / Standard init buttons and `--derive-model --set-neutral-init` / `--set-<option>` (`documentation/deriving-models.md`); v9 replaces top-level `activation_function` with one activation per site (`stem_activation`, `tower_end_activation`, `feature_skip_activation`, `policy_head_activation`, `value_head_conv_activation`, `value_head_fc1_hidden_activation`) — a site the topology lacks holds `does_not_apply` (never an identity activation), older files resolve each site from `activation_function`; v10 applies that rule to an SE-less group's `se_activation` (an older file's value resolves to `does_not_apply`); v11 adds no field: `training_step` is the trainer step (on a trainer-state file equal to `trainer_completed_steps`; writer and reader refuse a mismatch) and the segment step is the lineage `segment_local_step`; older files are read by their writer's meaning (`ModelFileStepReading`, by `creator`), flagged once `[ARCH] legacy file`; builds before v11 refuse every v11+ file, presets and `architecture.json` included; v12 adds `policy_tail_precision`.
- **Model size is guidance, not limits** (owner decision 2026-10-03): `validate()` has no size upper bound (it refuses structural errors, non-positive counts, and `Int` overflow computed per group with checked arithmetic without expanding the tower). `ModelSizeGuidance` scales to physical memory (64 GB reference: 15M params recommended, batch 4096 up to 20M, `20M × √(4096 / batch)` down to batch 512, "likely too large" beyond); its one refusal is a training state (16 B/param) larger than physical memory, applied by Build New Model, `--new-model`, a graft and the GUI build.
- **Policy tail precision is an architecture field** (owner decision 2026-10-07; `documentation/plans-active/POLICY_TAIL_ARCHITECTURE_PLAN.md` holds the full rules). `NetworkArchitecture.policyTailPrecision` (`PolicyTailPrecisionSetting`: `fp32_from_pre_bn` / `mixed_final_projection`; `does_not_apply` exactly on fp32, enforced by `validate()`) changes the built graph like `computeDataType`; `computeDataType` is `private(set)` and changes only through `withComputeDataType(_:tail:)`. Format v12 adds it; set in Build New Model or `--derive-model --set-policy-tail-precision <value>` on a plain model (no tensor rewritten). A pre-v12 file resolves to the tail it records — `trainer_policy_tail_precision`, else lineage `configuration.policy_tail_precision` (both present and different: refused; `SafetensorsModelIO.decodeArchitecture(fromMetadata:source:)`) — else `mixed_final_projection` (`does_not_apply` on fp32). Unrecorded fp32-tail-era files are audited (tail from the writing build's default, overridden by launch-flag evidence); owner-approved ones get a one-off in-place header edit adding only the flat `trainer_policy_tail_precision` key — no format-version change, weights untouched (PT-D3); a session's unrecorded `champion.safetensors` takes that session's trainer-file tail (PT-D3 rule 4, `CheckpointManager.decodeSessionChampionFile`). Writers no longer write the flat key; a v12 file carrying it is refused. Every network and trainer is built at its architecture's tail, inference included (a trainer file recording `fp32_from_pre_bn` plays and probes under it); the `policy_tail` resume gap is gone; the numerics audit builds bf16 and fp16 under both tails in one run. The `--policy-tail-precision` launch flag is removed (an unknown-argument error) — **never reintroduce a process-wide or launch-time precision setting.**
- Legal-move masking is CPU-side, fused into the softmax in `MoveSampler.sampleMove` (only legal logits are exponentiated); the graph emits raw logits.

### Sampling (temperature schedules)

Temperature softmax over legal logits — no top-k, no search. `tau(ply) = max(floor, start − decay·ply)` per game-total ply. The live schedules are `SamplingSchedule` values built from `TrainingParameters` and held in `SamplingScheduleBox`, re-pushed when the settings popovers are saved. Defaults (owner's running configuration as of 2026-10-01; previously self-play 1.0 → 0.5 / 0.007, arena 0.6 → 0.2 / 0.02): **self-play** and **arena** both start 0.2 → floor 0.02, decay 0.02/ply (`selfPlayStartTau` / `selfPlayTargetTau` / `selfPlayTauDecayPerPly`, `arena…`). Self-play adds Dirichlet root noise (`SamplingSchedule.selfPlay.dirichletNoise`, `.alphaZero`), its main source of opening variety; the arena has none. `.uniform` (flat 1.0) is for Play Game / Forward Pass. Details: `documentation/sampling-parameters.md`.

### ModelID identity

`ModelID` (`yyyymmdd-N-XXXX`, optional `-<generation>` suffix on a trainer) is minted at Build, fresh Play-and-Train start (trainer generation) and promotion's trainer fork (the champion inherits the candidate's ID; the trainer gets a fresh next generation forked from it); every other weight copy, arena snapshots included, inherits. The rules aren't obvious — **read `documentation/sampling-parameters.md` "Model identity" before changing when IDs change.** `[STATS]` / `[ARENA]` lines report `trainer=`, `champion=` and (during an arena) `candidate=`.

## GPU faults (owner request 2026-10-09; `documentation/plans-active/GPU_FAULT_FORENSICS_PLAN.md`)

A GPU hang in any process makes macOS reset the GPU and discard every in-flight command buffer in every process ("victim of GPU error/recovery"); a discarded buffer's outputs are garbage. Three such resets on 2026-10-09 reached no session log and fed a NaN gradient and 10M-norm gradients into training.

- **Every GPU submission goes through `GPUSubmission`** (`Network/GPUSubmission.swift`): `runGraph` / `runExecutable`, or create → encode with its execution descriptor → `commit()` → `verify()` (`waitUntilCompleted()` inside a lock section that must not throw, `verify()` after it). It checks the first and last command buffers and the completion handler, logs `[GPU-ERR]`, records the fault in `GPUFaultLedger`, and throws `ChessNetworkError.gpuCommandFailed`. **Never call `MPSGraph.run` / `MPSGraphExecutable.run` / `encode` + `commit` directly** — they report no failure. MPSGraph splits work across command buffers the app can't reach, so this is not complete on its own:
- **`GPUFaultMonitor`** (`Network/GPUFaultMonitor.swift`) polls this process's own system-log entries (`OSLogStore`, every 10 s, ≈2 s per query) for `kIOGPUCommandBufferCallbackError…` and records each in the ledger (`[GPU-SYSLOG]`). Each start counts faults logged from 60 s before it on; an older one a query returns is logged `(not counted …)`, never recorded. Stop pauses it after one closing poll (10 s later); a pause longer than the window is not read (`[GPU-SYSLOG] monitoring resumed: …`), and a fault the closing poll or a barrier after Stop records from the stopped run (logged by 10 s after Stop) taints its trainer (`StoppedRunGPUFaultWatch`, until the next start or a dropped trainer).
- **`GPUFaultWatch`** (`Training/GPUFaultWatch.swift`) is a run's view: any fault since the run started stops training (the weights may be wrong); `barrier()` (a synchronous monitor poll) runs before every save, promotion and Promote Trainee Now, and refuses them on a fault — so a run's last save is always one written before any fault.
- **Per path:** corpus replay and train-vs-UCI stop with no further save, write `results.json` (`termination_reason: gpu_fault`, `gpu_faults`) and **exit 36**; GUI Play-and-Train suspends training as `.divergence` (autosave skipped); GUI `--train` ends through `AutoTrainTermination` (`gpu_fault`); self-play abandons in-progress games; an arena with a fault in its span is voided. A non-finite halt runs the barrier first: a fault makes it a GPU fault. In the GUI, `GPUFaultTaint` (`App/SessionController+GPUFault.swift`) outlives Stop: a start that keeps a tainted trainer (continue, new session on the same trainer), a fork of a tainted champion, a save and a promotion are refused until the weights are replaced (start from a loaded session or the champion; network built; model or session loaded). `results.json` `gpu_faults` (monitor availability, faults, crash dumps) is on every CLI run and `--train`.
- **Crash dumps** (`Training/CrashDump.swift`) on a GPU-fault stop, a non-finite stop, and a near miss (pre-clip gradient norm ≥ 1,000 × the cap's reference median; at most one per 1,000 steps, training continues): `CrashDumps/<time>-<modelID>-step<N>-<reason>.dcmcrash/` with `manifest.json`, `batch.safetensors`, `log-tail.txt`, `system-log.txt`, macOS's `gpuEvent` reports when readable, then `weights-after.safetensors` + census (GPU reads last, 60 s limit; `weights-after-error.txt` otherwise). The trainer-state reads (staged batch, gradient-norm history, recent batch hashes) run at once under their own 60 s limit; a part not read is listed in the manifest's `notes` (unread batch hashes leave `recent_batch_hashes` out). Plain safetensors, never model files. Never deleted automatically; the launch sweep removes only old `.dcmcrash.tmp` staging.
- **Batch hashes** (`Training/BatchHashChain.swift`): every step's batch (boards, moves, outcomes after the draw penalty) is SHA-256'd on a utility queue (≈12 ms, off the step) and chained per 1,000-step window; `[BATCH-HASH]` every 100 steps. A corpus-replay exact resume reproduces the original's lines exactly when it trains on the same batches.
- **Limits:** 117 calls (`MPSNDArray` / `MPSGraphTensorData` creation, `readBytes` / `writeBytes`, `compile`) have no failure signal; their failures surface in the next checked submission or as non-finite values. A process killed outright (framework assertion, jetsam) writes nothing.

## Concurrency invariants

- Most long-lived objects are `final class @unchecked Sendable` guarded by an internal `OSAllocatedUnfairLock` or `SyncBox<T>` (`Utils/SyncBox.swift`) — not actors: `ReplayBuffer`, `ChessNetwork`, `ParallelWorkerStatsBox`, `GameWatcher`, `ReplayRatioController`, `GameDiversityTracker`, `TrainingLiveStatsBox` (in `ChessTrainer.swift`), the `*Box` / `*Flag` / `*Gate` classes in `Training/` and `Arena/`. Preserve the lock discipline in comments; don't convert to actors. No raw `os_unfair_lock`, no new `NSLock`s; `OSAllocatedUnfairLock` is the standard (~20× faster than `DispatchQueue.sync`).
- Remaining serial `DispatchQueue`s are work executors bridging structured concurrency to long synchronous GPU/IO work: `ChessTrainer.executionQueue`, `ChessNetwork.executionQueue`, `ChessMachine.delegateQueue`, `SessionLogger.queue` (which also guards the logger's state). They stay.
- **No long synchronous work inside a `Task`.** GPU work (`GPUSubmission`, which waits) runs on the networks' / trainer's serial `DispatchQueue`s behind `CheckedContinuation`; follow that for any new GPU path.
- `ChessMachine` delegate methods fire on a private serial `.userInteractive` queue; SwiftUI state changes need `Task { @MainActor in ... }`.
- **A GUI session save takes one consistent cut:** self-play stays paused from the champion export until the record is built (and until the replay buffer file is written, when included), training from the trainer export until the record is built. Gate releases reachable twice go through `WorkerPauseGateHold` (the gate isn't counted). Saves refuse during an arena; an arena waits for an in-flight save (`[ARENA] waiting for an in-flight session save …`), then marks itself active with no suspension point in between.
- **Every GUI `--train` termination** (time limit, step limit, legal-mass collapse, early stop, training-health stop, GPU fault) goes through `AutoTrainTermination` (`App/AutoTrainTermination.swift`): one shared claim, results written, `SessionLogger.shutdown()`, then `_exit(0)`.
- **Probe isolation:** no probe, diagnostic or observer may change trainer, optimizer, replay-buffer or RNG state; it reads a snapshot or its own copy with its own stream (`probe.<name>.<step>`). The KL probe, the one that touches training-graph state, only moves *when* a step's single dropout-RNG advance happens (after its own forward instead of inside the training executable), never how many (`DropoutRNGStateTests.testKLProbeDoesNotChangeTheDropoutSequence`). Its schedule derives from the step index (`ChessTrainer.isKLProbeStep`), so a resumed run probes on the same steps.

## Training observability worth knowing about

`[STATS]` counters that matter for training health:
- `pLoss` — signed-advantage policy loss: `max(0, A)·CE(played) + max(0, −A)·complementCE`, with A the RMS-normalized advantage; bounded below by 0. Read with `pEnt`.
- `pEnt` — mean entropy of the **legal-move** (masked) policy softmax, nats; uniform ≈ `ln(#legal)` (≈ 3.4 at 30 legal moves). Below `TrainingHealthThresholds.policyEntropyAlarm` (1.0, `Training/TrainingHealth.swift`) → `[ALARM] policy may be collapsing`.
- `vMean` / `vAbs` — mean / mean-abs of `v = p_win − p_loss`; `pW` / `pD` / `pL` — W/D/L batch means (sum ≈ 1). The failure signature is `pD → 1.0` (`vAbs → 0`) and staying there; `pD` falling below its bias-init prior (`value_head_draw_prior`, standard 0.75) is the sign training works. `vLoss` is categorical-CE scale (≈ `[0, ln 3]`).
- `gNorm` — rolling pre-clip global gradient L2 norm. Clipping: `gradClipMaxNorm` plus the relative cap (`[GRAD-CLIP]`; default mode logs only); clips show as `gNormMax=` / `clips=` / `gCap=`.
- `diversity=unique=X/Y(%) diverge=N.N` — `GameDiversityTracker` over the last 200 games; `diverge` = mean, over new games, of the longest prefix shared with any stored game. Healthy steady state is `[0-5]`-heavy in the histogram tile.
- `[LAYER-HEALTH]` — `Training/LayerHealth.swift` (pure; site list from the architecture in graph build order, cross-checked in `LayerHealthTests`; classification model in its header), logged via `Training/LayerHealthLog.swift`. For BN sites feeding ReLU / leaky ReLU, β/|γ| classifies channels **dead** (< −3), **mostly off** (−3 … −2), **always on** (> +3): `dead= off= alwaysOn= worst=<site>(…)`, `maxBetaOverGamma` / `minBetaOverGamma` as `value@site[channel]`; with no such site, `dead=n/a off=n/a alwaysOn=n/a (no relu/leaky_relu BN sites)`. Every activated site, SiLU / GELU included, gets activation-aware `parkedSites` / `parkedCh` / `parked` / `parkedOff` / `parkedBy` (equal to dead / mostly off for relu and leaky_relu; read by the `dead_channels` rule). Also `rvMaxOverMedian` (largest BN running-variance max/median), `rvOver10xMedian` (channels ≥ 10× their site median; `LayerHealth.runningVarianceRatios` is the one ratio definition; checkpoint table column `rv≥10x`), `rezeroCapFrac` + `saturated=k/N` (effective α = cap·tanh(α/cap) as a fraction of cap; saturated ≥ 0.99), `nonFinite`. Tiers:
  - **live** — `[LAYER-HEALTH] live trainerStep=N scope=batch_norm_state_only …`, BN γ/β/running stats + ReZero α via `ChessTrainer.readLayerHealthLiveState()` on the trainer's `executionQueue` (never concurrent with an SGD step); on every step line.
  - **checkpoint** — `[LAYER-HEALTH] checkpoint <replay-|vsuci-|session-><trigger> step=N trainerStep=N scope=all_tensors …` + per-site table, on every trainer save from the already-exported weights + velocity; adds `seZeroVel` / `seLowVel` / `worstSE` (SE FC1 units whose weight-velocity column — native `[in, out]` — is exactly 0, or below `lowVelocityFractionOfReferenceUnitNorm` × the layer's `lowVelocityReferencePercentile` (p90) unit norm), `valueFC1ZeroVel`, `maxAbs`. CLI runs record it under `layer_health` in `results.json`; `--analyze-numerics` includes it (non-finite = BAD; dead / always-on / zero-velocity = degraded; variance spread and ReZero saturation reported without a verdict).
  - **value-fc1** — `[LAYER-HEALTH] value-fc1 trainerStep=N trained=N …`, the alarms' dedicated value-FC1 velocity read.
  
  Head shared offsets stay on `pLogitMean` / `vLogitMean` + the numerics audit. A failed read logs `[LAYER-HEALTH] … failed: …` and never stops training or a save.

### Training health alarms

Every training path (GUI Play-and-Train and `--train`, `--replay-corpus`, `--train-vs-uci`) runs one shared `TrainingHealthEvaluator` (`Training/TrainingHealth.swift`) through a per-run `TrainingHealthMonitor`: 14 rules (`non_finite`, `dead_channels`, `value_fc1_zero_velocity`, `illegal_mass`, `gradient_collapse`, `loss_spike`, `policy_offset_drift`, `bn_running_variance_runaway`, `gradient_spike`, `divergence`, `value_saturation`, `value_draw_saturation`, `legal_mass_stall`, `bn_running_variance_jump`) over every SGD step's record, a live layer-health read every 50 trainer steps, every save's checkpoint pass, and a value-FC1 velocity read at most 1,000 steps apart. Rules 10–13 share their conditions with the GUI banner detectors / legal-mass probe (`TrainingHealthDetectorConditions`, owner decision OD-9); rule 14 `bn_running_variance_jump` keeps its lookback in `Training/BatchNormRunningVarianceJump.swift`. Thresholds are `TrainingHealthThresholds`; the 17 `training_health_*` parameters (Health tab) set enable, check interval, learning grace and one action per rule, every action defaulting to log. A stop ends a CLI run through its final save (`health-stop`, results `training_health_alarm`, **exit 35**), suspends GUI training (`trainingSuspension = .healthAlarm`: worker parked, arenas and Promote Trainee Now refused, self-play and periodic autosave continue) or ends GUI `--train` through `AutoTrainTermination`. The monitor is a pure observer (no random draws, no trainer/optimizer/buffer changes). Log: `[HEALTH]` (`config`, `check` every `training_health_check_interval_steps` with the monitor's cost, rewinds, stale observations, `training suspended`) and `[ALARM] health <raise|escalate|worsen|active|clear|stop> rule=…` (`grep '\[ALARM\] health'` selects exactly these). `results.json`: `alarms`, `alarm_config`. `--replay-health-log <log>…` runs the evaluator over saved logs, read-only. Rules, thresholds and per-path behavior: `documentation/training-health-alarms.md`.

## Run tracking: three axes (architectural decision, 2026-08-11)

The dashboards (`documentation/dashboards/`) plot every run on **three separate, non-interchangeable x-axes**. `registry.json` holds per-run segment config; `data/<run>.csv` (columns in `_schema.py`) is the source of truth; `master.py` renders.

- **step** — `cum_step = segment.cumstep_base + segment step` (segment step = lineage `segment_local_step` from format v11, header `training_step` before; `dcm_lineage.step_reading` is the one Python reader). Exact, but a *work* axis only while batch size and replay ratio are constant.
- **time** — `elapsed_train_sec`, **sleep-clamped**: `_clamped_timeline` banks `min(real_gap, segment_median_s_per_step × Δsteps + 120s)` per interval, one-directionally (faster intervals pass uncapped). `wall_sec` is the same walk uncapped, so `wall_sec − elapsed_train_sec` is exactly what the clamp discarded. Keep both; the clamp stays auditable, never baked in.
- **compute** — `games_fed`, cumulative corpus games from the runner's `games=`; the device-independent axis for cross-machine comparison.

Rules not to be quietly reversed:

- **Never normalize time across devices.** Where a lineage spans machines the by-time slope genuinely changes (v5 breaks 2.59× at cum 100,320: a Pacific-TZ VM on an M5 host → native M4 Pro — VM vs native, not silicon). With batch and replay ratio fixed, a "normalized seconds" axis is just `steps × reference_ms` — a relabelled step axis that destroys the record of real cost.
- **`games_fed` is measured, never modeled.** A segment with a missing log is **blank** — not zero, not interpolated. A modeled value in a measured column still looks plottable.
- Each segment carries `device`, `model_id`, `games_base`, and pinned `elapsed_base_sec` / `wall_base_sec` in `registry.json`; without pins (prior logs may be absent) the time axis silently restarts at zero.
- **Enumerated checkpoint names come from the out-model stem and the trainer step `T`** (= the file's `training_step` from v11): `<base>-replay-step<T>` / `<base>-vsuci-step<T>` from a `<base>-<tag>-latest` rolling stem, `<stem>-step<T>` from any other (`EnumeratedCheckpointNaming`). An exact resume continues its run's series under the same stem (resume from `…-step36000` writes `…-step37000`). Saves land on multiples of 1000 plus the final save; a segment that trained no step writes none. Legacy names stay as they are: pre-v11 resumed segments wrote `<stem>-replay-seg<k>-step<N>` (N their own step; still refused as a rolling `--out-model`), and pre-lineage runs gave each resumed segment its own stem (`…-Qeu8-replay-step*`, `…-Qeu8-resume2-replay-step*`, …).
  - Probe loops (`experiments/probe_loop.sh`): a v11+ resumed segment takes `PROBE_ABOVE_STEP=<its start trainer step>`, and a segment 0 that a later segment wrote after takes a step limit; `PROBE_SEGMENT=<k>` is for legacy `-seg<k>` names only; the two are refused together. The loop refuses a `TRAINER_PID` that isn't the out-model's writer (exit 3) and never records a probe that exited non-zero. The tracker finds a resumed segment's files by `segment_id` (`derive-registry`), never an `enum_stem` glob (a glob over a stem several segments wrote into is reported, not filed).
  - The app enforces: `--enumerate-checkpoints` never overwrites a file the run didn't write, and a run whose stem already holds step files it could reach (trainer steps above its start, up to start + `--training-step-limit`, or all without one) refuses to start and names them (`TrainerOutputFileGuard`, `CorpusReplayRunner.swift`).
  - `registry.json` names only the *latest* via `out_model`, so one glob misses earlier segments; a segment may declare `enum_stem`, and `enum_specs()` resolves one glob per segment (fallback: the old single glob). `python3 replay.py discover-stems [run] [--write]` derives stems **by evidence, not filename**: resume-shaped suffix (keeps sibling `Qeu8e5` out of `Qeu8`), one `model_id` per stem, segment chosen by how many of the stem's files land on `cum_step`s the CSV already knows (tie-break: segment length vs stem extent), all stems mapped monotonically in creation order; it refuses when ambiguous. **Never infer the segment from the suffix** — qeu8's segment 0 predates enumeration, so its first enumerated segment (1) wrote the *unsuffixed* stem; trusting names there invents 68 rows at nonexistent cum steps. **Run it on the machine holding `Models/`** (`models_dir` is deliberately `~/…`).
- **The rolling `--out-model` (corpus replay) is checked before training** (train-vs-UCI writes session folders and refuses `--out-model` / `--overwrite-out-model`). It is never the `--start-model`, never anything but a regular file, never a step-enumerated name (`EnumeratedCheckpointNaming`'s parser) whether or not it exists; an existing file is replaced only when it holds the `--start-model`'s `model_id` at its `training_step` (the rolling file of the state being continued). Anything else (an earlier run of the same command, under its own minted `model_id`; an earlier checkpoint of the line via a mistyped path) refuses unless `--overwrite-out-model`. A failed save warns the first time and halts on the next consecutive failure; a failed final or abort save fails the run (`TrainerSaveFailureStreak.requireLastSaveSucceeded`, shared with train-vs-UCI).
- **Corpora:** corpus replay opens them read-only and skips unsealed `.open` shards with a warning. Only `--validate-corpus <dir> --fix` recovers a crash-leftover `.open` shard (truncate to its last complete game and seal, or remove one with none; logged `[CORPUS-RECOVERY]`). Every `ShardWriter` holds an exclusive `O_EXLOCK` on its `.open` file until it seals, discards or closes (released at process exit); `--fix` skips a locked shard (`open-shard-in-use`) and then leaves `corpus.json` alone. Writers from builds before the lock aren't protected. Without `--fix` it only reports.
- **Identify checkpoints by safetensors `__metadata__` (`model_id` + `training_step`), never by filename.** `training_step` is the trainer step from v11 and, on pre-v11 corpus-replay / train-vs-UCI files, the writing segment's step (`ModelFileStepReading` / `dcm_lineage.step_reading`, by `creator`). Pre-v11 segment-local numbering repeats names across stems, and before reused stems were refused, earlier files were overwritten in place. `import-probes` refuses modelID mismatches per segment; `ckpt_inventory.py` builds a manifest from headers.

## Conventions specific to this project

- **File writes that could touch something the operation doesn't own go through `FileSafety`** (`Utils/FileSafety.swift`; operations and per-operation race windows in its type doc — don't call them race-free). Rules: touch only the exact files the operation writes, replace only regular files, never remove before writing, never silently overwrite, refuse folders and symbolic links, throw a `FileSafetyError` naming the path. A staged file's validated name must leave `FileSafety.temporarySiblingNameOverhead` bytes of `NAME_MAX` free. Don't reintroduce `FileManager.createFile` / `removeItem`-then-write / `.atomic` over a path the operation doesn't own, and don't add another helper — extend `FileSafety`.
- Source comments are multi-paragraph design explanations, not boilerplate. For a tricky mechanism, explain *why*, including the failure modes that motivated it (house style: `BatchedSelfPlayDriver`'s and `ReplayBuffer`'s class docs).
- **One SwiftUI `View` struct per file.** `App/ContentView.swift` composes the shared `ChartCoordinator` with `UpperContentView` over `LowerContentView`. Session-lifecycle wiring lives in `App/SessionController.swift` and its `SessionController+*.swift` extensions; `App/UpperContentView/UpperContentView.swift` (~3.8k lines) is the main view. Put new UI pieces in new files under `App/UpperContentView/` (or the matching `Views/.../` subdir for chart tiles). `body` is the only allowed `some View` property — no helper `@ViewBuilder` / `some View` properties; decompose into child `View` structs (same file as the parent is fine). `UpperContentView.swift` still has seven legacy helper properties; don't add more.
- Don't say "draw collapse". You tend to throw this phrase around like salt at a french fry convention and most of the time you're wrong because you never check the fucking data details. You shoot from the hip without paying any fucking attention. If you find yourself thinking about writing 'draw collapse', you've probably fucked up in some way. For example, if you start with a high number of draws -- which every single training round will do -- that's not draw collapse. That's just draws.
- Details matter. Get them right. Verify them and make sure they're right -- Every time.
