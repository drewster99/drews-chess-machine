# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A from-scratch self-play chess engine written in Swift/SwiftUI for macOS. The neural network runs on MetalPerformanceShadersGraph (MPSGraph) on Apple Silicon.

**This project does not use MCTS.** There is no tree search of any kind — no MCTS, no alpha-beta, no minimax, no rollouts. Move selection is a single forward pass: network emits 4864 policy logits (76 channels × 64 squares, AlphaZero-shape encoding) + a value scalar, the CPU masks illegal moves, temperature-scales, softmaxes, and categorical-samples. That's it. Do not add search, and do not suggest "for MCTS you'd…" style edits — AlphaZero-style search is an explicit non-goal. Strength comes entirely from the network itself, bootstrapped through self-play + arena promotion. See `documentation/chess-engine-design.md` ("My Goal") and `documentation/sampling-parameters.md` ("Sampling method") for the explicit rationale.

There is also no opening book and no human training data.

The app is a single-window macOS SwiftUI app used as an interactive training console: build a fresh network, run Play-and-Train (N concurrent self-play workers feeding a replay buffer while a trainer consumes batches), trigger an Arena to measure candidate vs. champion, and promote if score ≥ threshold.

## Build / run

Always use **drews-xcode-mcp** for building or running. Never invoke `xcodebuild` / `swift build` directly.

- Project: `DrewsChessMachine/DrewsChessMachine.xcodeproj` (scheme `DrewsChessMachine`, macOS only).
- A pre-Compile Run Script phase invokes `DrewsChessMachine/generate-build-info.sh`, which bumps `DrewsChessMachine/build_counter.txt` and regenerates `DrewsChessMachine/DrewsChessMachine/BuildInfo.swift` every build. Both files are expected to show up as modified after any build — never edit `BuildInfo.swift` by hand, and don't fight the counter changes.
- XCTest target `DrewsChessMachineTests` exists and covers the pure-logic components (PolicyEncoding bijection, BoardEncoder planes, repetition tracking, ReplayBuffer, MPSGraph gradient/reshape semantics, legal-move validation, sign consistency, ArenaEloStats, ChartZoom stops). Add tests for any new pure-logic component that has correctness invariants. Higher-level behaviors that require Metal/MPSGraph setup still rely on the Engine Diagnostics UI button and session-log observation rather than XCTest.

### Running the tests

The full suite is **slow — roughly an hour cold** on this machine: a cold build-for-testing of the large test target dominates, and on top of that test *execution* alone is ~19 min (865 cases). So:

- **Most of the time, run only the specific test(s) / class you're touching.** The cold test-target build is the real cost; once it's warm, incremental rebuilds + targeted `-only-testing:DrewsChessMachineTests/<Class>[/<method>]` runs are quick. Run the **full suite only occasionally** — before merging, or after changes to the graph builders (`ChessNetwork`), training math (`ChessTrainer`), persistence/serialization, or move generation.
- **Heavy *forensic* suites are gated** behind the `DCM_RUN_SLOW_TESTS` env var (`1`/`true`). They are diagnostic bug-maps, not correctness gates, and dominate execution time. Gated today (see `DrewsChessMachineTests/SlowTestGate.swift`): `MacOS27NaNIsolationTests` (**~11.6 min — ~60% of the whole exec time**; the 63-case precision×batch×step NaN-isolation matrix, several cells 1m+ each) and `ConvKernelExecutionPathNumericsTests` (~37 s — the Winograd-blowup refutation). Gating both drops exec from ~19 min to **~7 min**. **Note: the scheme's test plan currently turns them ON** — `DrewsChessMachine/DrewsChessMachine.xctestplan`'s "Test Scheme Action" configuration sets `DCM_RUN_SLOW_TESTS=1` (enabled), so a scheme test run (Xcode or `drews-xcode-mcp`'s `run_project_tests`) includes them. To leave them out, disable that entry in the test plan (Edit Test Plan ▸ Configurations ▸ Environment Variables); a targeted `-only-testing:` run that doesn't name them is unaffected either way.
- **Other heavy-but-core suites are NOT gated** (they assert real correctness, so they stay in the default run): `PolicyHeadCorrectnessTests` (~92 s), `CheckpointManagerSafetensorsTests` (~89 s, bit-exact round-trips), `MomentumOptimizerTests` (~86 s), `RuntimeArchReachTests` (~52 s). If one becomes a problem, prefer trimming its slowest cases over gating the whole class.
- **Private `UserDefaults` in tests:** take the suite from `makeTemporaryDefaultsSuite()` / `makeTemporaryDefaults()` (`DrewsChessMachineTests/TemporaryDefaultsSuite.swift`). Never `UserDefaults(suiteName: "<name>")` plus `removePersistentDomain(forName:)`: that leaves an empty plist in `~/Library/Preferences`, and `cfprefsd` writes it back even after the file is deleted. The helper's suite lives in its own temp folder, removed at teardown.
- **Gating a new forensic suite:** add `override func setUpWithError() throws { try SlowTestGate.requireEnabled("<label>") }` to the class — it skips cleanly with a reason naming the env var. Don't gate a suite that pins a correctness invariant.

## Where to look for runtime state

The app terminal console only shows SwiftUI chart warnings and bring-up noise. All meaningful runtime telemetry goes to the session log:

- `~/Library/Logs/DrewsChessMachine/dcm_log_YYYYMMDD-HHMMSS.txt` (one file per launch; a second launch in the same second gets `-2`, `-3`, … before `.txt`). A test run never writes there: an XCTest host (`XCTestHostDetection`, the one test-run signal) logs to `$TMPDIR/DrewsChessMachine-XCTest-SessionLogs/run-<stamp>-pid<pid>/`, left in place after the run (`SessionLogger.Location.forProcess`).
- `drews-xcode-mcp`'s `get_runtime_output` only returns output after the app has terminated; while the session is running, read the session log file directly.
- Every log line is timestamped. Tags to look for: `[APP]` (launch banner with build+git), `[BUTTON]` (user actions), `[STATS]` (periodic training snapshot on the step-line cadence every path shares, `Training/TrainingStepLineSchedule.swift`: the first observed trainer step, every 50 trainer steps through 1000, every trainer-step multiple of 1000, and the first step with diagnostics `step_line_interval_sec` (default 180 s, live) after the previous line; `[REPLAY]` / `[VS-UCI]` step lines follow the same schedule, keyed on the trainer step, and every line after a segment's first carries the diagnostics; `[BATCH-STATS]` is written with the step lines, not on every batch-stats step), `[ARENA]` (arena start/end, W/L/D, kept vs promoted), `[ALARM]` (e.g. policy entropy below threshold), `[CHECKPOINT]` (autosaves; each save line ends `buffer=included replay=…` or `buffer=omitted`), `[RESUME]` (one `EXACT` or `NOT EXACT: <gaps>` verdict per resume — corpus replay and train-vs-UCI `--resume-exact` refuse unless `--accept-inexact <gaps>` names every gap; a changed build, OS or Mac (hardware model, chip, VM flag, GPU name) logs `[RESUME] build|OS|device changed …` and is a `build` / `os` / `device` gap only when the behavior fingerprint differs; corpus replay also logs `[RESUME] replay buffer capacity: …` (a `params` gap) or `[RESUME] buffer fill not checked: …`), `[REPLAY] refused:` / `[VS-UCI] refused:` (a CLI run refused at launch, exit 2), `[ARCH] size guidance (<event>)` (parameter count against this Mac's memory — `verdict=within_recommended|trains_at_batch_N|likely_too_large|exceeds_physical_memory`; logged by `--new-model`, `--derive-model` and GUI builds), `[BATCHER]` (batched-eval startup correctness probe), `[RUN]` (the run's master seed at run start — `seed=… mode=seeded|seeded(--seed)|unseeded(drawn) derivation=v1`; see "Run seed" below), `[LAYER-HEALTH]` (dead / always-on BN channels, BN running-variance spread, ReZero cap saturation, NaN/Inf — a `live trainerStep=N` line on every step line, a `checkpoint <context> step=N` block on every trainer save, and a `value-fc1 trainerStep=N trained=N …` line for the alarms' dedicated value-FC1 velocity read; see below), `[GRAD-CLIP]` (relative gradient-norm cap, `Training/RelativeGradientCap.swift`: `[GRAD-CLIP] config mode=… k=… N=… W=… floor=… hardMax=…` at each run start, then one line per step whose pre-clip norm exceeded the cap fed to the graph (`applied=true`, hard-max clips included) and, in log-only mode, per step the rule would have clipped (`applied=false`); `[STATS]` / `[REPLAY]` / `[VS-UCI]` carry `gNormMax=` / `clips=` / `gCap=` for the steps since the previous line), `[HEALTH]` (training-health alarms: `config` at run start, `check` every `training_health_check_interval_steps` with the monitor's own cost, rewinds, stale observations, `training suspended`), `[ALARM] health <raise|escalate|worsen|active|clear|stop> rule=…` (one line per training-health event; `grep '\[ALARM\] health'` selects exactly these — see "Training health alarms" below).

## Training parameters

All tunable training parameters live in a single `@MainActor @Observable` singleton: `TrainingParameters.shared` (`DrewsChessMachine/DrewsChessMachine/Training/TrainingParameters.swift`). Each parameter is declared via the `@TrainingParameter` macro (in the local SwiftPM package `DrewsChessMachine/Packages/TrainingParametersMacro/`) which generates the id, definition (with range + category + liveTunable flag), and typed encode/decode.

### Adding / removing / renaming a parameter — full checklist

The macro covers id + persistence + JSON encode/decode, but several touchpoints are still manual. **Walk all of these every time a parameter is added, removed, or renamed** — drift between them tends not to fail the build, just silently desync at runtime.

1. **Declare it.** Write a `@TrainingParameter(...) public enum FooBar: TrainingParameterKey {}` declaration and add the type to `allKeys` in `TrainingParameters.swift`. **Declare its `absentValue:`** — what a resume applies when a checkpoint has no value for the key (`TrainingParameterAbsence`): `.preFeature(<value the run factually used before the feature existed>)`, `.declaredRangeMaximum` (pre-feature behavior was "unbounded"), `.currentSetting` (operational knob that doesn't change training math), or `.refuseExact` (training math with no known value: exact resumes refuse, the GUI uses the live setting and reports NOT EXACT). The `TrainingParameterKey` protocol requires it, so a key without one doesn't compile.
2. **Wire the singleton.** Add a stored property + matching entries in `collectValues` / `applyOne` (and the snapshot's read accessor).
3. **`parameters.json` save/load.** Confirm the new key appears in `--show-default-parameters` output and that the round-trip of `--create-parameters-file` → manual edit → reload behaves. (Macro-generated, but verify nothing is hand-listed in the CLI path.)
4. **Session save/load (`.dcmsession`).** Add an Optional field to `SessionCheckpointState` in `Persistence/SessionCheckpointFile.swift` (Optional so older sessions still decode), pass it through `buildCurrentSessionState` in `SessionController+Checkpoint.swift`, and add one `resume.restore(FooBar.self, saved: rs.fooBar, into: \.fooBar)` line (`savedFloat:` for a trainer `Float`) to `SessionParameterResume.applyGuiSession` (`App/SessionParameterResume.swift`, the GUI resume's one parameter block). `SessionParameterResume` resolves it through `TrainingParameterResolution` (the key's `absentValue` decides when the session is silent), writes it with the right persistence (session values saved; pre-feature values held for the run only, never written to `UserDefaults`, and put back — `TrainingParameters.releaseRunHolds`, logged `[PARAM] values held for the previous resumed run released …` — when the next Play-and-Train start that is not a continue after Stop begins, while any other assignment of the key during the run ends its hold; live-setting sources untouched) and logs one `[RESUME-DIFF] <id>: saved=… applied=… current=… (<reason>)` line. The trainer is configured afterwards from the settings through `TrainerHyperparameters`, so a trainer-level parameter needs no extra resume wiring beyond step 2.
5. **`results.json` / `CliTrainingRecorder`.** If the parameter influences sampling, training math, or anything a CLI/autotrain run cares to compare, surface it in the recorder's snapshot (e.g. `BatchStatsSnapshot.samplingConstraints`) so it shows up in `results.json` alongside metrics.
6. **Runtime log.** Make sure the parameter's *value* (or an observable derived from it) is visible in `[STATS]`, `[SAMPLER]`, `[BATCH-STATS]` (written only alongside step lines), or a similar tag — otherwise a misconfiguration is invisible while the run is in progress.
7. **UI position.** Decide where the parameter lives in `TrainingSettingsPopover.swift` (or another popover/control if it's not a training-loop knob), and add a binding + validation entry to `TrainingSettingsPopoverModel.swift`. A parameter with no UI is reachable only via `parameters.json` editing — fine for autotrain-only knobs but make that choice deliberately.
8. **Live tunability.** If `liveTunable: true`, confirm the consumer re-reads from `TrainingParameters.shared` on a periodic reconcile loop instead of caching it in a snapshot at session start.
9. **Renames.** Update the parameter's `id` (snake_case key in `UserDefaults` and JSON) **and** the Swift property name. Old `UserDefaults` entries under the previous id will then be ignored on load and the user's preference is silently reset to default — note this in the commit message; do not write migration code unless the user asks.

Reading values:
- **From SwiftUI views**: `@Bindable var trainingParams = TrainingParameters.shared`, then read `trainingParams.entropyBonus` or bind `$trainingParams.entropyBonus`. Re-renders fire automatically.
- **From off-main / structured-concurrency code**: take a snapshot at session boundary — `let p = await TrainingParameters.shared.snapshot()` — then `p.entropyBonus`. The snapshot is `Sendable`, immutable, and lock-free; mid-iteration UI changes are picked up next snapshot. Most parameters are flagged `liveTunable` (≈52 of ~62), but only a handful are consumed by long-running loops that must re-read live — `selfPlayConcurrency`, `trainingStepDelayMs`, `replayRatioTarget`, `replayRatioAutoAdjust`, `periodicAutosaveIntervalSec`; for those, running consumers re-read from `TrainingParameters.shared` on a periodic reconcile loop instead of using a snapshot.

The app's caps on self-play workers, `self_play_delay_ms` / `training_step_delay_ms` (0…3000) and `arena_concurrency` (1…1024) are the declarations' upper bounds (the `UpperContentView` statics are derived from them). Change the declaration, never a separate constant; no loader or resume clamps them.

Persistence is automatic: every property `didSet` writes to `UserDefaults` under the parameter's id, and the next `init` reads it back (validated). There is no `@AppStorage` for training parameters anywhere — the singleton owns all persistence.

`DrewsChessMachine --help` (or `-h`) prints the full usage to stdout and exits 0.

CLI flags for emitting defaults:
- `DrewsChessMachine --show-default-parameters` — flat snake_case JSON to stdout, descriptions to stderr; sub-second exit, no GUI.
- `DrewsChessMachine --create-parameters-file [path] [--force]` — writes both `parameters.json` and `parameters.md` (categorized doc). `path` is a folder (existing, or ending in `/`) to write both into, or the `.json` file itself (a path whose extension is `.md` in any letter case is refused — the markdown would land on it). Either file already existing needs `--force`, which replaces existing regular files and refuses anything else (never a folder).

### Run provenance (`[RUN]`)

Every run path logs exactly one `[RUN]` line at its start, formatted by `RunProvenanceLine` (`Logging/RunProvenanceLine.swift`; determinism plan D4): GUI Play-and-Train / `--train` at every start (including a continue after Stop), `--replay-corpus`, `--train-vs-uci`, `--derive-model` and `--uci`. It carries the path, the lineage run ID and segment index with how the segment began (fresh, branch from / exact resume of / derived from `<model_id> sha=<12>`, or a not-exact resume with its gaps), build/git/dirty, device/VM/OS, the run seed fields, the parameter snapshot's hash, the totals the run starts from (`cum_step` / `cum_games` / `cum_train_sec`, `unrecorded` where no predecessor recorded one) and the redacted argv. A value that does not apply is written as `none`. The seed's own `[PARAM]` notes come just before it; a continue after Stop also logs `[RUN-SEED] continuing …` with the game serials. `results.json` (CLI runs and GUI `--train`) carries the run's last-save lineage as a top-level `lineage` object (the record minus `segments` / `derivation_history`, plus `checkpoint_sha256` of that file; GUI `--train` reports the record at its last stats tick, with no file hash) and per-row `cum_trainer_step` / `cum_train_step_sec` / `cum_games`. A file's `derivation_history` lives in its lineage record and is carried verbatim by every later save of the line (training saves never append; only `--derive-model` does), with the flat `derivation_history` metadata key as its mirror.

### Run seed

Every training run (GUI Play-and-Train, `--replay-corpus`, `--train-vs-uci`) resolves one **master seed** at run start through `RunRandomSeed.resolve` (`Training/RandomSeedMode.swift`) and logs it on the run's `[RUN]` line (also `random_seed` / `random_seed_mode` / `rng_stream_derivation` in `results.json`). `random_seed_mode` (`0` = draw a seed, the default; `1` = use `random_seed`) and `random_seed` (a `UInt64`, written to JSON as a decimal **string** so values above 2^53 survive) are the settings, on the settings popover's Sessions tab; `--seed <n>` (with `--train`, `--replay-corpus` or `--train-vs-uci`) overrides both for that process. The seed is digits only: a sign (`+5`, `-0`) is refused there, in parameters files, stored settings and lineage records (`UInt64(strictDecimal:)`, the one parser for seed text). There is one code path: "unseeded" still draws a seed and logs it, so any run can be repeated with `--seed`. Every training-relevant draw comes from a named stream derived from it (`DCMRandomStreams`, plan Part A3): the replay buffer's `sampler`, each self-play game's `selfplay.game.<serial>`, each arena game's `arena.<arenaIndex>.game.<g>`, each train-vs-UCI game's `vsuci.game.<serial>`, the trainer's `dropout` masks (the GUI trainer outlives runs, so each new run hands it its stream via `ChessTrainer.beginDropoutStream`), the entropy probe's `probe.entropy_by_bucket.<step>`. Game serials are assigned in serial passes in slot order, never inside the parallel tick, so a game's moves do not depend on how many games run beside it. **Do not add a draw from `SystemRandomNumberGenerator` / `Int.random` / `.shuffled()` to a training path** — take a stream, and pass the generator explicitly (no defaulted generator arguments). Interactive play, UCI, the Lichess bot and network-load scratch containers deliberately draw from the system (`DCMRandom.seededFromSystem()`, `NetworkInitMode.overwrittenByLoad`). A Stop + continue keeps the run's seed and serials. A GUI session resume continues the saved run's seed, game serials, arena count, sampler and dropout-stream positions when the trainer file's record carries them and the seed can be inherited; otherwise (no streams, `--seed` naming another seed, another stream derivation) it draws a seed for the run (or uses `--seed`), logs `[RESUME] rng: the saved run's seed is not continued; …`, and reports `rng_sampler` / `serials` NOT EXACT. It never changes the `random_seed_mode` / `random_seed` settings.

## Saved model state

`CheckpointManager` writes both single-model (`.safetensors`; legacy `.dcmmodel` still readable) and full-session (`.dcmsession`) checkpoints under `~/Library/Application Support/DrewsChessMachine/{Models,Sessions}/`. **Nothing is ever overwritten** — every save is a new file, naming scheme `<YYYYMMDD-HHMMSS>-<modelID>-<trigger>.<ext>`. See ROADMAP.md for the full design including the bit-exact forward-pass verification that runs on every save.

Three triggers produce a `.dcmsession` — the trigger tag appears in the filename, the status bar, and the `[CHECKPOINT] Saved session (<trigger>): …` log line so every save is grep-distinct:

- **`manual`** — user clicked File > Save Session.
- **`post-promotion`** (folder tag `-promote`) — fires automatically after each arena promotion (on by default; `autosaveSessionsOnPromote`). Re-uses the weight snapshots taken under the arena's self-play and training pauses. Train ▸ Promote Trainee Now writes the same `-promote` tag (`SessionSaveTrigger.promotionDiskTag`, through the shared `saveSessionInternal` path with fresh weight exports) and is treated exactly like an arena promotion. Both are in the automatic-save retention pool below.
- **`periodic`** — interval autosave while Play-and-Train is active (cadence = the `periodicAutosaveIntervalSec` parameter, default 6 hours; live-tunable from the settings popover's **Sessions** tab — the heartbeat re-anchors the running `PeriodicSaveController` via `updateInterval`). The controller defers a deadline crossing that lands inside an arena, then either swallows it (if a post-promotion save landed during the deferred window) or fires a little late (otherwise). Any successful save of any trigger resets the clock. Periodic saves are in the automatic-save retention pool below.

**`--train-vs-uci` saves session folders too** — through the same `CheckpointManager.saveSession`, into `--out-session-dir` (default `Sessions/`), tagged `vsuci-periodic` (the `periodic_autosave_interval_sec` cadence, read once at run start), `vsuci-final`, `vsuci-abort` (Ctrl-C) and `vsuci-health-stop` (a training-health alarm stopped the run; exit 35). They replace the rolling `--out-model` file this path used to write (`--out-model` / `--overwrite-out-model` are now refused with `--train-vs-uci`); `champion.safetensors` is the play network synced from the trainer at the save, `trainer.safetensors` the complete trainer state, and the buffer is included only with `--save-replay-buffer`. Their lineage `path_kind` is `vsuci`: the GUI refuses to load one (`SessionCheckpointState.guiLoadRefusal`), they never enter the retention pool (wrong tag), and the CLI never moves `LastSessionPointer`. Resume with `--train-vs-uci … --start-model <folder> --resume-exact` (`--start-model` also takes a model file). A failed final or abort save fails the run. See `documentation/UCI.md` "Output: session folders".

**Automatic-save retention — off by default, and forced off in this build.** Pruning runs only when `CheckpointPaths.automaticSavePruningDecision` says so: the build's kill switch `CheckpointPaths.automaticSavePruningForcedOff` is not set, the `automaticSavePruningEnabled` parameter (`automatic_save_pruning_enabled`, default `false`; Sessions tab "Prune old autosaves") is on, and `maxPeriodicAutosavesKept` is above 0. **The kill switch is set (`true`) by owner decision 2026-10-01**, pending D-8 (saves without the replay buffer by default) and more confidence in automatic deletion, so today no automatic save is ever deleted whatever the setting says — the toggle is shown disabled with "Disabled in this build", and `AutomaticSavePruningGateTests` pins the constant so lifting it is a deliberate change. Every periodic or `-promote` save that does not sweep logs one `[PRUNE] skipped after <folder>: off: <reason> (automatic_save_pruning_enabled=… max_periodic_autosaves_kept=…)` line, and Play-and-Train start logs the effective state as `[PRUNE] automatic-save pruning at Play-and-Train start: …`. What follows is the rule pruning applies when it is allowed to run. After each successful periodic or `-promote`-tagged save (`saveSessionInternal` and the arena's inline post-promotion save both call `scheduleAutomaticSaveRetentionSweep`, which decides from the disk tag via `CheckpointPaths.AutomaticSaveKind`), `CheckpointPaths.pruneAutomaticSaves` keeps the newest `maxPeriodicAutosavesKept` (0 = unlimited, nothing pruned) of **one global pool**: every `-periodic.dcmsession` and `-promote.dcmsession` folder in `Sessions/`, from any session, ranked newest first by the folder name's leading UTC timestamp — trigger and session never affect the order. A folder is counted only if its name is exactly `<YYYYMMDD-HHMMSS>-<sessionID>-(periodic|promote).dcmsession` with a minted session ID, it is a real directory (not a symbolic link), and it holds a regular `session.json` carrying that same `sessionID`; anything else is kept, logged with the reason, and not counted. Never deleted: `-manual` and `-sigusr2` saves (never pool members), the just-written save, and the current `LastSessionPointer` target — a protected folder beyond the cap keeps its rank without pulling an older one back under the cap. Deletion goes through `FileSafety.removeOwnedItem` with the identity recorded at inspection, so a folder swapped in under the same name is refused. Each sweep logs `[PRUNE] retention: cap=N periodic=a promote=b kept=… protected=… unverified=… deleting=…`, one `[PRUNE]` line per kept-for-a-reason folder and per removal (with session ID and trigger), and `[PRUNE-ERR]` for a failure, which does not abort the sweep.

Every save stages under `<final>.tmp`, created exclusively — a pre-existing staging path fails the save with `stagingPathAlreadyExists` and is left untouched; a save only ever removes staging it created. The GUI-launch orphan sweep (`CheckpointPaths.cleanupOrphans`) removes only staging debris of the expected type that has gone unmodified for `orphanStagingMinimumAge`, so a second instance launching mid-save cannot delete the first one's live staging; it also removes `FileSafety`'s own hidden `.<name>.<UUID>.tmp` staging files (regular files only, recognized by `FileSafety.destinationName(ofTemporarySiblingName:)`) from `Models/` and `Sessions/` under the same age rule. Every removal is identity-checked against what was inspected. Staging leftovers anywhere else are never cleaned up automatically — see `documentation/disk-cleanup.md`.

**A GUI session save includes `replay_buffer.bin` (7–11 GB) only when asked** (#8, decision D-8 in `documentation/plans-active/DETERMINISM_RESUME_LINEAGE_PLAN.md`): automatic saves (periodic, post-promotion, Promote Trainee Now, SIGUSR2) follow the `session_save_include_replay_buffer` parameter (default off; Sessions tab "Include replay buffer"), and File ▸ Save Session opens a sheet whose "Include replay buffer" checkbox starts from it. Every save line says `buffer=included replay=…` or `buffer=omitted`. A resume without a buffer refills from new games and is logged `[RESUME] NOT EXACT: buffer`. Train-vs-UCI session saves omit the buffer unless `--save-replay-buffer` is passed (the GUI parameter does not apply to the CLI); an exact resume from a session that has one restores it. Per D-1, GUI and train-vs-UCI resumes are state-exact at most; corpus replay is the only path whose resume continues the uninterrupted run's random streams and feed exactly; weights match bit for bit only where MPSGraph steps are deterministic, not on a shared GPU (determinism plan, seventh pass). A corpus-replay `--resume-exact` is refused when the checkpoint's run has already used the epoch budget (`--epochs`, default 1, counted from the lineage start), when its saved corpus position is outside the corpus, or when the rebuilt replay buffer does not hold as many positions as the saved one.

**File lineage (`LineageRecord`, architecture format v7, session.json v2).** Every model file a training path, `--new-model` or `--derive-model` writes carries one `LineageRecord` as JSON under `__metadata__["dcm_lineage"]` (plus derived flat mirrors `lineage_run_id`, `lineage_segment_index`, `cum_trainer_step`, `cum_games_fed`, `cum_train_step_sec`, `git_dirty`, `lineage_segment_local_step`, never read back), and a session's `trainer.safetensors` and `session.json` carry the run's record at the save, while `champion.safetensors` carries the record of the champion's own weights — a mint record when it was built in the process, else its load or promotion record without trainer state (`SessionController.championFileLineageRecord`); a champion with no recorded origin fails the save. No record or file carries a placeholder model ID: a missing or empty `model_id` is a decode error. ## High-level architecture

### The self-play → train → arena loop

One run of Play-and-Train spins up, in parallel:

1. **N concurrent self-play games** (driven by the tick-based `BatchedSelfPlayDriver`, live-tunable via a Stepper in the UI, bounded by `UpperContentView.absoluteMaxSelfPlayWorkers`). One Swift task runs the outer loop; each *tick* advances all K games one ply in lockstep — parallel-encode the K positions, issue a single batched `network.evaluateBatched(...)`, parallel-sample + apply one move per game, then a serial game-end pass flushes completed games into `ReplayBuffer` in one bulk copy. Per-game state lives on an `ActiveGame` (no per-game `Task`, no actor barrier).
2. **One trainer** (`ChessTrainer`) that pulls minibatches from `ReplayBuffer.sample(count:)` and runs MPSGraph SGD steps on a separate training-mode copy of the network.
3. **Replay ratio controller** (`ReplayRatioController`) that auto-adjusts `stepDelay` so `cons/prod` approaches the configured target (`replayRatioTarget`, default 0.48; auto-adjust `replayRatioAutoAdjust` is off by default). The `[STATS]` line reports `ratio=(target=... cur=... prod=... cons=... auto=on/off delay=XXms)`.
4. **Arena** on demand (`TickTournamentDriver` via the Run Arena button). Pauses self-play via `selfPlayGate` and training via `trainingGate`, snapshots the current trainer weights into a dedicated candidate inference network, and plays a tournament candidate-vs-champion (candidate on one network, a dedicated `arenaChampionNetwork` holding a snapshot of champion weights on the other) using the arena `SamplingSchedule`. The promotion rule is `arenaPromotionCriterion`: **SPRT** by default (sequential test of `elo0` vs `elo1` that plays until the evidence crosses a bound; see `documentation/arena-sprt.md`), or score threshold (a fixed `arenaGamesPerTournament` games, promote if score ≥ `promoteThreshold`, default 0.53). On promotion, the candidate's weights are copied into **both** the live champion (`network`) and the live trainer (`trainer.network`), so both lineages converge on the arena-validated snapshot. Champion inherits the candidate's ModelID; trainer gets a freshly-minted next-generation trainer ID forked from the promoted champion. `CheckpointManager` writes a `-promote.dcmsession` snapshot when `autosaveSessionsOnPromote` is on.

### Networks are singular

A session holds exactly:
- `network` — the live champion. Also what every self-play game is evaluated against, via the tick driver's single batched `evaluateBatched` call per tick. Source of the arena-champion snapshot.
- `trainer.network` — internal to `ChessTrainer`, training-mode BN. The single source of weights for arena candidates. Forked from `network` on a fresh start, or loaded from the session's safetensors trainer weights on session resume, or overwritten by a promoted candidate's weights after an arena win.
- `candidateInferenceNetwork` — inference-mode, persists for the life of the app (lazy-built on first Play-and-Train start, reused across sessions). Receives the trainer's current weights at each arena start.
- `arenaChampionNetwork` — inference-mode, also persists for the life of the app. Receives a snapshot of `network`'s weights at each arena start so the arena's "champion side" plays against a stable snapshot while the live champion remains free for continuous self-play.

There are no per-worker inference networks. The original design ran a single self-play worker against `network` directly; the current N-worker setup added the shared batched evaluator rather than fanning out to per-worker networks.

### MoveEvaluationSource abstraction

The interactive single-game players (`MPSChessPlayer`) don't talk to `ChessMPSNetwork` directly — they hold a `MoveEvaluationSource`:

- `DirectMoveEvaluationSource` → single-position `network.evaluate(board:)`. Used by **Play Game / Human-vs-Network and `--uci`** (the latter via `UCIEngine`; `LiveTrainerMoveEvaluationSource` / `UIGatedMoveEvaluationSource` wrap it for the live-trainer and UI-gated variants).
- **Self-play and the arena do NOT use this abstraction.** Both run the tick-based drivers (`BatchedSelfPlayDriver` / `TickTournamentDriver`) that call `network.evaluateBatched(...)` once per tick and sample inline via `MoveSampler`. The older per-slot actor-barrier batcher (`BatchedMoveEvaluationSource`, with its `expectedSlotCount` grow/shrink protocol) was removed when the tick model landed — there is no slot-count deadlock window anymore (grow = append `ActiveGame`s, shrink = `removeLast` the tail).

### Board encoding and policy space

- Input: **30 planes × 8 × 8** NCHW, always from the current player's perspective. Planes 0-15 are pieces + castling, plane 16 en passant, plane 17 halfmove clock normalized as `min(clock, 99) / 99` (Leela convention), planes 18-19 threefold-repetition *counts* (≥1× before, ≥2× before), planes 20-29 threefold-repetition *temporal pattern* — plane `20 + i` is all-1 iff the position `i + 1` plies ago is a strict chess-rules duplicate (PositionKey equality on board + STM + castling + EP) of the current position. The 10-ply history window is cleared on any irreversible move (halfmove clock = 0). **Six of these planes can never be 1 in any position** (issue #10): planes 20, 21, 22, 24, 26, 28 (1, 2, 3, 5, 7, 9 plies ago — impossible under chess rules; only 23/25/27/29 can fire). Plane 19 is never 1 in a *self-play* training sample (the engine adjudicates the threefold draw on the same visit that would set it), but it does fire, rarely, in corpus replay — which replays recorded games past an unclaimed threefold — and at inference wherever an outside authority decides draws (Lichess bot, `--uci`). See `BoardEncoder.swift` and `chess-engine-design.md` for the full plane table. That 30-plane layout is the `basic30` input encoding, which every existing model and every built-in preset uses. **New models default to `basic24`** (`NetworkArchitecture.newModelDefault`: the current preset with the 24-plane input — Build New Model and Build Network start from it): `basic30` without the six impossible planes, i.e. planes 0-19 unchanged and planes 20-23 = repetition 4, 6, 8, 10 plies ago (`InputEncoding.possibleRepetitionPlyDistances`). The encoding is per model (`NetworkArchitecture.inputEncoding`), so a model keeps the encoding it was built with.
- Policy output: **4864 logits** = 76 channels × 64 squares. AlphaZero-shape encoding: 56 queen-style (8 directions × 7 distances) + 8 knight + 9 underpromotion (3 pieces × 3 directions) + 3 queen-promotion. Indexed as `channel * 64 + row * 8 + col` in the (vertically-flipped for black) encoder frame. The bijection between `ChessMove` and `(channel, row, col)` lives in `PolicyEncoding.swift` — every site that converts moves ↔ indices must use it (deliberately no `policyIndex` property on `ChessMove` itself, so callers must think about the side to move).
- Value output: a **3-logit win/draw/loss head** (slot order `[win, draw, loss]`), trained with categorical cross-entropy against a one-hot on the game result. Everything downstream that wants "am I winning?" as a scalar reads the derived `v = softmax(logits)·[+1, 0, −1] = p_win − p_loss ∈ [−1, +1]` — a difference of two probabilities, no `tanh`. (Switched from a single `tanh` scalar + MSE on 2026-05-12 because the scalar head went silent on a draw-heavy buffer; see `wdl-value-head.md` and the 2026-05-12 CHANGELOG entry.) Always relative to the current player.
- Network: **architecture is runtime-configurable per model**, not a compile-time constant — every model embeds its full `NetworkArchitecture` (the single source of truth; see `NetworkArchitecture.swift` and `documentation/plans-active/RUNTIME_ARCHITECTURE_CONFIG_PLAN.md`). Shape = stem (inputPlanes→first-group width) → an ordered list of **block groups** (`blockGroups: [BlockGroup]`, each a count + a complete per-group recipe: channels, both conv kernels, SE style/ratio/β init, SE FC1 activation (`se_activation`, independent of the main path's — issue #2), ReZero α init and cap (`rezero_alpha_init` — `0` is legal, the ReZero-paper zero init — and `rezero_alpha_cap`, the asymptote C of the forward `C·tanh(α/C)`; see `documentation/rezero-alpha-clamp.md`), activation function/style, skip merge, dropout multiplier, and the init-neutral options `se_gamma_bias_init` / `branch_output_init` / `skip_projection_init`) → tower-end BN + its activation (pre-act tail only) → policy head + value head. Towers may be **heterogeneous** (WRN-style width staircase): where adjacent groups differ in width, that block gets a bias-free 1×1 skip projection. The engine consumes only the flattened `expandedBlocks`; uniform towers (one group) build byte-identically to the pre-block-groups code. Architecture fields added later are gated by the carrier's format version (`Network/ArchitectureFormat.swift`; current v12: `se_beta_init` required from v4, `se_activation` from v5, `rezero_alpha_cap` from v6 — an older file resolves the cap to `rezero_alpha_init × rezeroTanhCeilingMultiple`, the C the engine derived before the field existed; v7 adds no architecture field but requires every safetensors model file to carry a `dcm_lineage` record — see "File lineage" below; v8 requires the init-neutral options — per group `se_gamma_bias_init`, `branch_output_init`, `skip_projection_init`, and `policy_head_final_init`, `value_head_final_init`, `value_head_draw_prior` on the heads — which an older file, or one in the pre-block-groups uniform-tower form, resolves to the standard init every model had before them; Build New Model's Neutral init / Standard init buttons and `--derive-model --set-neutral-init` / `--set-<option>` set them, see `documentation/deriving-models.md`; v9 replaces the top-level `activation_function` with one activation per architecture-level site (`stem_activation`, `tower_end_activation`, `feature_skip_activation`, `policy_head_activation`, `value_head_conv_activation`, `value_head_fc1_hidden_activation`); a site the topology lacks holds `does_not_apply` (never an identity activation), and an older file resolves each existing site from its own `activation_function`; v10 applies the same rule to an SE-less group's `se_activation`, which is `does_not_apply` (an older file's value, which had to equal the group's activation, resolves to `does_not_apply`); v11 adds no architecture field: a model file's `training_step` is the trainer step (on a trainer-state file equal to `trainer_completed_steps`, refused otherwise) and the segment step is the lineage record's `segment_local_step`; an older file is read by its writer's meaning (`ModelFileStepReading`, by `creator`) and flagged on load with one `[ARCH] legacy file` entry, and builds before v11 refuse every file written from v11 on, presets and `architecture.json` included; v12 adds `policy_tail_precision`, see the next bullet): an older file without the field resolves to the pre-field behavior (logged once as `[ARCH] legacy file …`), a current-version file without it is a load error. The current default preset is `v4_5block_7x7` (5 blocks, 7×7, 128ch, ~8.45M params); the policy head has three styles (simple_conv / intermediate_conv / fc_bottleneck) and the value head is the 3-logit W/D/L head. Build new towers via Build-New-Model (per-group editor + live `ArchitectureDiagramView`). **Model size is guidance, not limits** (owner decision 2026-10-03): `validate()` refuses only non-positive counts and `Int` overflow, computed per group with checked arithmetic and never expanding the tower; `ModelSizeGuidance` scales a recommendation to physical memory (64 GB reference: 15M parameters recommended, batch 4096 up to 20M, `20M × √(4096 / batch)` down to batch 512, "likely too large" beyond), and its one refusal is a training state (16 B per parameter) larger than physical memory, applied by Build New Model, `--new-model`, a graft and the GUI build. See `ChessNetwork.swift` (graph builders) and `documentation/plans-completed/ARCHITECTURE_EXPANSION_PLAN.md` (block-groups design). SE blocks match modern lc0 practice.
- **Policy tail precision is an architecture field** (owner decision 2026-10-07; plan `documentation/plans-active/POLICY_TAIL_ARCHITECTURE_PLAN.md`). Where the policy head leaves the compute dtype for fp32 (`fp32_from_pre_bn` / `mixed_final_projection`) changes the graph a model is built as, exactly as `computeDataType` does, so it lives in `NetworkArchitecture`, is chosen in Build New Model and set on an existing model with `--derive-model`, and travels with every model file. Architecture format v12 adds it; a file written before v12 resolves to the tail it records (its `trainer_policy_tail_precision` key or lineage `configuration.policy_tail_precision`), else `mixed_final_projection` (`does_not_apply` on fp32); unrecorded files from the fp32-tail era are audited (their tail from the writing build's default, overridden by launch-flag evidence), and those the owner approves get a one-off in-place header edit that adds only the flat `trainer_policy_tail_precision` key — no format-version change, weights untouched (plan PT-D3; a session's unrecorded `champion.safetensors` takes the same session's trainer-file tail). The process-wide `--policy-tail-precision` launch flag is removed (passing it is an unknown-argument error) — do not reintroduce a process-wide or launch-time precision setting. The tail is `NetworkArchitecture.policyTailPrecision` (`PolicyTailPrecisionSetting`; `does_not_apply` exactly on fp32, enforced by `validate()`); `computeDataType` is `private(set)` and changes only through `withComputeDataType(_:tail:)`, which sets the tail consistently. The pre-v12 resolution reads the recorded tail in `SafetensorsModelIO.decodeArchitecture(fromMetadata:source:)` (`trainer_policy_tail_precision`, else lineage `configuration.policy_tail_precision`; both present and different is refused), and `CheckpointManager.decodeSessionChampionFile` applies PT-D3 rule 4. Writers no longer write the flat key; a v12 file that carries it is refused. Every network and trainer is built at its architecture's tail (inference included: a trainer file recording `fp32_from_pre_bn` now plays and probes under it), the `policy_tail` resume gap is gone, the numerics audit builds bf16 and fp16 under both tails in one run, and `--derive-model --set-policy-tail-precision <value>` sets it on an existing plain model (no tensor rewritten).
- Legal-move masking is done CPU-side in `MPSChessPlayer.chooseMove` after softmax; the graph emits raw logits, not a masked softmax.

### Sampling (temperature schedules)

Move selection is temperature-softmax over legal-only logits — no top-k, no MCTS. The self-play and arena schedules are **tunable** — built from `TrainingParameters` at session start and held on `MPSChessPlayer.SamplingSchedule` as resolved start/decay/floor. Temperature decays linearly per **game-total ply**: `tau(ply) = max(floor, start − decay·ply)`.
- **self-play** — default start 0.2 → floor 0.02, decay 0.02/ply (`selfPlayStartTau` / `selfPlayTargetTau` / `selfPlayTauDecayPerPly`). Self-play also adds Dirichlet root noise, which is its main source of opening variety at these low temperatures.
- **arena** — default start 0.2 → floor 0.02, decay 0.02/ply (`arenaStartTau` / `arenaTargetTau` / `arenaTauDecayPerPly`). No Dirichlet noise — arena games measure strength.
- `.uniform` — flat 1.0, used by Play Game / Forward Pass demo.

These defaults (identical for both schedules) are the owner's running configuration as of 2026-10-01; before that the defaults were self-play 1.0 → 0.5 / 0.007 and arena 0.6 → 0.2 / 0.02.

(The hardcoded `SamplingSchedule.selfPlay`/`.arena` constants — start 2.0 — are now only fallbacks; the live schedules use the parameters above.)

See `documentation/sampling-parameters.md` for rationale.

### ModelID identity

`ModelID` (`yyyymmdd-N-XXXX`) is minted at well-defined events (Build, Play-and-Train start, arena snapshot) and inherited verbatim on most weight copies. The mint/inherit rules aren't obvious — **read `sampling-parameters.md` before adjusting when IDs change**. Every `[STATS]` and `[ARENA]` line reports `trainer=...`, `champion=...`, and (during arena) `candidate=...` so logs stay traceable back to specific weight snapshots.

## Concurrency invariants

- Most long-lived objects are `final class @unchecked Sendable` with an internal `OSAllocatedUnfairLock` (or `SyncBox<T>`, the project's tiny wrapper over `OSAllocatedUnfairLock<T>` at `Utils/SyncBox.swift`) — not actor-isolated. When editing any of them (`ReplayBuffer`, `ChessNetwork`, `ChessMPSNetwork`, `SessionLogger`, `ParallelWorkerStatsBox`, `GameWatcher`, `ReplayRatioController`, `GameDiversityTracker`, the `TrainingLiveStatsBox` inside `ChessTrainer.swift`, all the small `*Box`/`*Flag`/`*Gate` classes in `Training/` and `Arena/`, etc.), preserve the lock discipline in comments rather than converting to an actor. Do NOT use raw `os_unfair_lock` (unsafe in Swift) and do not introduce new `NSLock`s — `OSAllocatedUnfairLock` is ~20× faster than `DispatchQueue.sync` even uncontended and is the project standard. The serial `DispatchQueue`s that remain (`ChessTrainer.executionQueue`, `ChessNetwork.executionQueue`, `ChessMachine.delegateQueue`, `SessionLogger.queue`) are *work executors* — they exist to bridge structured concurrency to long-running synchronous GPU/IO work, not to protect data — and they stay.
- Structured concurrency rule from the user's global instructions applies strongly here: **don't do long-running synchronous work inside a `Task`**. MPSGraph `.run` is the usual offender — the network wraps it in `CheckedContinuation` + `DispatchQueue` so the Swift concurrency thread keeps making progress. Follow the same pattern for any new GPU path.
- Delegate methods on `ChessMachine` fire on a private serial `.userInteractive` dispatch queue (not the main actor). Anything touching SwiftUI state must `Task { @MainActor in ... }`.
- **A GUI session save takes one consistent cut:** self-play stays paused from the champion export until the record is built (and until the replay buffer file is written when the save includes it), training from the trainer export until the record is built. Gate releases that can be reached twice go through `WorkerPauseGateHold` (the gate is not counted). Saves refuse while an arena runs; an arena waits for an in-flight save (`[ARENA] waiting for an in-flight session save …`), then marks itself active with no suspension point in between.
- **Every GUI `--train` termination** (time limit, step limit, legal-mass collapse, early stop) goes through `AutoTrainTermination` (`App/AutoTrainTermination.swift`): one shared claim, results written, `SessionLogger.shutdown()` to drain the log, then `_exit(0)`.
- **Probe isolation:** no probe, diagnostic or observer may change trainer, optimizer, replay-buffer or RNG state. A probe reads a snapshot or runs on its own copy and its own named random stream (`probe.<name>.<step>`). The one probe that touches training-graph state, the KL probe, only moves *when* a step's single dropout-RNG advance is issued (after its own forward instead of inside the training executable), never how many; `DropoutRNGStateTests.testKLProbeDoesNotChangeTheDropoutSequence` pins that. The KL probe's schedule is derived from the step index (`ChessTrainer.isKLProbeStep`), not from a per-process counter, so a resumed run probes on the steps the uninterrupted run would have.

## Training observability worth knowing about

The `[STATS]` line carries a dense set of counters. A few that matter for diagnosing training health:
- `pLoss` — outcome-weighted policy cross-entropy. **Unbounded on both sides** (negative is fine when well-predicted winning plays dominate). Read alongside `pEnt`, not in isolation.
- `pEnt` — mean Shannon entropy of the policy softmax, in nats. `log(4864) ≈ 8.49` at uniform init for the current 4864-cell policy head. Below `TrainingHealthThresholds.policyEntropyAlarm` (1.0 in-repo, in `Training/TrainingHealth.swift`) triggers `[ALARM] policy may be collapsing`.
- `vMean` / `vAbs` — mean / mean-abs of the derived value scalar `p_win − p_loss` (no tanh). `pW` / `pD` / `pL` — the W/D/L softmax batch-means (sum ≈ 1). The value-head collapse signature is `pD → 1.0` (equivalently `vAbs → 0` and staying there) — the post-WDL "everything is a draw"; watch `pD` falling off its `0.75` bias-init prior as the sign training is working. `vLoss` is now categorical-CE-scale (≈ `[0, ln 3]` at convergence), not the old MSE scale.
- `gNorm` — pre-clip global gradient L2 norm, reported every step. Compare against `ChessTrainer.gradClipMaxNorm`; values above it are clip events, not bugs.
- `diversity=unique=X/Y(%) diverge=N.N` — rolling `GameDiversityTracker` snapshot over the last 200 games; `diverge` is the avg ply at which pairs of games first differ. Steady-state healthy is `[0-5]`-heavy in the histogram tile.
- `[LAYER-HEALTH]` — `Training/LayerHealth.swift` (pure; site list derived from the architecture in graph build order, cross-checked against `weightTensorPlan()` and the built graph in `LayerHealthTests`), logged through `Training/LayerHealthLog.swift`. For every BN site whose output feeds ReLU / leaky ReLU, β/|γ| classifies channels **dead** (< −3), **mostly off** (−3 … −2) or **always on** (> +3) — `dead= off= alwaysOn= worst=<site>(…)`, plus `maxBetaOverGamma` / `minBetaOverGamma` as `value@site[channel]`. SiLU / GELU / unactivated BN sites are explicitly not classified (`dead=n/a` when none are). Also `rvMaxOverMedian` (largest BN running-variance max/median, any site), `rvOver10xMedian` (channels at ≥ 10× their site's median running variance, every site; `LayerHealth.runningVarianceRatios` is the one ratio definition; the checkpoint table's `rv≥10x` column per site), `rezeroCapFrac` + `saturated=k/N` (effective α = cap·tanh(α/cap) as a fraction of cap; saturated at ≥ 0.99), `nonFinite`. Two tiers: **live** (`[LAYER-HEALTH] live trainerStep=N scope=batch_norm_state_only …`) reads only BN γ/β/running stats + ReZero α via `ChessTrainer.readLayerHealthLiveState()` on the trainer's own `executionQueue` (between SGD steps — never concurrent with one); it rides every step line (`[STATS]`, `[REPLAY]`, `[VS-UCI]`). **checkpoint** (`[LAYER-HEALTH] checkpoint <replay-|vsuci-|session-><trigger> step=N trainerStep=N scope=all_tensors …` + a per-site table) runs on every trainer save from the already-exported weights + velocity (no extra GPU read) and adds `seZeroVel` / `seLowVel` / `worstSE` (SE FC1 units whose weight-velocity column — native `[in, out]` layout — is exactly 0, or below `lowVelocityFractionOfReferenceUnitNorm` × the layer's `lowVelocityReferencePercentile` (p90) unit norm), `valueFC1ZeroVel`, `maxAbs`; CLI runs record it under `layer_health` in `results.json`, and `--analyze-numerics` includes it (layer-health findings: non-finite = BAD, dead/always-on/zero-velocity = degraded; running-variance spread and ReZero saturation are reported without a verdict). Head shared offsets stay on `pLogitMean` / `vLogitMean` + the numerics audit. A failed health read logs `[LAYER-HEALTH] … failed: …` and never stops training or a save.

### Training health alarms

Every training path (GUI Play-and-Train and `--train`, `--replay-corpus`, `--train-vs-uci`) runs one shared evaluator, `TrainingHealthEvaluator` (`Training/TrainingHealth.swift`), through a per-run `TrainingHealthMonitor`: fourteen rules (`non_finite`, `dead_channels`, `value_fc1_zero_velocity`, `illegal_mass`, `gradient_collapse`, `loss_spike`, `policy_offset_drift`, `bn_running_variance_runaway`, `gradient_spike`, and — the GUI banner detectors' and legal-mass probe's conditions, shared with the banner through `TrainingHealthDetectorConditions` (OD-9) — `divergence`, `value_saturation`, `value_draw_saturation`, `legal_mass_stall`, then `bn_running_variance_jump`, the change counterpart of rule 8: a BN channel at ≥ 10× its site median that rose ≥ 10× above its own lowest ratio over the live reads of the previous 1,000 trainer steps, critical at ≥ 100×, or the ≥ 10× channel count doubling (+5); live reads only, from the learning gate on; reads before the process has trained 100 steps only build the baseline; its lookback (`Training/BatchNormRunningVarianceJump.swift`) emptied by every trainer-clock rewind; default action log) over every SGD step's record, a live layer-health read every 50 trainer steps on overall multiples, every save's checkpoint pass, and a value-FC1 velocity read at most 1,000 trainer steps apart. Thresholds are declared constants (`TrainingHealthThresholds`, measured against the incident runs); the 17 `training_health_*` parameters (Health tab) set enable, check interval, learning grace and one action per rule. Every rule only logs by default; a stop action ends a CLI run through its final save (`health-stop`, results `training_health_alarm`, **exit status 35**), suspends GUI training (`trainingSuspension = .healthAlarm`: worker parked, arenas and Promote Trainee Now refused, periodic autosave still runs) or ends GUI `--train` through `AutoTrainTermination`. The monitor is an observer: no random draws, no change to trainer, optimizer or buffer state. `results.json` carries `alarms` and `alarm_config`. `--replay-health-log <log>…` runs the same evaluator over saved logs, read only. See `documentation/training-health-alarms.md`.

## Run tracking: three axes (architectural decision, 2026-08-11)

The dashboards (`documentation/dashboards/`) plot every run on **three separate x-axes**, and they are not interchangeable. `registry.json` holds per-run segment config; `data/<run>.csv` (columns in `_schema.py`) is the source of truth; `master.py` renders.

- **step** — `cum_step = segment.cumstep_base + segment step`, the segment step being the lineage record's `segment_local_step` from format v11 and the header's `training_step` before (`dcm_lineage.step_reading`, the one Python reader). Exact, but a *work* axis only while batch size and replay ratio hold constant.
- **time** — `elapsed_train_sec`, which is **sleep-clamped**: `_clamped_timeline` banks `min(real_gap, segment_median_s_per_step × Δsteps + 120s)` per interval, one-directionally (faster-than-median intervals pass through uncapped). `wall_sec` is the same walk uncapped, so `wall_sec − elapsed_train_sec` is exactly what the clamp discarded. Keep both; the clamp must stay auditable rather than baked in.
- **compute** — `games_fed`, cumulative corpus games from the runner's own `games=`. The device-independent axis, and the one to reach for when comparing across machines.

Rules that follow from this, and that must not be quietly reversed:

- **Never normalize time across devices.** Where a lineage spans machines the by-time curve genuinely changes slope (v5 breaks 2.59× at cum 100,320, a Pacific-TZ VM on an M5 host → native M4 Pro; that is a VM-vs-native comparison, not a silicon one). That break is hardware and stays visible. With batch and replay ratio fixed, a "normalized seconds" axis reduces to `steps × reference_ms` — a relabelled step axis that adds nothing while destroying the record of real cost.
- **`games_fed` is measured, never modeled.** Where a segment's log is missing, leave it **blank** — not zero, not interpolated from an anchor. A modeled value in a measured column is worse than a gap because it still looks plottable.
- Each segment carries `device`, `model_id`, `games_base`, and pinned `elapsed_base_sec` / `wall_base_sec` in `registry.json`. Pins exist because prior segments' logs may be absent; without them the time axis silently restarts at zero.
- **Enumerated checkpoints are named from the out-model stem and the trainer step.** Every segment of a lineage run writes `<stem>-replay-step<T>` (`-vsuci-step<T>` for train-vs-UCI), `T` the trainer step at the save — the same value as the file's `training_step` from format v11 — so an exact resume continues its run's series under the same stem (a resume from `…-step36000` writes `…-step37000`). Saves land on trainer-step multiples of 1000 (plus the final save); a segment that trained no step writes no enumerated copy. Resumed segments written before v11 named their files `<stem>-replay-seg<k>-step<N>` (N their own step); those names stay as they are and are still refused as a rolling `--out-model`. Runs from before lineage records gave every resumed segment its own stem (`…-Qeu8-replay-step*`, `…-Qeu8-resume2-replay-step*`, …); those names stay as they are too. A probe loop for a resumed segment from v11 on takes `PROBE_ABOVE_STEP=<its start trainer step>` (so it skips the earlier segments' files under the stem) and, for a segment 0 that a later segment wrote after, a step limit (a trainer step); `PROBE_SEGMENT=<k>` is for the legacy `-seg<k>` names only, and the two are refused together (`experiments/probe_loop.sh`); the loop refuses a `TRAINER_PID` that is not the trainer writing the out-model (exit 3) and never records a probe that exited non-zero, and the tracker finds a resumed segment's files by its `segment_id` (`derive-registry`), never by an `enum_stem` glob (a glob over a stem several segments wrote into is reported, not filed). The app enforces: `--enumerate-checkpoints` never writes over a file the run did not write, and a run whose stem already holds step files it could reach (trainer steps above the one it starts from, up to that plus `--training-step-limit`, or all of them without one) refuses to start and names the files (`TrainerOutputFileGuard` in `CorpusReplayRunner.swift`). `registry.json` names only the *latest* via `out_model`, so a single glob is blind to every earlier segment. Each segment may therefore declare `enum_stem`; `enum_specs()` resolves one glob per segment and falls back to the old single glob when none is declared. `python3 replay.py discover-stems [run] [--write]` derives them from the checkpoints themselves, **by evidence rather than by filename**: a stem's suffix must be resume-shaped (which keeps a sibling run like `Qeu8e5` out of `Qeu8`), every file under one stem must agree on `model_id`, and the segment is then chosen by how many of the stem's files land on `cum_step`s the CSV already knows, tie-broken by which segment's length best matches the stem's extent, with all stems required to map onto segments monotonically in creation-time order. It refuses rather than guesses when that is ambiguous. **Do not infer the segment from the suffix** — qeu8's segment 0 predates enumeration, so its first enumerated segment is 1 and it wrote under the *unsuffixed* stem; trusting the name there invents 68 rows at cum steps that never existed. **Run it on the machine that holds `Models/`** — it reads `models_dir`, which is deliberately `~/…` so it resolves locally wherever the tracker runs.
- **The rolling `--out-model` file is checked before training** (corpus replay; train-vs-UCI writes session folders instead and refuses `--out-model`). It is never the `--start-model` itself and never anything but a regular file; it is never a name shaped like a step-enumerated checkpoint (`<stem>-replay-step<N>`, `-vsuci-step<N>`, `-step<N>` — recognized by `EnumeratedCheckpointNaming`'s own parser), whether or not a file is there; and an existing file is replaced only when it holds the `--start-model`'s `model_id` at the start model's own `training_step` — the rolling file of the state being continued. Anything else (an earlier run of the same command, which saved under its own freshly minted `model_id`; an earlier checkpoint of the same line, reached by a mistyped `--out-model`) refuses the run unless `--overwrite-out-model` is passed. A failed save is a warning the first time and halts the run on the next consecutive failure; a failed final or abort save fails the run outright, since nothing else holds its end state (`TrainerSaveFailureStreak.requireLastSaveSucceeded`, shared with train-vs-UCI). Corpus replay opens corpora read-only: unsealed `.open` shards are skipped with a warning, never recovered or modified. The one place that recovers a crash-leftover `.open` shard (truncate to its last complete game and seal, or remove one with none, each logged `[CORPUS-RECOVERY]`) is `--validate-corpus <dir> --fix`. A live writer's shard looks identical on disk, so every `ShardWriter` holds an exclusive `O_EXLOCK` lock on its `.open` file until it seals, discards or closes it (the kernel drops it when the process ends), and `--fix` skips any shard whose lock is held (`open-shard-in-use`) and then leaves `corpus.json` alone; writers from builds before the lock are not protected. Without `--fix` it only reports them.
- **Identify checkpoints by safetensors `__metadata__` (`model_id` + `training_step`), never by filename.** `training_step` is the trainer step from format v11 and, on corpus-replay and train-vs-UCI files before v11, the writing segment's step (read through `ModelFileStepReading` / `dcm_lineage.step_reading`, by the file's `creator`). Segment-local step numbering in files before v11 means names repeat across stems — and, before the app refused a reused stem, earlier segments' files were overwritten in place. `import-probes` enforces a modelID match per segment and refuses mismatches; `ckpt_inventory.py` builds a manifest from headers.

## Conventions specific to this project

- **File writes that could touch something the operation does not own go through `FileSafety`** (`Utils/FileSafety.swift`): exclusive create of a file or directory, publish-without-overwrite (`renamex_np(RENAME_EXCL)`), replace-a-regular-file-only (optionally only the exact file previously written, by device+inode), open-for-writing with an explicit refuse/truncate policy, numeric-suffix create, identity-checked removal (a directory is moved to a private name and checked there before it is deleted), and `F_FULLFSYNC`. Replacing and removing still check by path before acting, so a small window remains — `FileSafety`'s type doc states it per operation; don't describe these as race-free. A name validated for a file written via staging must leave `FileSafety.temporarySiblingNameOverhead` bytes of `NAME_MAX` free. The rules: touch only the exact files the operation writes, replace only regular files, never remove before writing, never silently overwrite, refuse folders and symbolic links, and throw a `FileSafetyError` naming the path. Don't reintroduce `FileManager.createFile` / `removeItem`-then-write / `.atomic` over a path the operation doesn't own, and don't add another helper for these — extend `FileSafety`.
- Most source comments are multi-paragraph design explanations, not function-summary boilerplate. When adding a tricky mechanism, match that style — explain *why*, including failure modes that motivated the design. See `BatchedSelfPlayDriver`'s class doc or `ReplayBuffer`'s class doc for the house style.
- The UI layer follows **one SwiftUI `View` struct per file**. `ContentView.swift` (`App/ContentView.swift`) is just the small composer that owns the shared `ChartCoordinator` and stacks `UpperContentView` over `LowerContentView`. The bulk of the session-lifecycle wiring lives in `App/UpperContentView/UpperContentView.swift` (~9.6k lines, large on purpose). When adding new UI pieces, prefer a new file under `App/UpperContentView/` (or the matching `Views/.../` subdir for chart tiles) over wedging another `View` struct into an existing file. The only property with a `some View` signature allowed on a `View` is `body` itself — helper `@ViewBuilder`/`some View` properties are NOT blessed. Decompose a complex `body` into proper child `View` structs (which may live in the same file as their parent), never into helper view properties.
- New architectural plans go into ROADMAP.md (with user's express permission, per the global rules). Don't silently invent a new markdown doc at the repo root.
- Don't say "draw collapse". You tend to throw this phrase around like salt at a french fry convention and most of the time you're wrong because you never check the fucking data details. You shoot from the hip without paying any fucking attention. If you find yourself thinking about writing 'draw collapse', you've probably fucked up in some way. For example, if you start with a high number of draws -- which every single training round will do -- that's not draw collapse. That's just draws.
- Details matter. Get them right. Verify them and make sure they're right -- Every time.
